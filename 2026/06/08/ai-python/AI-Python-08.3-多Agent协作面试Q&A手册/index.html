前言

本文档是对《第 8-9 周多 Agent 协作系统重新设计》的深度面试整理，涵盖架构重构、M0-M8 各模块的技术细节、以及实战中的挑战与解决方案。每一道题都基于真实的项目经验，适合作为技术面试的参考。

一、整体架构重构

Q1: 为什么要把 collaboration 模块全部重写？之前的架构有什么问题？

难度：⭐⭐⭐⭐⭐（专家级）
频率：★★★★★（必问）

回答结构

“重写的直接原因是 supervisor_analyzer.py 这个文件已经膨胀到了 700+ 行，一个人承担了意图分类、LLM 分析、Worker 执行等所有职责。这在代码层面表现为：一个函数内部同时在做三件事——先判断用户想干什么，再调用 LLM 做分析，然后根据结果直接执行任务。修改任何一个逻辑都需要在这个文件里改，测试也变得越来越困难。

更深层的问题是模块没有真正串联。虽然项目里已经有了 context_pipeline.py、dag_executor.py、peer_mailbox.py 这些设计良好的模块，但它们没有被接入主流程。supervisor_analyzer.py 的执行路径直接调了 agent_chat，跳过了任务分解和上下文裁剪。这意味着 M5 和 M6 实际上没有被使用，系统的上下文管理能力没有发挥出来。

还有两个结构性缺失：

没有意图识别层——所有用户消息都走完整的多 Agent 协作流程。用户问”什么是 JWT”也会触发 M1→M2→M3→M4→M5→M6→M7，浪费大量 Token 和延迟。

工作流模板没有用起来——workflow_service.py 有完整的模板系统，但 supervisor_analyzer.py 完全不参考。团队绑定的流程模板形同虚设。

所以重写的核心思路是：每个模块只做一件事，然后在图层面把它们串联起来。“

追问：具体是怎么拆分的？800 行代码变成了几个文件？

“原来的 700+ 行拆分成了 8 个文件，每个文件不超过 200 行：

文件 职责
m0_intent_router.py 只做意图识别，输出 routing_decision
m1_requirement_analyzer.py 只做需求分析，输出 analysis_summary 和 phases_plan
m2_clarification.py 只做需求澄清，处理 HITL 断点
m3_agent_orchestrator.py 只做 Agent 编排，检查可用性和处理缺失
m4_task_decomposer.py 只做任务分解，生成 DAG
m5_context_pipeline.py 只做上下文裁剪
m6_dag_executor.py 只做 Agent 调度执行
m7_verifier.py 只做独立验证

拆分后，每个模块的输入输出是明确的。比如 m1_requirement_analyzer.py 只依赖 messages 和 workflow_template，只输出 analysis 相关字段。修改它的逻辑不需要动其他任何文件。”

三、M1 与工作流模板的深度集成

Q3: M1 怎么做需求分析的？工作流模板具体怎么注入？

难度：⭐⭐⭐⭐（深入）
频率：★★★★（常见）

回答结构

“M1 接收 M0 传递过来的用户消息、团队 Agent 列表以及工作流模板（如果有），然后调用 LLM 做结构化分析。

Prompt 构建是核心设计。如果团队绑定了工作流模板，它会以参考上下文的形式注入：

关键设计点：模板不是强制路径，而是建议。Prompt 中明确写了”如果模板与需求冲突，以实际需求为准”。这样 Supervisor Agent 有完全的自由度。

输出通过 JSON Schema 校验后写入 state：

  • problem_type：决定后续的 SOP 选择
  • required_roles：M3 用这个字段从团队中匹配 Agent
  • phases：M4 用这个作为任务分解的参考
  • clarity_score：M2 用这个判断是否需要澄清

追问：M1 输出的 phases 和 M4 输出的 plan 有什么区别？

“phases 是阶段计划，是高层级的步骤划分，比如”设计阶段”、”编码阶段”、”测试阶段”。它是参考性的，不包含具体任务。

plan（DAG）是可执行任务，是细粒度的分配，比如”Task1: Coder-01 创建用户模型”、”Task2: Coder-01 实现登录 API”。它是执行指令。

两者的关系是：M1 给出建议路径（phases），M4 在 M1 的基础上细化出具体 task DAG。M1 的 phases 可以被 M4 沿用、合并或拆分——M4 有最终的决策权。”

四、M2 需求澄清的触发与用户交互

Q4: M2 怎么决定要不要问用户？会不会反复问同样的问题？

难度：⭐⭐⭐⭐（深入）
频率：★★★（常见）

回答结构

“M2 的触发条件是 clarity_score < 0.7。这个阈值不是拍脑袋定的，而是基于测试数据——当清晰度低于 0.7 时，直接执行后续流程有超过 30% 的概率需要退回重做，所以提前问清楚更划算。

会不会反复问是我的重点考虑。我做了两个机制：

问题合并——M2 不会逐个问题问。它会收集所有不明确的信息点，合并为一条结构化的 HITL 消息，一次性展示给用户。比如：

增量更新——用户可以不回答所有问题，只补充他知道的部分。用户回答后，M1 会用新信息重新分析，clarity_score 会重新计算。如果还不够，再次触发 M2。但第二次触发时，不会重复问已经回答过的问题——missing_info 中会排除已确认的项。

另外，HITL 有超时机制（默认 5 分钟）。超时后系统会按默认配置继续执行（如使用最常用的技术栈方案），而不是无限等待。”

追问：用户回答后，M1 重新分析会丢失之前的分析结果吗？

“不会。LangGraph 的 AsyncPostgresSaver 会在每个节点执行后持久化完整状态。M1 重入时，state 中已经包含了上一轮的分析结果。M1 只在新的 messages（用户的回答）基础上做增量更新——补充 clarity_score 和 phases_plan，但不覆盖原有的 problem_type 和 required_roles（除非用户明确说”我不是这个意思”）。”

五、M4 任务分解的 DAG 生成

Q5: M4 怎么保证 LLM 生成的 DAG 没有环？拓扑排序具体怎么做？

难度：⭐⭐⭐⭐⭐（专家级）
频率：★★★★（常见）

回答结构

“LLM 生成的 DAG 可能存在两种环：

  • 直接环：A → B → A（自己依赖回自己）
  • 间接环：A → B → C → A（循环依赖）

我在 M4 中实现了一个通用的拓扑排序环检测器：

如果检测到环，M4 会拒绝该输出，让 LLM 重新生成，最多重试 3 次。如果 3 次后仍然有环，降级为串行执行（忽略依赖关系，按顺序跑）。

环的常见原因有两个：一个是 LLM 在描述复杂任务关系时搞混了先后顺序；另一个是 LLM 生成了递归任务（如”Task1: 设计 → Task2: 实现 → Task3: 修改设计”）。第一种情况通常重试就能解决，第二种需要限制 LLM 的生成规则（禁止递归依赖）。”

追问：并行执行时，不同 Agent 同时修改同一个文件怎么办？

“这是 M6 中 Workspace Manager 的职责。并行 task 在各自的 Copy-on-Write 副本上操作。合并时通过 git 三路合并：如果改动的是不同文件，直接合并；如果改的是同一文件的不同区域，自动合并；如果改的是同一区域，生成冲突标记并升级为 HITL。

还需要说明一点：同 phase 内的 task 在设计时就已经考虑了并行安全。M4 在生成 DAG 时，会把需要修改同一文件的 task 放在不同 phase 或同一个 phase 内串行执行。这是通过一个文件锁启发式检查实现的——如果任务列表中有两个以上 task 都提到了同一个文件名，自动给它们添加依赖关系。”

六、M6 DAG 执行器

Q6: M6 是怎么按 DAG 调度 Agent 执行的？执行进度怎么实时呈现给用户？

难度：⭐⭐⭐⭐（深入）
频率：★★★★（常见）

回答结构

“M6 的核心是一个拓扑排序 + 异步任务调度循环：

进度推送到 WebSocket 的方式是：每完成一个 task，就通过 Publish channel 发送 task_completed 事件。前端收到事件后，更新 TaskCard 上对应 task 的图标和状态文字。

执行过程中，M8 的 Peer Mailbox 负责 Agent 间的通信。比如后端 Agent 改了一个接口定义，它可以通过 M8 发一条消息给前端 Agent：”接口路径从 /api/login 改成了 /api/auth/login“。前端 Agent 收到后调整自己的实现。这种通信不经过 LangGraph 的 state，直接走 Redis Pub/Sub，延迟 < 50ms。”

追问：如果某个 task 执行失败了，M6 会怎么处理？

“M6 内部有一个失败处理的三级机制：

  1. 自动重试（Transient Error）：如果是 API 超时、模型不可用等临时性错误，自动重试，指数退避（1s, 2s, 4s）。
  2. 内容重试（Content Error）：如果 Agent 输出了不符合格式要求的内容，注入错误信息后重试，最多 3 次。
  3. 重规划（Plan Error）：如果某个 task 连续失败 3 次，M6 不会无限重试。它会调用 M4（当前 state 不变）重新生成剩余任务的 DAG，排除失败的 task。如果重规划后仍然失败，升级为 HITL。

关键设计：失败只影响当前 task 和依赖它的后续 task。已经完成的 task 不受影响。”

七、M7 独立验证

Q7: M7 的独立验证怎么保证客观性？验证 Agent 知道的信息范围怎么控制？

难度：⭐⭐⭐⭐（深入）
频率：★★★（常见）

回答结构

“M7 的核心机制是信息隔离——验证 Agent 只看到需求（requirements_anchor）和产出物（artifacts），看不到执行过程，也看不到是哪个 Agent 执行的。

追问：M7 和已有的 Validation Gate 有什么区别？两个都要用吗？

“两者定位不同，都要用。

Validation Gate 是在单个 Agent 输出后立即执行的，检查格式、事实、安全等硬性指标。它是局部验证，延迟低（< 1s）。

M7 是在所有任务都完成后执行的，从整体上验证所有产出物是否满足用户需求。它是全局验证，延迟较高（5-10s），但因为是在任务完成后执行，不影响执行效率。

两者是互补关系：Validation Gate 保证单个 Agent 的输出质量，M7 保证整个协作的成果质量。”

八、LangGraph 图定义

Q8: 重新设计后的 graph.py 只有 200 行，比之前少了 100 行，具体少了什么？

难度：⭐⭐⭐（进阶）
频率：★★★（常见）

回答结构

“之前的 graph.py 混入了三件事：

  1. 图定义（节点、边、路由）
  2. 节点的部分业务逻辑（如 M1 的 LLM 调用部分写在了图定义中）
  3. WebSocket 事件流处理（在节点执行前后发送事件）

重构后，图定义只做图编排。业务逻辑在独立的 m0~m8 文件中，事件流处理在 streaming.py 中。graph.py 只负责注册节点、连接边、设置路由条件——这是它唯一应该做的事情。

这样做的好处是：如果未来要换引擎（比如从 LangGraph 换成 Temporal），只需要重写 graph.py 一个文件，8 个业务模块和事件流处理完全不受影响。因为每个业务模块都是独立的 async function(state) -> dict，不依赖 LangGraph 的任何特性。”

九、面试亮点总结

亮点 深度解析 面试话术
M0 两级路由 规则优先（零 LLM）+ LLM 兜底，85% 消息走规则路径 “规则处理 85% 的场景，LLM 只处理那 15% 规则无法判断的情况，单次调用成本 0.001 元”
工作流模板注入 作为建议而非强制，LLM 可裁剪、合并、忽略 “模板不是铁律，是参考建议，在不强制的前提下提供了最佳实践”
M7 独立盲审 验证 Agent 看不到执行过程，只能看到需求和产物 “执行者自验存在确认偏差，盲审让验证结果更客观”
DAG 环检测 采用 Kahn 算法的拓扑排序 + 自动重试 + 串行降级 “LLM 生成的 DAG 一定有环？不一定，但拓扑排序能保证 100% 检测到”
M6 三级失败处理 瞬态重试 → 内容重试 → 重规划 → HITL “单点失败不触发全流程回滚，M6 会重新规划剩余任务”
~200 行图定义 职责分离，LangGraph 可替换 “把业务逻辑从 graph.py 抽到独立文件，换引擎只改一个文件”
M2 问题合并 + 增量更新 不会反复问，超时自动降级 “我设计的一定是用最小次数问完最多的问题”

一句话总结

“第8-9周的重构核心是从 700 行耦合到 8 个独立模块，新增 M0 意图识别、注入工作流模板、实现独立盲审，让系统在结构化和灵活性之间取得了平衡。这个架构既保留了 SOP 的稳定性，又支持了动态适配的灵活性。”

十、实战挑战与最佳实践

挑战 1：循环依赖

任务分解时可能出现 A→B→A 的循环依赖，需要：

  • 分解时检测环并报错
  • 让 M4（任务分解）重新规划

解决方案：Kahn 算法拓扑排序 + 最大 3 次重试 + 串行降级

挑战 2：上下文裁剪

每个 Agent 不需要看到全部上下文，只看到与自身任务相关的部分：

  • Agent 只看到前置任务的产出摘要
  • 敏感信息（如 API Key）只发给需要的 Agent

解决方案：M5 Context Pipeline 按角色和任务动态裁剪上下文

挑战 3：失败处理

某个 Agent 失败时的策略：

  • 重试（transient 错误）
  • HITL 升级（无法自动解决）
  • 跳过（可选任务）

解决方案：M6 三级失败处理机制

最佳实践

  1. 任务粒度适中：太细导致调度开销大，太粗无法并行
  2. 明确依赖关系：避免隐式依赖导致执行顺序混乱
  3. 充分的 Agent 通信：关键变更及时通知相关 Agent
  4. 验证先于合并：所有产出通过验证后再返回给用户

练习题

  1. 设计一个”写技术博客”的多 Agent 系统，包含：规划、写作、审稿三个角色
  2. 实现一个简单的 DAG 调度器，支持并行执行
  3. 设计 Agent 通信协议，处理”接口变更通知”场景
