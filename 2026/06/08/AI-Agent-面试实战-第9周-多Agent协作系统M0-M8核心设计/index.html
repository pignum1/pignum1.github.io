AI Agent 面试实战 — 第9周：多 Agent 协作系统 M0-M8 核心设计

M0-M8 核心设计：解决什么问题、为什么这么设计、面试如何回答。

一、M0 意图识别

解决的问题

所有消息都走完整的多 Agent 协作流程，导致简单请求（如”什么是 JWT”）也触发 M1→M2→…→M7，浪费大量 Token 和延迟。

为什么这么设计

规则优先 + LLM 兜底的两级路由，85% 的消息零 LLM 调用就完成路由。

面试回答

“M0 要解决的核心问题是：不是所有消息都需要多 Agent 协作。 用户问’什么是 JWT’只需要一个 Agent 回答就行，但如果也走完整的多 Agent 流程，会浪费 5-10 秒和几千 Token。

我的设计是两级路由：

  • 第一级是规则引擎，零 LLM 调用。检测 @AgentName、闲聊关键词、多 Agent 触发词（’帮我写’、’开发’、’设计’），覆盖 85% 的场景。
  • 第二级是 LLM 兜底，当规则无法判断时，调用 Haiku 级别的轻量模型，只输出 single 或 multi，不做内容生成。

这样设计的原因是：高频场景用规则快速处理，低频模糊场景用 LLM 准确判断。 简单问答 200ms 内返回结果，复杂需求才走协作流程。”

二、M1 需求分析

解决的问题

Supervisor Agent 在分析需求时没有参考信息，只能凭模型自身的知识，导致每个任务的执行路径差异大、不稳定。

为什么这么设计

注入团队工作流模板作为参考，提供最佳实践但不强制遵循。

面试回答

“M1 要解决的核心问题是：需求分析不能没有上下文。 没有团队规范的参考，同一个需求今天和明天的执行路径可能完全不同，用户无法预期系统行为。

我的设计是在分析 Prompt 中注入团队绑定的工作流模板：

  • 如果团队绑定了模板，作为结构化参考注入
  • 模板不是强制路径，Prompt 中明确写’如果模板与需求冲突，以实际需求为准’
  • Supervisor Agent 可以沿用、裁剪、合并或完全忽略模板

这样设计的原因是：在标准化和灵活性之间找到平衡。 模板提供最佳实践的起点，但不限制 Agent 的发挥空间。成熟业务用模板保证流程稳定性，创新任务可以自由规划。”

三、M2 需求澄清

解决的问题

需求不明确时直接启动协作，执行到一半才发现理解错了，导致大量返工浪费。

为什么这么设计

在进入执行之前就澄清需求，减少返工成本。一次性问完所有问题，不反复打扰用户。

面试回答

“M2 要解决的核心问题是：需求理解错了，后面做再多都是浪费。 如果用户说’帮我做一个登录系统’，但没说是 JWT 还是 OAuth2、没说是前后端分离还是模板渲染，直接执行到一半才发现理解错了，前面所有 task 都要重做。

我的设计是在 M1 输出的 clarity_score < 0.7 时触发澄清：

  • 把所有不确定的点合并为一个 HITL 卡片，一次性展示给用户
  • 用户可以不回答全部问题，只补充他知道的部分
  • 用户回答后 M1 重新分析，clarity_score 重新计算
  • 超时 5 分钟后按默认配置继续执行

这样设计的原因是：执行前的 30 秒澄清可能节省执行后的 30 分钟返工。 在源头把需求锁死，后面的任务分解和执行才有意义。”

四、M3 Agent 编排

解决的问题

Supervisor 分析出需要哪些角色，但团队中可能没有对应的 Agent，或者 Agent 正在忙。

为什么这么设计

将”需要什么角色”和”有没有这个 Agent”解耦，缺失角色通过 HITL 让用户决策。

面试回答

“M3 要解决的核心问题是：需求分析出来了，但团队能力跟不上。 M1 说需要后端工程师，但团队里只有前端和架构师。如果系统直接报错，用户体验很差。

我的设计是检查可用性，分两种情况处理：

  • 如果 Agent 都存在 → 直接分配
  • 如果有缺失 → 通过 HITL 通知用户，提供两个选择：
    • ‘邀请新 Agent’（跳转到创建页面）
    • ‘跳过该角色’（降低复杂度，由现有 Agent 分担）

这样设计的原因是：不要让系统因为 Agent 缺失而崩溃，给用户选择权。 用户知道自己的团队能力边界，他们能做出最合理的决策。”

五、M4 任务分解

解决的问题

Agent 拿到需求后不知道从哪开始，或者自己决定执行顺序，导致关键步骤遗漏或依赖关系错乱。

为什么这么设计

用 LLM 动态生成 DAG，拓扑排序保证合法性，文件冲突检测保证并行安全。

面试回答

“M4 要解决的核心问题是：模糊的需求无法直接执行，必须拆解为具体的、有依赖关系的可执行任务。 用户说’做一个登录系统’，不能直接丢给 Coder-01 让他自己猜——架构设计还没做，数据库表还没创建，直接写代码肯定会出问题。

我的设计是 LLM 动态生成 DAG，核心机制是：

  • LLM 生成：输入确认后的需求和可用角色，输出分阶段的任务列表，每个任务标注 role 和 depends_on
  • 环检测：用 Kahn 算法的拓扑排序验证 DAG 合法性，有环则拒绝输出并重试
  • 文件冲突预防：扫描所有 task 的 description，如果两个 task 都提到同一个文件名，自动添加依赖关系，确保串行修改

这样设计的原因是：让 LLM 做它擅长的事（语义理解、任务拆解），让代码做它擅长的事（合法性校验、冲突检测）。 两者结合，既灵活又可靠。”

六、M5 上下文管理

一、M5 上下文管理的分类

在 M5 中，我把上下文分成了 5 类：

类别 内容 来源 占比
System Prompt Agent 的角色定义、能力边界、行为规则 Persona 配置 10%
Memory Context 团队记忆（L2）+ 个人记忆（L3+L4） Memory Manager 40%
RAG Context 知识库中检索到的相关文档 RAG Engine 30%
Task Context 当前任务的输入、前置任务的产出 TaskState 15%
Skill Instructions 当前任务绑定的 Skill 指令 Skill Registry 5%

二、为什么这么设计？每个分类解决什么问题？

1. System Prompt（10%）

解决的问题：Agent 不知道自己的角色和能力边界。

没有 System Prompt 时，Agent 只能凭模型自身的知识回答，不知道自己是架构师还是程序员，不知道能用什么工具。把 System Prompt 独立出来，保证 Agent 每次执行都明确自己的身份。

为什么不放大比例：System Prompt 通常是 500-1000 tokens，10% 已经够用。多了会挤压 Memory 和 RAG 的空间。

2. Memory Context（40%）

解决的问题：Agent 没有团队经验和历史记忆。

如果 Agent 不记得团队之前的技术决策（”后端用 FastAPI”），可能会做出不一致的方案。Memory Context 提供了四层记忆：

  • L1 系统记忆：全局规范，所有 Agent 共享
  • L2 团队记忆：团队决策、架构选型，Leader 写入自动同步
  • L3 个人记忆：Agent 的跨团队经验，随身携带
  • L4 上下文记忆：当前 Session 的对话历史

为什么占 40%：团队经验是 Agent 做出正确决策的最重要参考。过去决策的上下文，比通用知识库更关键。裁剪时，L4 最先裁，L1 最后裁。

3. RAG Context（30%）

解决的问题：Agent 不知道外部知识库的相关内容。

用户需求可能涉及特定的技术文档、API 规范、代码库结构。没有 RAG，Agent 只能依赖模型训练数据中的知识（可能过时或不相关）。

为什么占 30%：外部知识重要，但优先级低于团队内部记忆。裁剪时，RAG 比 Memory 先裁。

4. Task Context（15%）

解决的问题：Agent 不知道当前要做什么、前置任务做了什么。

M4 分解出的每个 task 是孤立的。Agent 需要知道：

  • 这个 task 的输入是什么？（”设计用户模型”）
  • 前置 task 的产出是什么？（架构师输出的接口定义）
  • 当前进度是什么？（第 2 个 phase 的第 1 个 task）

为什么占 15%：Task Context 是当前任务的核心输入，不能裁。但内容通常较短，15% 已经够用。

5. Skill Instructions（5%）

解决的问题：Agent 不知道当前 task 有没有特殊的执行要求。

如果 task 绑定了 Skill（如”代码审查”），Agent 需要知道 Skill 的指令和输出格式。没有这个，Agent 可能会用默认方式执行，而不是按照团队定义的标准流程。

为什么只占 5%：Skill 指令通常很短（200-500 tokens），5% 足够。

三、这样设计有什么优势？

优势 1：剪裁时知道先扔什么

Token 不足时的裁剪顺序（从先到后）：

如果没有分类，裁剪时只能一刀切（”把上下文截断到 8000 tokens”），可能把关键的 Task Context 截掉，保留了不太重要的 RAG 结果。

优势 2：调试时知道问题在哪

如果 Agent 执行结果不好，可以快速定位：

问题现象 排查方向
Agent 没有引用团队决策 Memory 不够
Agent 用了过时的信息 RAG 没检索到合适的文档
Agent 偏离了角色 System Prompt 不清晰
Agent 忽略了 Skill 要求 Skill Instructions 没注入

优势 3：每个 Agent 看到的内容不同

两个 Agent 看到的 L2 Memory 相同（共享团队决策），但 L3 Memory 和 Task Context 不同（Coder 看到 Architect 的产出），System Prompt 和 Skill 也不同。这是 M5 的核心价值。

四、面试回答

面试官问：”你的上下文管理器怎么设计的？为什么分这么多类？“

“我的上下文管理器把 Agent 看到的内容分成了 5 类：System Prompt、Memory、RAG、Task Context、Skill Instructions。

分 5 类的核心原因是：不同类型的上下文有不同的生命周期和重要性，不能同等对待。

  • System Prompt 是 Agent 的根基，不能裁
  • Memory 是内部经验，最重要的参考
  • RAG 是外部知识，优先级低于内部经验
  • Task Context 是当前任务的输入，不能裁
  • Skill Instructions 是特殊要求，通常很小

这样设计的最大好处是剪裁时知道先扔什么。Token 不够时，先裁 RAG 的 Top-K 数量，再裁 L4 Memory 中重要性低的条目，最后才裁 L2 团队记忆。System Prompt 和 Task Context 从来不裁。

如果我不分这 5 类，把所有的上下文拼在一起，Token 不够时只能一刀切——截断文件、丢失关键信息。有了分类，剪裁是精准的、可预期的。”

面试官可能追问：”Memory 占了 40%，如果 Memory 内容很多怎么办？“

“Memory 占了 40%，是因为它是 Agent 做出正确决策的最重要参考。但确实可能很多。

我们的处理是三级缓冲：

  1. 剪裁：先裁 L4 中 importance 最低的条目，再裁 L3，最后才动 L2
  2. 压缩：如果剪裁不够，调用轻量 LLM 把多条记忆压缩为一段摘要（70% 触发）
  3. 硬限制：每个 Agent 的 Memory Token 预算固定，超了就裁，不能超

极端情况下，Agent 可能只看到最重要的 5 条记忆，但它能看到最相关的。这比看到 50 条不相关的记忆要好。”

七、M6 DAG 执行

解决的问题

多个 Agent 的任务有依赖关系，必须按顺序执行；无依赖的任务如果能并行执行，可以显著缩短总耗时。

为什么这么设计

拓扑排序 + 并行执行 + 进度推送 + 三级失败处理。

面试回答

“M6 要解决的核心问题是：有依赖关系的任务不能乱序执行，无依赖关系的任务应该并行执行以节省时间。 比如必须先完成架构设计（t1），才能开始编码（t2、t3）。但 t3 和 t4（注册 API 和登录 API）没有互相依赖，可以并行写。

我的设计是一个执行循环，核心机制是：

  • 拓扑排序：每次从 DAG 中找出所有依赖已完成的 task，作为一个 batch 并行执行
  • 工作空间隔离：并行 task 在各自的 Copy-on-Write 副本上操作，互不干扰
  • 进度推送：每完成一个 task，通过 WebSocket 推送 task_completed 事件，前端实时更新
  • 三级失败处理：
    • 瞬态错误（API 超时）：自动重试，指数退避
    • 内容错误（输出格式不符）：注入反馈后重试，最多 3 次
    • 持久错误（连续失败）：重规划剩余任务或升级 HITL

这样设计的原因是：不浪费可并行的机会，也不让单点故障影响全局。 并行 task 同时执行，串行 task 按依赖顺序执行，失败时只重做受影响的部分。”

八、M7 独立验证

解决的问题

执行者自验存在确认偏差——自己写的代码很难客观地找出自己的 Bug。

为什么这么设计

盲审机制：验证 Agent 不知道执行过程，只看到需求和产物，保证客观性。

面试回答

“M7 要解决的核心问题是：谁来做质量把关？ 如果让执行者自验，他倾向于相信自己的输出是正确的（确认偏差）。如果让另一个 Agent 验证，但告诉他’这是谁写的、怎么做出来的’，他可能会受到执行过程的影响，无法客观评价。

我的设计是盲审机制：

  • 验证 Agent 只看到两样东西：用户需求（requirements_anchor）和所有产出物（artifacts）
  • 看不到：执行计划、Agent 分配、中间对话
  • 验证维度：功能完整性、一致性、安全性
  • 输出：passed/failed + severity + feedback

如果验证不通过，根据严重程度：

  • low/medium：回到对应 Agent 重试（带上反馈信息）
  • high：升级为 HITL，由人工判断是否偏离需求

这样设计的原因是：盲审保证了客观性。 验证者不知道谁写的、怎么写的，只从用户需求的原始角度出发，检查最终产物是否满足要求。这是 Code Review 在 Agent 系统中的等价实现。”

九、M8 对等通信

解决的问题

Agent A 在执行过程中发现了会影响 Agent B 的变更，但无法通知对方。

为什么这么设计

异步消息通道，不经过 LangGraph state，低延迟通信。

面试回答

“M8 要解决的核心问题是：Agent 之间需要信息同步，但不能通过 LangGraph state——state 是给人类看的，不是给 Agent 用来聊天的。 如果 Coder-01 改了接口路径，Coder-02 可能还在用旧路径写前端代码，等执行完才发现不匹配。

我的设计是基于 Redis Pub/Sub 的异步消息通道：

  • 消息类型：api_change、schema_update、question、share
  • 发送：peer_mailbox.send(from, to, message) → 发布到目标 Agent 的频道
  • 接收：peer_mailbox.receive(agent_id) → 消费自己频道的消息
  • 延迟：< 50ms
  • 不经过 LangGraph state：消息不触发 Checkpointer 持久化，不增加 state 体积

这样设计的原因是：Agent 间的沟通应该轻量、及时、不影响主流程。 通过独立通道的消息机制，Agent 可以在不影响 LangGraph 状态机的前提下，实时同步信息。”

十、面试总结

模块 核心问题 设计方案 面试关键词
M0 所有消息都走多 Agent 流程 规则优先 + LLM 兜底 两级路由，85% 零 LLM
M1 需求分析没有参考信息 注入工作流模板 参考建议非强制
M2 需求不明确导致返工 问题合并一次性澄清 源头锁定，减少返工
M3 团队能力跟不上需求 Agent 可用性检查 缺失角色用户决策
M4 模糊需求无法直接执行 DAG 生成 + 拓扑排序 环检测 + 文件冲突预防
M5 5 类上下文同等对待导致裁剪不可控 分类管理 + 三级缓冲（剪裁→压缩→硬限制） 分类裁剪，知道先扔什么
M6 依赖关系导致执行混乱 拓扑排序 + 并行执行 三级失败处理
M7 执行者自验有偏见 盲审机制 只看到需求和产物
M8 Agent 间需要信息同步 异步消息通道 不经过 state，低延迟

一句话总结：

M0-M8 的设计核心是：把多 Agent 协作拆解为”识别→分析→澄清→编排→分解→组装→执行→通信→验证”九个独立环节，每个环节只做一件事。让 LLM 做语义理解，让代码做合法性校验，两者结合既灵活又可靠。
