前言

在单 Agent 系统中，我们通过工具调用、记忆管理、规划能力让 AI 能够完成复杂任务。但当任务涉及多个专业领域、需要多种技能协同工作时，单 Agent 就显得力不从心了。

多 Agent 协作让不同的 AI 角色（如架构师、程序员、测试工程师）各司其职，通过分工合作完成更复杂的任务。

二、多 Agent 协作的 9 个核心组件

相比单 Agent，多 Agent 新增了任务分解、Agent 编排、Agent 通信、独立验证等组件。

1. 意图识别（M0）— 新增多 Agent 判断

项目 内容
职责 判断是否需要多 Agent 协作，还是单 Agent 即可完成
输出 collaboration_type: single | multi
判断依据 任务复杂度、涉及领域数量、是否需要多角色协同
示例 “帮我写一个 Hello World” → single；”做一个登录系统” → multi

2. 需求分析（M1）— 多 Agent 场景

项目 内容
职责 分析需求所需的技术栈、涉及的角色、任务范围
输出 analysis（问题类型、复杂度、所需角色、是否明确）
关键差异 单 Agent 只分析内容；多 Agent 还要分析需要哪些角色
示例 “需要前端、后端、数据库三个角色”

3. Agent 编排（M3）— 多 Agent 特有

项目 内容
职责 检查团队中可用 Agent，匹配所需角色，处理缺失情况
输入 analysis.required_roles
输出 available_agents, missing_agents
关键功能 能力匹配、工作负载检查、HITL 邀请缺失 Agent
示例 “需要后端工程师，团队中有 Coder-01（匹配 ✅），缺少前端工程师（需邀请）”

4. 任务分解（M4）— 多 Agent 特有

项目 内容
职责 将需求拆解为可分配给不同 Agent 的子任务 DAG
输入 requirements, available_agents
输出 plan（phases + tasks，每个 task 标注 role）
关键功能 依赖分析、并行任务识别、角色匹配
示例 “Task1（架构师）→ Task2（后端，依赖 Task1）+ Task3（前端，依赖 Task1）→ Task4（测试，依赖 Task2+Task3）”

5. 上下文组装（M5）— 每个 Agent 独立

项目 内容
职责 为每个 Agent 裁剪独立的上下文
差异 每个 Agent 看到不同的上下文（与自身角色和任务相关）
输入 task, artifacts（前置任务产出）, requirements
输出 WorkerContext（该 Agent 专属的 Prompt）
示例 后端程序员看不到前端的 UI 设计稿细节，只看到接口定义

6. Agent 执行（M6）— 多 Agent 调度

项目 内容
职责 按 DAG 调度各 Agent 执行任务，支持并行
输入 plan, available_agents
输出 artifacts（所有 Agent 的产出）
关键功能 并发控制、失败重试、产物传递
执行单元 每个 Agent 内部是一个完整的两轮对话（接收任务 + 输出结果）

7. Agent 通信（M8）— 多 Agent 特有

项目 内容
职责 Agent 之间交换信息、澄清依赖、协调变更
通道 Redis Pub/Sub（异步）
消息类型 请求澄清 / 通知变更 / 共享上下文
示例 “后端修改了接口定义 → 通知前端更新调用”

8. 独立验证（M7）— 多 Agent 特有

项目 内容
职责 由不知道执行过程的独立 Agent 验证所有产出
输入 requirements, artifacts
输出 verification（通过/退回/阻塞）
关键设计 盲审——验证者不知道谁写的，保证客观性
失败处理 退回对应 Agent 修改，或升级 HITL

9. 结果合并 — 多 Agent 特有

项目 内容
职责 将各 Agent 的产出合并为统一格式返回给用户
输入 artifacts, verification
输出 最终响应（结构化的产物列表 + 验证报告）
示例 “完成了：架构方案.md、login.py、login.test.py、审查报告.md”

三、组件对比：单 Agent vs 多 Agent

组件 单 Agent 多 Agent 说明
意图识别 ✅ 简单分类 ✅ 需要判断是否需要多 Agent 多 Agent 版输出 collaboration_type
需求分析 ✅ ✅ 更重 多 Agent 版需要分析涉及的角色数量
需求澄清 ✅ ✅ 相同，通过 HITL 确认
Agent 编排 ❌ ✅ 新增 检查可用 Agent，处理缺失
任务分解 ❌ ✅ 新增 拆解为可分配的子任务 DAG
上下文组装 ✅ 单上下文 ✅ 多个独立上下文 每个 Agent 看到不同的上下文
Agent 执行 ✅ 单 Agent ✅ 多 Agent 并行/串行 DAG 调度器负责协调
Agent 通信 ❌ ✅ 新增 Redis Pub/Sub 通道
独立验证 ❌ ✅ 新增 盲审机制
结果合并 ❌ ✅ 新增 合并各 Agent 产出
输出验证 ✅ ✅ 相同，对每个 Agent 输出独立验证
记忆存储 ✅ ✅ 多级写入 L2（团队共享）+ L4（Agent 个人）
响应输出 ✅ ✅ 结构化 包含多个产物和验证报告

六、实战挑战与最佳实践

挑战 1：循环依赖

任务分解时可能出现 A→B→A 的循环依赖，需要：

  • 分解时检测环并报错
  • 让 M4（任务分解）重新规划

挑战 2：上下文裁剪

每个 Agent 不需要看到全部上下文，只看到与自身任务相关的部分：

  • Agent 只看到前置任务的产出摘要
  • 敏感信息（如 API Key）只发给需要的 Agent

挑战 3：失败处理

某个 Agent 失败时的策略：

  • 重试（transient 错误）
  • HITL 升级（无法自动解决）
  • 跳过（可选任务）

最佳实践

  1. 任务粒度适中：太细导致调度开销大，太粗无法并行
  2. 明确依赖关系：避免隐式依赖导致执行顺序混乱
  3. 充分的 Agent 通信：关键变更及时通知相关 Agent
  4. 验证先于合并：所有产出通过验证后再返回给用户

七、总结

多 Agent 协作通过专业化分工和结构化协作，让 AI 系统能够处理更复杂的任务。核心思想是：

  • 编排层负责规划和调度
  • 执行层由多个专业 Agent 各司其职
  • 验证层保证产出质量

相比单 Agent，多 Agent 系统更复杂，但能完成更专业、更可靠的工作。

  3. 设计 Agent 通信协议，处理”接口变更通知”场景
