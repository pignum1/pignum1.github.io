AI Agent 面试实战 — 第9周补充：聊天室与三模式协作系统 Q&A

基于《The Boy Assistant》聊天室与三模式协作系统，涵盖整体架构、Swarm/Supervisor/LangGraph 三引擎、暗流信息架构、Harness 横切层、输入框行为机等高频面试题。

一、整体架构设计

Q1: 你们的三模式协作引擎是什么？为什么用三种模式而不是一个通用引擎？

难度：⭐⭐⭐⭐（深入）
频率：★★★★★（必问）

回答：

“我们的系统提供了三种协作模式：Swarm（群聊模式）、Supervisor（主管模式）、LangGraph（工作流模式）。它们不是三个独立产品，而是从非结构化讨论到严格 SOP 执行的连续光谱。

Swarm 模式是自由讨论模式，Agent 地位平等，通过三阶段流水线（平行讨论→并行执行→HITL 决策）完成头脑风暴或开放设计任务。适合没有标准答案、需要多方视角碰撞的场景。

Supervisor 模式是主管决策模式，一个 Leader Agent（Supervisor）负责分析需求、分解任务、委派给专业 Agent 执行。M0-M7 的固定管道保证了流程的确定性，适合特性开发或多角色项目。

LangGraph 模式是严格工作流模式，通过 SOP Designer 预定义 DAG，节点按拓扑排序执行。适合已知流程的合规审查或部署流水线。

为什么不做一个通用引擎？ 因为不同场景的最优解不可通约。自由讨论的灵活性和 SOP 的确定性是冲突的。用单一引擎要么牺牲灵活性（不适合探索性任务），要么牺牲确定性（不适合合规场景）。三模式让用户根据团队类型选择最优协作方式。”

模式 适合团队 核心特点 典型场景
Swarm 研究团队 Agent 平等，三阶段流水线 头脑风暴、开放设计
Supervisor 开发团队 Leader 驱动，M0-M7 管道 特性开发、多角色项目
LangGraph 运维团队 SOP Designer 预定义 DAG 合规审查、部署流水线

追问：三种模式如何选择？

“在创建团队时配置。开发团队通常用 Supervisor 模式，研究团队用 Swarm 模式，运维团队用 LangGraph 模式。模式绑定团队，不随 session 变化。用户在同一团队内始终面对统一的聊天室界面，不感知后端引擎的切换。”

Q2: 聊天室的”暗流信息架构”是什么？有什么优势？

难度：⭐⭐⭐（进阶）
频率：★★★★（常见）

回答：

“暗流（Undercurrent）是本系统的核心 UX 创新。类比于河流——表面是对话的流动，水下是结构化信息的暗涌。

表面流是对话消息流：用户的输入、Agent 的回复、HITL 决策卡、系统通知。用户 90% 的时间只看表面流。

暗流是右侧抽屉中的结构化信息：任务 DAG 进度、产物文件树、团队状态、工作流迷你图。用户只有需要时才展开查看，约 10% 的时间。

优势有三点：

  1. 保持对话的沉浸感：用户不会因为复杂的结构化信息而被干扰
  2. 信息分层：高频的对话在表面，低频的结构化信息在暗流，各得其所
  3. 移动端友好：暗流在移动端折叠为底部 Sheet，展开时也不遮挡对话”

追问：暗流抽屉支持多开吗？

“当前版本支持单抽屉。但我们的设计已经规划了多开——用户最多可以同时打开 3 个抽屉（任务计划、产物文件、团队状态），每个抽屉独立调整宽度。移动端降级为底部 Sheet + Tab 切换。同时我们做了性能优化：非活跃抽屉的刷新频率自动降低 5 倍，减少不必要的渲染。”

二、Swarm 群聊模式

Q3: Swarm 模式的三阶段流水线是什么？Agent 如何协作？

难度：⭐⭐⭐⭐（深入）
频率：★★★★（常见）

回答：

“Swarm 模式使用 Phase 1 平行讨论 → Phase 2 并行执行 → Phase 3 HITL 决策 的三阶段流水线。

Phase 1：平行讨论。 每轮所有 Agent 同时发言，而不是轮流发言。我们用 asyncio.gather 让多个 Agent 并行调用 LLM，一轮讨论的延迟等于最慢的 Agent。讨论中有一个 Speaker 选择策略，默认由 LLM 根据讨论上下文选择下一位发言者，也支持轮转和优先级模式。

Phase 2：并行执行。 讨论结束后，每个 Agent 按角色自动执行任务。PM 产出 PRD，Architect 产出架构文档，Coder 产出代码。我们有一个兜底机制 _auto_save_by_role()：如果 LLM 忘记调用 file-ops 工具，系统会自动保存产物。

Phase 3：HITL 决策。 如果讨论中触发了 HITL 检测（如 __HITL__ 显式标记或特征组合检测），系统暂停并等待用户决策。用户选择后，引擎从断点恢复。

整个流程中，HITL 检测是关键。我们实现了三级检测：

级别 机制 置信度 示例
Level 1 __HITL__ 显式标记 最高 __HITL__ 关键词
Level 2 **方案A** 结构化选项 高 检测到多个加粗选项
Level 3 6 特征组合 中等 选项列表、问题标记等加权计算

特征组合覆盖了选项中列表、问题标记、用户导向、末位发言、非重复触发等维度，对比之前的关键词匹配，误触率降低了 70%。”

追问：HITL 检测的特征组合具体怎么工作的？

“我们设计了 6 个特征，每个有不同权重：

特征 权重 说明
选项列表 +2 检测到多个结构化选项（如 方案A / 方案B）
问题标记 +1 包含明确的问题标记（如 ？、需要确认）
用户导向 +1 出现”你”、”用户”等人称代词
末位发言 +1 此消息是该 Agent 本轮最后一条发言
非重复触发 +1 与上一轮的 HITL 触发消息不重复
排除模式 -1 匹配排除关键词（如 无需确认、自动执行）

总分 ≥ 3 时触发 HITL。

举个例子：Agent 说”需要用户确认：方案A：Redis — 高性能。方案B：Memcached — 简单。推荐方案A。”。特征计算：选项列表 +2、用户导向 +1、末位发言 +1，总分 4 ≥ 3 → 触发。这比关键词’需要用户确认’的单一检测准确得多。”

三、Supervisor 主管模式

Q4: Supervisor 模式的 M0-M7 管道是什么？和 LangGraph 的关系？

难度：⭐⭐⭐⭐（深入）
频率：★★★★★（必问）

回答：

“Supervisor 模式的核心是一个 M0-M7 的固定管道，由 Supervisor Agent 驱动：

模块 职责 一句话
M0 意图路由 判断单 Agent 还是多 Agent 项目
M1 需求分析 Supervisor 分析目标，确定所需角色
M2 澄清确认 需求不清晰时 HITL 等待用户确认
M3 Agent 编排 检查可用 Agent，处理缺失角色
M4 任务分解 将目标分解为 DAG
M5 上下文组装 为每个 Agent 组装任务级上下文
M6 DAG 执行 同级 Task 并行执行
M7 独立验证 验证产出是否满足需求

M0-M7 和 LangGraph 的关系：LangGraph 节点类型是原子执行单元，M0-M7 是用这些原子单元构建的固定管道。LangGraph 定义了 Agent、Condition、Validation、HITL 等原子节点，M0-M7 是这些节点的预定义组合实例。用户也可以通过 SOP Designer 用同样的原子节点构建自定义工作流。所以不是两套体系，而是一套原子节点 + 两种组装方式（预定义管道 vs 可视化 DAG）。”

追问：M5 和 Harness 的职责有什么区别？

“M5 负责任务级上下文——当前 Task 的输入、前置 Task 的产出、角色提示词。它只存在于 Supervisor 模式的 M6 执行阶段。

Harness 负责系统级上下文——历史对话记忆、RAG 知识库、Token 预算检查。它横切所有引擎的所有 Agent 执行。

两者的合并方式：

M5 保证 Agent 知道当前 Task 要做什么，Harness 保证 Agent 有足够的背景知识。”

Q5: M6 DAG 执行如何保证并行任务不冲突？

难度：⭐⭐⭐⭐（深入）
频率：★★★★（常见）

回答：

“M6 DAG 执行的核心是拓扑排序 + 层次并行。DAG 中的 Task 按拓扑序分层，同层的 Task 互不依赖，可以并行执行。

冲突预防有三个层次：

层次 时机 机制
第一层 任务分解时（M4） 检测共享文件 → 自动添加依赖关系，确保串行修改
第二层 执行时（M6） Copy-on-Write 隔离：共享基础目录，各 Task 改自己的副本
第三层 执行后（Harness） after_execution 验证输出、提取产物、记录 Token

第二层详解 — Copy-on-Write + 三路合并：

  • 每个 Task 在独立的 Workspace 中执行
  • 共享基础目录，每个 Task 的修改在自己的副本上
  • 合并时通过 git 三路合并处理：
    • 不同文件 → 直接合
    • 同文件不同区域 → 自动合
    • 同区域冲突 → 升级 HITL

如果验证失败，Feedback Loop 会回滚快照并重试。”

四、LangGraph 工作流模式

Q6: LangGraph 模式的拓扑排序执行模型是什么？

难度：⭐⭐⭐⭐（深入）
频率：★★★★（常见）

回答：

“LangGraph 模式使用拓扑排序 + 层次并行的执行模型。

第一步，从 SOP 定义中提取 DAG，只保留 Forward 边（Reject 和 Escalate 边不参与拓扑排序，避免引入环）。

第二步，用 Kahn 算法计算拓扑层级。in_degree 为 0 的节点归入 Level 0，移除后新 in_degree 为 0 的归入 Level 1，依此类推。

第三步，按层级执行。每层内的节点用 asyncio.gather 并行执行。遇到 Condition 节点时做分支剪枝——不满足条件的分支后续节点全部跳过。

第四步，处理 HITL 和 Validation：

  • HITL 节点暂停执行，等待用户 resume
  • Validation 节点失败时可以 retry（注入反馈后重试）或 escalate（升级给用户）

关键设计：Reject 和 Escalate 边不参与拓扑排序。它们是异常处理路径，不是常规执行路径。如果参与排序，它们会创建反向依赖，导致成环。”

五、聊天室核心设计

Q7: 输入框的行为机是什么？为什么输入框永不禁用？

难度：⭐⭐⭐（进阶）
频率：★★★（常见）

回答：

“输入框的行为机是聊天室的核心 UX 创新。同一个输入框根据系统状态切换行为：

状态 输入框行为 发送效果
空闲（idle） 正常输入消息 发送给 Agent
思考/执行中（thinking） 输入变为”软中断” 排队等待，不打断 Agent
HITL 等待（hitl_pending） 输入变为”提交回复” 直接作为 HITL 反馈提交
暂停（paused） 输入变为”恢复” 发送后恢复执行

输入框永不禁用，这是故意设计的。 因为禁用输入框会给用户一种’系统卡死了’的负面体验。即使 Agent 正在思考，用户也可以输入消息——系统会排队处理。同时，软中断的消息中如果包含 HITL 决策词的，会自动升级为 HITL 回复，让用户可以’打断’ Agent 的思考。”

六、工程实现

Q8: Harness 是什么？为什么要统一封装横切逻辑？

难度：⭐⭐⭐（进阶）
频率：★★★（常见）

回答：

“Harness 是横切拦截器，为三引擎提供统一的 Agent 执行前/后处理 Hook。它解决的问题是：文件提取逻辑在三引擎中有 3 处重复实现、持久化是 fire-and-forget 无重试、Token 统计分散各处、审计日志无处安放。

Harness 提供了四个核心方法：

方法 时机 职责
before_execution Agent 执行前 注入上下文（记忆 + RAG），检查 Token 预算
after_execution Agent 执行后 提取文件产物，记录 Token 统计，持久化记忆，审计日志
verify 执行完成后 选择不同于执行者的 Agent 进行独立验证
cleanup 完成后 清理计数器，重置预算

迁移策略是渐进的——先在引擎 run() 签名中添加 harness=None 可选参数，内部用 if harness: 守卫调用。然后逐步将现有的 _auto_save_by_role()、_do_persist()、_extract_node_files() 替换为 Harness 方法。”

追问：验证 Agent 如何选择？防止某 Agent 频繁被选？

“_select_reviewer 方法会选择一个不同于执行者的空闲 Agent，按 reviewed_count 升序排列，优先选择被选次数最少的。可以理解为轮询调度——保证每个 Agent 公平地承担验证工作。”
