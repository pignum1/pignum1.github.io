面试实战 02：腾讯 大模型应用岗 模拟

基于 The Boy（对外口径：算法考核智能分析系统）项目准备的腾讯大模型应用岗复盘。腾讯面更偏成本工程、稳定性、可控可复现、评测方法论、内容安全。所有题目带推荐话术，持续补充。

⚠️ 诚实口径（背诵前先读）：① 模型表述 = “DeepSeek 主力、模型适配层预留 Claude 等切换”，不要把 Claude 讲成线上在跑；② Harness 架构方向是你们定的、落地锚在 LangGraph（已学），叙述别夸大成大规模投产。

项目背景（开场必讲 + 亮点）

“我做的是一个算法考核域的智能分析系统——输入考核相关的数据、规则文档和过程记录，输出带引用的考核问答 ＋ 可复现的指标分析报告。解决三个痛点：知识散落在大量文档、考核指标口径不统一、报告靠人工整理费时易错。

架构是多模态 RAG + 多 Agent 应用：本地部署 BGE-M3 / Reranker / Qwen2-VL，推理用 DeepSeek API（适配层预留切换）。三个设计判断是它的含金量——
① 不做开放式通用 Agent，做’确定性工作流 + 局部 Agent 决策’：链路固化——文档解析→切分→混合召回→Rerank→原文扩展→指标计算→报告生成。模型只负责问题理解/任务拆分/工具选择/非结构化分析/报告生成；指标计算、权限校验、数据查询全走确定性代码——考核数字交给模型算会同一份数据出不一致结果，报告就不可复现、不可审计。
② 检索质量当产品核心做：按数据形态分四套分块策略（文档按标题语义切、含引用链的用父子块、业务表转 Row-to-NL），混合召回 + Cross-Encoder Rerank + 质量门阈值拒答。
③ 全链路可观测可审计：回答强制引用溯源，召回 Chunk/Rerank/Token 全进 trace，线上任何回答都能回放。”

亮点表（主动亮 + 留钩子）：

确定性指标 vs 模型自由发挥 考核数字不进模型计算，数值走代码/SQL “文本里的数字怎么抽？”

Q1：Agent 项目基于什么框架开发的？如何选型？

展开答案

“选型题我不背框架列表，我先说这个项目对 Agent 基座的三条硬要求，再拿要求去筛，最后讲组合——结论是推出来的。

第一步：硬要求 3 条——① 多 Agent + 动态路由（Supervisor 按意图分给不同 Worker）→ 要可编程控制流，不是固定剧本；② 中间必须能打断（HITL 审批、用户改需求抢占中断）→ 要暂停/恢复/状态持久化；③ 推理与执行解耦——模型只出 tool_call，执行权必须在应用层（白名单/Schema/权限拦截），框架不能把我锁死在黑盒。

第二步：排除法筛——Coze/Dify：低代码平台，控制流/状态机/拦截全被封装，深度定制受限 → 排除；LangChain Agent：ReAct 黑盒、流程固定不可干预，违反③ → 排除；CrewAI/AutoGen：角色编排友好，但 AutoGen 默认 Agent 间自然语言对话——我们明确禁止 Agent 直接对话（死循环、Token 爆炸），和我的架构前提冲突 → 排除；剩下 LangGraph：节点+边、条件边、Checkpointer、interrupt_before/after——正好是我那 3 条硬要求的原生原语 → 选它当编排基座。

第三步：分层组合，不是单选——LangGraph = 图编排底座（流程/状态持久化/HITL 恢复）；自研 Harness = 控制层（拦截/鉴权/风控/四状态机/抢占取消，LangGraph 不直接给，写在应用层）；MCP = 工具连接（模型无关）。我自己还用 DeepSeek API 搭过对话式 Harness 实验、接触过 Claude 相关 Agent 方案——对比收获是：消费级智能体单任务好用，生产级底座要可观测、可回滚、可审计。

补充选型六维（如果被问’一般怎么评’）：任务复杂度 / 模型兼容性 / 工具调用能力 / 工作流与状态管理 / 可观测性 / 部署成本。结论：先列需求，用’可编程控制 / 可中断恢复 / 执行解耦’排除，落成 LangGraph + Harness + MCP——选型不是选最好的框架，是选一组刚好满足约束的分层组合。“

Q2：考虑过 Claude Code 驱动的 Agent 架构吗？你了解的 Agent 架构有哪些？

展开答案

“考虑过，而且它印证了我一个设计判断，但要分清两个场景。Claude Code 的本质是编码型 Agent：主循环’读上下文→规划→调工具(读写文件/Bash/搜索)→观察→循环’，配 subagents 并行、hooks 拦截、每步工具执行权限确认——擅长操作型/编码型任务。为什么不当产品底座：我们的业务是读密集型（问答+报告），要可控流程、引用溯源、结果可复现；Claude Code 的强项（自由执行）恰是风险点——权限面大、执行不可预测、难审计，跟’指标数字必须代码算’冲突。所以：开发期用它提效，生产运行时是’确定性工作流+局部 Agent 决策’。它给我的启发：权限确认、subagent 隔离、hook 拦截——本质和我们的 HITL 审批、Worker 工具集隔离、Harness 中间件拦截是同一思路，反过来验证了控制层设计方向。

Agent 架构全景（按’控制在哪’分）：

架构族 代表 特点 我们用没
单 Agent 循环 ReAct / FC loop 自主想→调→看→再想 底层思想 ✓
图编排/状态机 LangGraph 可编程控制流、可打断恢复 ✓ 底座
确定性工作流 自研 Pipeline 流程固化可测，模型局部决策 ✓ 主流程
多 Agent 协作 Supervisor-Worker/Debate/Swarm 中心调度/竞合/handoff ✓ Supervisor
记忆增强 MemGPT/Letta 上下文分层、虚拟内存 ✓ 借鉴三层记忆
自省式检索 Self-RAG / CRAG 模型反思该不该检索、好不好 思路借鉴
编码/操作型 Claude Code / CUA 改代码、操作环境 ✗ 不适合读密集
协议+控制层 MCP + Harness 模型无关连接、执行权在己 ✓

没有哪个架构通吃，我选混合：自由探索给 ReAct，复杂产品用图编排，稳定链路走确定性工作流，模型自由度按环节收放——The Boy = 图编排 + 确定性工作流 + Supervisor-Worker + Harness 控制层的混合。”

Q3：Plan-and-Execute 和 ReAct 的区别？

展开答案

“本质是边想边做 vs 先想清楚再做。

ReAct 是 Thought→Action→Observation 紧耦合循环，每步根据上一步观察决定下一步——灵活、能随时转向，但没有全局视野，复杂长任务容易走偏、每步都烧推理 token、还可能卡循环。

Plan-and-Execute 拆两段：Planner 一次性产出完整步骤清单（先不执行），Executor 按清单逐步执行，失败或信息不足就触发 Replan——结构清晰、token 省（长任务明显）、计划可先给人审批（HITL 友好）、可复现；代价是初始计划可能脱离执行中发现的现实，所以 Replan 要设计好且设上限防死循环（呼应 Q13）。

选型：开放探索型（要先查信息才能定下一步）→ ReAct；步骤可预期、长、要可控可审 → Plan-and-Execute；生产常用混合——外骨架计划/工作流、内部局部 ReAct。The Boy = 确定性主流程（计划/工作流层）＋ 局部 Agent 决策（ReAct 层），和’确定性工作流+局部决策’主线一致。

LangGraph 落地：planner 节点 → executor 循环节点 → 条件边（done→收尾 / error 或信息不足→replan，限次数）。

常被追问’Plan 会不会脱离现实’：答’会，所以 executor 失败或前置信息变化时强制 Replan 且设上限——这也是我生产倾向把主流程固化成确定性工作流、而不是每次全靠 LLM 出计划的原因’。”

Q4：你说 Plan-Execute 更优？怎么评测比较两个架构？

展开答案

“我不直接下结论，而是设计对照实验。四点——
①控制变量：同模型/同工具/同 context 预算，只变策略，每任务跑 N 次取统计（ReAct 方差大，单次定不了胜负）。
②分层任务集：两类策略优势区间不同，混在一起比没意义。按会拉开差距的维度分层：开放探索型 / 固定流程型 / 长任务(>5步) / 中途变化型，每类 30-50 条带 ground truth。
③多维指标（四轴）：质量（完成率/正确率）、效率（步数/无效重试/卡循环率）、成本（token）、鲁棒性（N 次成功率方差/可复现率）；另加可控性（计划可审计比例、HITL 命中）。
④分开判定：终态用结构化字段校验（结果有 schema），中间过程质量单独评——避免’最后答对但过程乱’和’过程对但答案格式错’混在一起；LLM-as-Judge 只做辅助。

跑完大概率得到的是分类型结论：固定流程/长任务 Plan-Execute 完成率高+成本低+方差小；开放探索 ReAct 更灵活。所以生产结论是按任务类型路由，而不是全量替换——这也是’确定性工作流+局部决策’的评测依据。收口：评测的价值不是证明我选得对，是把’哪个架构在哪类任务赢’变成可复现的数据，指导路由。“

Q5：怎么界定单轮 vs 多轮？多轮对话怎么做 Benchmark？

展开答案

“界定不看 Agent 内部调几次模型/工具——一次请求触发十次工具调用，仍是单轮对话+多步执行。只看：完成任务是否依赖多次用户交互，以及后续请求是否依赖前面产生的状态。

满足任一即多轮：信息不足要追问 / 指令依赖前文（’把刚才第二项展开’）/ 后续操作依赖前一轮结果（’查数据→用数据出图’）/ 用户纠正（’不是一组是二组’）/ 对结果持续迭代 / 跨会话记忆 / 高风险步骤等人审批。

工程判定标准：把历史删掉，当前请求还能不能完整正确执行？能→单轮；出现目标/参数/指代/状态/约束缺失→多轮。多轮的本质不是消息数量多，而是存在跨轮次的状态依赖。

多轮 bench：每条 Case 是完整对话轨迹（JSON），标每轮输入、预期意图、应继承/覆盖/遗忘的信息、预期工具调用、预期终态。按六类能力建场景——信息补全（该追问追问、别猜、别重复问）、指代消解、状态继承（只改周期、部门自动继承）、状态覆盖纠正（旧值不能串回来）、长距离记忆（第1轮定的约束第10轮还遵守）、权限冲突（后指令不能越权）。

指标分三层（同一个最终答案可能来自错误过程——查错部门恰好算出相同数字，只评结果会误判）：对话层（理解/追问/继承）、轨迹层（工具/参数/顺序）、结果层（答案/数据/引用）。核心指标：任务成功率、Turn/Slot/State/Tool Accuracy、该追问时是否追问、Context Retention、Forgetting（纠正后停用旧值）、安全违规率、Token/延迟。可加权综合分，但高风险场景安全违规是硬门槛——越权/错误发布直接记 0。

运行方式：固定脚本（稳定回归）+ User Simulator（另一模型按规则扮演用户，不主动替 Agent 完成任务）探索 + 人工抽检。判定上任务结果和工具参数用代码判定（state_before/after 快照比对），表达质量才用 LLM-as-Judge——防’模型给模型放水’。

收口金句：单轮 Benchmark 评估’一个输入→一个结果’；多轮 Benchmark 评估’状态如何被携带、更新、纠正，最终完成任务’。“

Q6：评测集的一条记录怎么设计？包含哪些内容？

展开答案

“评测集要可自动化、可分环节归因、可版本化。落地用 JSONL，一行一条 Case + schema_version。一条记录分四块：

① 元信息：case_id、类型标签（单轮/多轮/拒答、领域、难度、是否含图表）、来源（真实日志回放/人工合成/线上 bad case）、gold 版本、加入时间。

② 输入：query 原文；多轮带 turns/initial_state；RAG 带关联知识库定位；可选关联文件。

③ Ground truth（关键：分环节标，别只标答案）——

  • 期望答案（多个可接受答法或关键点列表）
  • 期望检索：ground truth chunk_id 列表（算 Recall 用）
  • 期望引用出处（标 Citation）
  • 期望动作/工具与参数（Agent 类）
  • 期望状态变化（多轮，含应覆盖/应继承/应遗忘）
  • 拒答标记（这题该不该答）

④ 判定配置：判据类型（结构化字段校验/规则/LLM-judge rubric）、评分维度、可接受差异、禁止行为、通过阈值。

运行后追加结果字段（不覆盖）：实际输出、实际检索 chunk、工具 trace_id、分项得分、通过/失败原因——天然形成 bad case 沉淀与回归集。

为什么分环节标 GT：只标答案没法归因——Recall 低是检索层问题、引用错是生成层问题（呼应 Q29’召回≠进 Prompt≠引用’，和 Q7 RAGAS 分层评测）。示例记录：

收口：一条评测记录 = 元信息 + 输入 + 分环节 GT（答案/检索/引用/动作/状态）+ 判定配置 + 运行结果；GT 分环节标才能归因，JSONL+版本才能自动化和沉淀。“

Q7：评测周期长，怎么快速迭代 Agent？

展开答案

“评测周期长，核心不是把评测变快，而是把’验证’从’评测’里拆成快慢两级。每次改动走快环：单 case 用 trace 回放定位根因 → 失败聚类按模式批量修（先打最大簇）→ 改完跑 diff 子集 + fast smoke（判定用代码比对，分钟级）；全量离线评测只在攒够一批、准备上线时跑一次（慢环，决定上线）。让快环成立的三个前提要提前铺：①判定能代码化就不靠 LLM-judge（Q6 预置期望字段/状态）；②case 带标签能做 diff 子集回归；③记录带 trace_id 能回放定位（Q29）。

记忆骨架四桶：少量测试 / 链路追踪 / 场景分类 / 异常回放修复。完整生命周期 trace 必须跨四阶段记全：检索（query 前后/召回 chunk+score）→ 重排（前后序与分数）→ 组装（进 Prompt 的上下文/截断）→ 生成（prompt/输出/token），Agent 再加工具参数与 state 前后（呼应 Q29/Q5）。

追问’像不像 LoRA’：思路像（局部低成本适配——LoRA 冻主体只训低秩增量，我们冻全量只回归受影响子集），机制不像（LoRA 是训练侧参数级，我们是评测侧数据子集回归，更接近软件测试的增量回归/diff testing）——类比点到思路层即可，别往训练细节套。

收口：快环防回归、慢环定上线；bad case 是迭代燃料不是废料——评测慢，迭代节奏不能跟着慢。“

Q8：RAG 怎么优化？分析效果、形成数据闭环让数据飞轮持续优化？

展开答案

“优化不是一次调参，是让’每一次反馈都变成资产、反哺下一次迭代’。分两半——怎么分析 ＋ 怎么闭环。

分析（分层归因）：RAG 拆检索层/生成层，RAGAS 四指标各管一头——Context Precision（信号 vs 噪声）、Context Recall（漏没漏）管检索层；Faithfulness（编没编）、Answer Relevancy（切不切题）管生成层。指标掉了先定位层：Precision 低→加 Reranker/降 k/提阈值（缩）；Recall 低→混合检索/增大 k/多路（扩）；Faithfulness 低→强 Prompt/自检；Relevancy 低→Query 改写。但指标只说哪层坏、说不出哪个 chunk 错——归因靠 trace：坏例回放’召回≠进 Prompt≠引用’三层，钉到具体环节（Q29）。

闭环/飞轮五步：①观测——离线 RAGAS ＋ 在线 Judge 抽样 ＋ 用户显式（赞/踩/追问）＋ 隐式（放弃/重问/拒答率），点踩率是起点信号；②归因——trace 回放 ＋ 失败聚类（检索漏/重排错/幻觉/拒答错/格式），先打最大簇；③沉淀——坏例自动带完整 trace 进黄金回归集（Q6，分环节 GT），bad case 是资产；④改进——按根因批量修（检索策略/分块/prompt/路由/阈值），每次走快环 diff 子集（Q7）；⑤回归上线——全量离线通过才上线，上线继续观测。

数据四路收集（追问点）：①确定性规则信号——质量门拒答后仍追问、低分却答了、超时重试，零成本无偏；②用户显式＋隐式反馈（埋点行为规则）；③Judge 只做抽样初筛（5-10%＋触发式），不当真相，判完进’待确认池’；④人工终审确认才入黄金集。每条带置信度标签（规则待审→judge 疑似→人工确认）。Judge 偏误若直接当 ground truth，会把飞轮带歪。

收口：RAGAS 分层诊断定位到层 → trace 归因钉到环节 → 坏例系统化沉淀进黄金集 → 按根因批量修 → 全量回归后上线；飞轮的燃料是 bad case 的系统化采集，有效性看黄金集在变厚、修复不复发、核心指标随版本不退化。“

Q9：怎么评价你的 rewriter 是好的还是坏的？

展开答案

“评 rewriter 不看’改得像不像人话’——它唯一的目的是让下游检索更好，好不好 = 相对’不改写’的净增益。

① 端到端（主判据，慢环最终裁定）：同一 golden set，原 query 直接检索 vs 改写后检索对照，比 Recall@k / 最终答案正确率 / RAGAS CP/CR——永远和’不改写’做 baseline，看相对增益不是绝对分（否则’改得漂亮但检索没变好’会被误判成好）。
② 代理指标（快环诊断）：Recall 增益（有没有用）、保真度 fidelity（有没有偏题）、指代消解率、改写稳定性（不可复现＝坏）、成本。两类性质不同——Recall 增益答’有没有用’；保真度/稳定/成本答’值不值、有没有带偏’，判据 = 净增益 = 增益 − 约束代价。
③ GT 用’应命中的 chunk’而不是’期望改写文本’——合法改写不唯一，判命中比判文本相似稳。
④ 失败分类：过度改写（加戏偏题）/ 改写不足（指代没解）/ 不稳定。
⑤ 按需改写——query 本来就清晰就不改，省一次 LLM 调用、也防引入错误。

收口：先证明有净增益，再用约束指标防带偏，最后让清晰的 query 别被白改。“

Q10：调整了 top_k 之后，怎么打分、怎么构建评测指标？

展开答案

“top_k 不是优化目标，是 Recall ↔ Precision 的旋钮。打分要分三层，别单点看：

层 指标 关心什么
① 召回层（只看检索器） Recall@k / Precision@k 该进的进了没；信号 vs 噪声
② 链路层（有 Reranker 时） 候选池 Recall ＋ rerank 后 top-N 精度 top_k 是喂 reranker 的候选池大小——怕’对的被漏在池外’，池内排序交给 reranker
③ 生成层/端到端 答案正确率、Faithfulness、延迟、token k 太大→噪声多→faithfulness 掉；k 太小→漏→编造

打分方法 = 扫曲线不是测一次：固定其他变量，k 扫 {3,5,10,20,50}，同一 golden set 每个 k 跑一遍，画 Recall@k/Precision@k/nDCG@k 曲线 ＋ 各 k 的 e2e 矩阵表，选 k = 拐点（Recall 增长变缓处）且落在延迟预算内。

两个关键：①k 与阈值/Reranker 联调——k 调大噪声同步增，必须配套提质量门阈值或靠 reranker 挡，否则只是把脏上下文喂给模型；②golden set 固定且带分环节 GT（Q6），trace 能看出漏在召回层/被 rerank 挤掉/被阈值挡了（Q29）。

收口：top_k 打分看三层曲线的拐点，不是单点调参。“

Q11：指标一个升一个降怎么办？rerank 调整后怎么评整体效果？

展开答案

“分成两半：指标互损怎么决策 ＋ rerank 调整怎么评整体效果。

一、互损四步决策
① 先分是真权衡还是 bug——Recall↔Precision 此消彼长是结构性权衡（正常）；八竿子打不着的指标也降＝引入的新问题，先当 bug 查；
② 定红线——任务正确率/Faithfulness/安全违规不许降（硬指标，越界直接否决）；CP/CR/Recall/Precision 是过程指标，可互损；
③ 先找帕累托改进——rerank 调紧让 Precision 升、Recall 降，就扩大候选池 k 把 Recall 补回来（先扩召回再精排），两头不亏就不用取舍；
④ 真无法两全才业务加权综合分显式取舍，且看显著性（多次、方差、别被 judge 噪声骗）。

二、rerank 评价（关注点按重要性排）
① 候选池守恒（池里没有的 rerank 救不了，先确认 k 没缩）；② 核心 chunk 有没有被剔除（淘汰对不对——召回损失来源）；③ 排序变化（nDCG@N / Precision@N 是否变好）；④ 端到端（答案正确率/Faithfulness）＋ 延迟（rerank 开销）。
判据三条同时成立才算调整成功：端到端变好 ＋ 延迟达标 ＋ 候选池 Recall 不降。

收口：过程指标看阈值、核心指标看趋势、红线指标一票否决；rerank 先看有没有挤掉对的，再看排得好不好。“

Q12：query 对应的标准答案个数不一样，怎么平衡它对结果的影响？

展开答案

“答案个数不一致会系统性污染分数——单解题假阴性（合法变体被判错）、多解题假阳性（候选多、命中率高）。原则：别让’答案条数’成为打分变量，把’答案集合’转成’判定条件’或’集合指标’。

按题型定 GT 形态：

题型 GT 形态 指标 为什么不怕个数多
唯一解（数值/字段） 精确值 字段精确比对 无多解问题
检索类 gold chunk 集合 Recall@k / nDCG 集合指标是比例，自动归一
多解生成 checklist 关键点 覆盖率（命中数/总数） 0-1 比例，不是命中条数
开放语义 多个 gold 任一 判’等价于任一 gold’（取 max 不累加） 不因条数虚高
开放主观 rubric LLM-judge 按维度打分

checklist 是什么：把’标准答案文本’换成’必答要点集合‘——定 required（必答点）/ bonus（加分点）/ forbidden（禁止项），得分 = 命中必答点数 ÷ 必答点总数（0-1 覆盖率）；每个点二值判定（数值/术语用代码规则，语义用 judge）。天然归一，答案几条、怎么措辞都不影响。

聚合防偏：per-query 先归一成 0-1，再对 query 宏平均（每题权重相同）——绝不按答案条数加权。分层报告：case 标判定类型（唯一解/多解/开放）＋ 难度，分层报告，别混一个总分。

收口：让指标回答’答对了没’，而不是’命中了几条参考答案’——精确值→字段、检索→集合比例、多解→要点覆盖率，全部归一成 0-1。“

Q13：最终取的 top 3 还是 top 5，怎么判断？

展开答案

“先分清两个 k：召回 k（候选池，20-50，Recall 驱动，宁多勿漏）与最终 top_n（rerank 后进 Prompt 的条数，3-5，Precision＋预算驱动）。这题问的是后者，四个判据：
① 离线 sweep 找拐点——同一 golden set 扫 {1,2,3,5,8,10}，看答案正确率/Faithfulness/nDCG@N，通常 3-5 是平台区；② 两个反向力——n 小会漏（正确率降、幻觉升）、n 大会带噪让 Faithfulness 先升后降，最优在交叉点；③ 任务类型定 n——单点事实问答 top1-3、多跳/对比/汇总 top5-8、报告生成按章节分别检索各取 n；④ 上下文预算（token/延迟/成本内取收益最大）。

关键补充：top_n 是上限，不是配额——低于分数阈值的不进（宁少勿凑）；去重 / MMR 保多样性（别让 5 个名额全被同一段占满）；按父块聚合（命中同父块的子块合并计，父子块场景）。

怎么验证 3 还是 5 更好：A/B 对照 ＋ 看 trace 引用率——进 Prompt 的 5 个里只有 2 个被回答引用，说明 n 虚高可缩；引用率高说明 n 不够。

收口：top_n 看 sweep 曲线拐点、看反向力交叉，是上限非配额，用引用率验证。“

Q14：具体评测 RAG 召回，应该用什么指标？

展开答案

“看有没有标注分两类。有标注用经典 IR：召回阶段头号指标 Recall@k（该召回的里实际进 top-k 的比例，漏没漏——漏了 Reranker 救不回）、辅看 Hit Rate@k；精排阶段看 nDCG@k / Precision@k / MRR（排序质量）；综合用 MAP。无标注用 RAGAS：Context Precision（信号 vs 噪声）、Context Recall（漏没漏）——LLM 判，适合线上持续监控。

四个要点：① 召回以 Recall 优先——漏掉的救不回，Precision 交给 rerank 阶段管；② 报告必须写清 @k 是召回 k 还是最终 top_n，否则数字没意义；③ GT = gold chunk 集合（可能多个），集合指标天然归一、不怕答案个数（Q12）；④ 分层报告（按 KB 类型/难度/题型分开，别混总分）。

GT（gold chunk）从哪来：人工标注 / 从参考答案反推引用章节 / LLM 合成——存进 Q6 记录的 ground_truth.chunk_ids 字段。

收口：召回看 Recall@k 漏没漏，精排看 nDCG 排得好不好，无标注用 RAGAS 的 CP/CR。“

Q15：RAG 过程中出现的幻觉怎么解决？

展开答案

“别默认幻觉是生成问题——按 RAG 链路分层归因，哪层出的治哪层。

层 幻觉怎么来 解法
① 检索层 没检索到对证据（漏）→ 编；噪声 → 被带偏；过时/错误文档 → 忠实编错 混合检索＋Reranker；质量门阈值拒答；切块优化；增量更新；来源可信度分级
② 组装层 chunk 截断/表头丢、父子块被拆 → 信息不完整 → 脑补；矛盾 chunk → 混淆 父子块保上下文；去重/一致性；按相关性排序；标来源
③ 生成层 Prompt 没约束 → 自由发挥；上下文与模型记忆冲突 → 偏向记忆 强约束 Prompt（只依据文档、没有就说不知道）＋引用溯源（标 chunk id）
④ 校验层 生成完没人核 Self-RAG 自检（关键事实回文档找依据，找不到重生成）；Grounding 校验（第二 LLM/NLI 判有无依据）；一致性采样

关键分清两种幻觉：忠实性幻觉（上下文里没有、模型自己编）→ 治生成；上下文错误幻觉（上下文本身错/过时/被注入、模型’忠实’照错说）→ 必须治检索质量＋来源可信度，光治生成没用（这就是’检索错上下文也会幻觉’）。

兜底三板斧：① 拒答优先——质量门没过就说’检索内容不足’，最好的解幻觉是不让它答；② 引用溯源（Q29）；③ RAGAS Faithfulness 监控闭环（Q8）。

收口：先定位幻觉出在’没给对证据 / 给了错证据 / 给了对证据还编’哪一种，再对症下药。“

Q16：怎么减少 transform 生成过程中产生的幻觉？

展开答案

“transform 是中间生成步骤，它自己会编，形态有四：加戏/过度改写（原文没提的部门自己补）、指代解错（’它’解成错对象）、数值/专名走样（V8 权重被改错）、丢约束（时间/部门限定丢了）。

治它七招（按性价比排）：
① 约束 Prompt——最小必要修改，只补指代/去口语，禁止新增概念、禁改数值/专名/约束、禁整段重述（negative prompting）；
② diff 式改写——只输出’改了什么’而不是整句重写，输出空间越小幻觉面越小；
③ 保真校验＋回退——数字/专名/约束规则校验（最硬）＋ 语义等价小模型判，不过就回退到原 query（宁可没改，不可改歪）；
④ 能规则别 LLM——术语归一/缩写展开/纠错走词典表，直接消灭这类幻觉面；
⑤ 低温＋短输出（temp=0、限长、结构化 JSON）；
⑥ 多路一致性（多次/双模型不一致 → 可疑回退）；
⑦ 检索侧冗余兜底——改写 query 和原 query 并行召回做 RRF 融合，即使改写引入噪声，原文仍保底召回正确结果（RAG-Fusion 思路）——用检索侧的冗余兜住生成侧的幻觉。

收口：transform 幻觉不靠’让它改得更好’，靠’约束最小改动 ＋ 校验回退 ＋ 原文并行兜底’。“

附：方法论题的记忆骨架（学习方法）

方法论题（选型/评测/迭代/闭环）别死记全篇——背”骨架 + 概念锚点”，细节面试临场发散。

  • 跨题通用骨架：少量测试 / 链路追踪 / 场景分类 / 异常回放修复（Q4 比较架构、Q5 多轮 bench、Q7 快速迭代、Q8 数据飞轮都用同一张骨架，换开头一句即可）。
  • 必须精确的概念锚点（背错就露馅）：ReAct＝Thought→Action→Observation；LoRA＝W=W₀+BA（冻主体只训 B·A）；MemGPT＝Core/Recall/Archival 三层；Plan-Execute＝Planner→Executor→Replan（限次）；判定单多轮＝删掉历史能否独立执行；Claude Code＝编码型（工具+权限确认+subagent），不适合读密集型产品底座。
