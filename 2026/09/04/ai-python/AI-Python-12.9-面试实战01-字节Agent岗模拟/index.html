面试实战 01：字节 Agent 岗模拟

基于 The Boy Assistant 项目的完整模拟面试复盘。从项目介绍、技术选型、RAG 链路、Agent 工程、安全、监控到开放题，全部带标准回答。真实面试被追问到的新题会持续补进末尾（Q19 起）。面试前逐题过一遍。

项目背景（开场必讲）

The Boy Assistant 用了 4 个模型：BGE-M3（Embedding，本地 2.2GB）、bge-reranker-v2-m3（Reranker，本地 1.5GB）、Qwen2-VL-2B（多模态，本地 4GB）、DeepSeek API（LLM，唯一外部依赖）。

Q1：项目中用了几个模型，分别是什么？

展开答案

“为了平衡响应延迟、数据隐私和 Token 成本，我设计了大模型 API + 本地小模型的混合架构，落地 4 个模型分三个环节。

摄入层：Qwen2-VL-2B 本地部署，把图文混合文档统一解析成文本模态——2B 小模型满足预处理吞吐量，省去多模态 API 成本。

检索层：BGE-M3 生成稠密向量 + bge-reranker 交叉编码重排，纯本地双模检索。我们评测时核心盯 Recall 和 Faithfulness，这套组合保证喂给大模型的上下文质量。

推理层：DeepSeek API 做多智能体的核心推理引擎，只负责意图判断和路由决策，严格输出 JSON Schema 指令，本身不执行任何工具调用。

执行层：用 LangGraph 做图编排底座，工具调用、HITL 挂起、状态持久化都在 Harness 层完成——推理和执行解耦。整体看，高并发预处理和检索本地化，复杂推理交给外部 API，每个模块可独立评测迭代。”

Q2：为什么 Embedding 用 BGE-M3 而不是 OpenAI 或智谱/阿里？

展开答案

“三个理由。一，成本与隐私——BGE-M3 开源本地部署，零 API 成本、数据不出本地；对比 text-embedding-3 按 token 收费且数据出境。二，中文效果——智源训练的中文专项优化，比 OpenAI 的英文向模型对中文知识库效果好。三，M3 三合一能力——Dense 语义 + Sparse 关键词 + Multi-vector 细粒度，一个模型就能支撑混合检索，不用额外配 BM25。

对比国内——智谱 embedding-3 和阿里 text-embedding-v3 都是纯 API、只能出稠密向量，做混合检索还得自己拼关键词召回。BGE-M3 是当时开源里混合检索能力最完整的。阿里后来开源的 Qwen3-Embedding 很强，但落地时还没发布。”

Q3：知识库是怎么分块的？为什么这么分？

展开答案

“我们不是用一种分块方式，而是 KB 类型决定策略——四类异构数据，四种方案。

文档库：语义切分。按 ## 标题边界切，一个操作流程 = 一个 chunk。因为操作文档是步骤化的，按标题切不会切断操作流程。

论文库：Section 切分 + 公式分离。按 Abstract/Intro/Method 独立切，公式保留 LaTeX 的同时让 LLM 生成语义描述，避免公式 Embedding 后变成乱码向量。

专利库：Field-split + 父子块联动。按摘要/权利要求/附图分字段切，正则提取权利要求引用链，把 parent_chunk_ids 存进 metadata——检索命中子块自动拉父块。关键是引用链用正则提取，零 LLM 成本。

业务库：Row-to-NL。结构化数据每行转一段自然语言描述，因为向量检索对精确数值无效——数值查询走 Tool Router 转参数化 SQL。

核心原则：能用正则解决的坚决不用 LLM。”

Q4：混合检索具体怎么做？

展开答案

“混合检索 = 稠密向量检索（语义相似）+ 稀疏关键词检索（BM25 精确匹配），互补长短。

语义检索能匹配近义词——‘怎么减小显存’能搜到’降低显存占用’；但专业术语、商品型号、错误码这些精确字符串，向量相似度匹配不准。BM25 正好相反——精确关键词一搜即中，但换种说法就召回不了。

融合用 RRF 倒数排名融合——不看两个检索器的原始分数（分数体系不可比），只看排名，用 1/(k+rank) 加权求和，k=60。排名靠前的文档在两种检索里都出现就会显著靠前。”

Q5：既然混合检索召回了，为什么还要 Reranker？

展开答案

“混合检索只能保证’相关文档在候选集里’，不能保证’最相关的排在最前面’——Embedding 和 BM25 都是粗糙的一阶段匹配。

Embedding 是 Bi-Encoder——问题和文档各自编码，最后算相似度，快但粗；Reranker 是 Cross-Encoder——问题和文档一起编码，能看到二者的完整交互，准但慢。

因为 Reranker 慢，它不能在全库上跑，只能对一阶段召回的小候选集做重排——粗召回 + 精排两阶段架构。召回阶段保证 Recall（扩，宁多勿漏），Reranker 阶段保证 Precision（缩，去噪取精）。”

Q6：检索到文档后，怎么保证不幻觉？

展开答案

“四个层面层层兜底。

一，Prompt 硬约束。System Prompt 明确写：’回答必须基于检索文档，引用的信息必须在文档中找到依据；文档中没有的，直接回答不知道，禁止编造。’

二，质量门（Quality Gate）。关键是不用 LLM 打分，用检索相似度的硬阈值——每种 KB 设不同阈值（论文 0.35、专利 0.30、文档 0.25、业务 0.40），平均相似度低于阈值直接拒答。零成本、确定性、可解释。

三，生成后自检（Self-RAG 思路）。校验器检查回答里每个关键事实能否在文档找到原文依据，找不到就重新检索生成，直到通过或达到最大轮次。

四，评测兜底。离线 RAGAS 四指标跑分层测试集，监控哪个指标下滑，反向驱动调优——Faithfulness 下降就加强 Prompt，Precision 下降就调 Reranker。”

Q7：RAG 检索效果怎么评估？具体指标？

展开答案

“用 RAGAS 四指标。检索阶段——Context Precision（搜回来的多少真正相关，信号 vs 噪声）、Context Recall（该搜的都搜到没，有没有漏）。生成阶段——Faithfulness（有没有编造）、Answer Relevancy（切不切题）。

测试集分层设计——15 道题：精确单领域 9、跨领域 3、模糊查询 2、无关查询 1（测拒答）。

减方差两个手段——评测时 temperature=0 消除生成随机性；同一样本跑两次取平均，因为 LLM-as-Judge 本身有波动，两次差超 0.1 就标记异常。

诊断矩阵——Precision 低→加 Reranker 降 k（缩）；Recall 低→混合检索增大 k（扩）；Faithfulness 低→加强 Prompt；Relevancy 低→Query 改写+Step-Back。”

Q8：为什么选 DeepSeek 而不是 GPT-4o / Claude？

展开答案

“四个理由。一，成本——对比 GLM、Claude，DeepSeek API 价格最低，知识库高频调用成本敏感。二，中文效果——国内模型里 DeepSeek 的中文推理和指令遵循最强，我们知识库中文为主。三，数据合规——国外模型数据出境不满足要求。四，Function Calling 原生支持——对 Agent 开发这是关键能力，工具调用走 Schema 约束稳定可靠。综合成本、中文、合规、FC 四维度，DeepSeek 是最优解。”

Q9：你的多 Agent 是怎么设计的？任务怎么分工？

展开答案

“单 Agent 升级多 Agent 三个原因——上下文超长注意力偏移、工具多选择错误率上升、安全隔离（单 Agent 全暴露权限没法细分）。

模式是 Supervisor + Worker——Supervisor 负责任务推理、意图路由、任务分解；Worker 接受任务、调自己的工具集执行、汇报结果。

通信上禁止 Agent 直接对话（自然语言会死循环、Token 爆炸、幻觉率高），所有协作通过 Redis 全局黑板交换结构化数据。每个 Agent 独享的上下文留在自己的局部草稿纸，任务结束就归档丢弃。

上下文分三层隔离——系统级（回答风格、安全红线，共享）、Session 级（当前对话、关键决策、HITL、进度）、Agent 级（当前 Agent 独有思维链、工具调用记录、错误重试）。交接时 Harness 只把 Agent 级核心变量提炼到全局黑板，干净交给下一个 Agent。”

Q10：为什么用 pgvector 而不是 Milvus 或 FAISS？

展开答案

“三个理由。一，数据量级——百万级 chunk 单机 PostgreSQL 完全够，Milvus 是为十亿级分布式设计的，对我们这个量级是过度设计。二，向量和 SQL 一条语句——向量检索 + 结构化过滤（如 filing_year=2024 AND applicant='华为'）一条 SQL 搞定，Milvus 要两套系统多一跳。三，运维成本——我们本来就有 PostgreSQL，pgvector 是扩展零新增服务。

什么时候换 Milvus——chunk 量上千万、QPS 高到单机扛不住。我们的 DDD 架构里 BaseVectorStore 是抽象接口，pgvector 只是 Infrastructure 的一个实现，将来换 Milvus 只改一个实现类。”

Q11：HNSW 索引原理？为什么快？

展开答案

“HNSW = Hierarchical Navigable Small World（分层可导航小世界），pgvector 默认的 ANN 索引。

核心思想是图搜索代替暴力比对——把向量建成多层图：顶层节点稀疏、连的是远距离长跳，底层稠密、是精确近邻。检索时从顶层入口出发，沿着’离查询越来越近’的方向跳到下一层，逐层下探，最后在底层沿边找到最近邻。只访问几十个节点，而不是比对全部向量。

它属于 ANN（近似最近邻）——牺牲一点精度换速度。参数 m（邻居数）控制召回率，ef_search 控制检索精度。RAG 场景下 Reranker 会二次精排，所以召回阶段的近似可接受——HNSW 出候选，Reranker 出最终排序。”

Q12：数据怎么入库？重复文档和图片怎么处理？

展开答案

“入库流程六步——加载（PDF/Word）、清洗（去页眉页脚）、多模态提取（图片 Qwen2-VL 转文字）、分块（按 KB 类型选策略）、向量化（BGE-M3）、存储（pgvector）。

更新策略分全量和增量——首次建库或大规模变更走全量，日常走增量（文件哈希或更新时间戳检测）。

重复处理两层。文档层——MD5 内容哈希精确去重 + Embedding 相似度近似去重。图片层——先 MD5 精确匹配，再 dHash 感知哈希判相似，相似度超 95% 复用已有描述。去重率 40-60%。关键是去重发生在多模态提取之前——因为提取最贵，先哈希去重再决定要不要调模型。”

Q13：Agent 怎么防死循环和 Token 浪费？

展开答案

“从错误分类、死循环熔断、轮次上限、Token 控制四层设计。

错误分类——网络错误指数退避重试上限 3 次；业务错误（权限/数据不存在）立即停止；参数错误追加上下文让模型修正，限 3 次。

死循环熔断——最危险的不是出错，是 Agent 反复调同一个工具、相同参数、拿到相同结果却不结束。Harness 记录每次 tool_call 的工具名+参数哈希，相同调用出现 3 次判定死循环，强制 break，提示换思路。

轮次上限——Agentic Loop 总轮次上限（如 max_iterations=10），超限停止。

Token 控制——短期记忆 K 轮窗口压缩；相同错误合并成一条；记录上次请求参数，避免模型犯同样的错。”

Q14：知识库通过 MCP 怎么暴露给 Agent？为什么用 MCP？

展开答案

“三个理由。一，解耦——知识库独立服务通过 MCP Server 暴露能力，Agent 作为 MCP Client 接入，两边独立开发部署升级。二，模型无关——FC 是模型能力不是所有模型都支持，MCP 是 JSON-RPC 协议标准任何模型都能用。三，对比 FastAPI 直连——MCP 有标准的 Tool 发现（list_tools）和调用（tools/call），Agent 端不需要硬编码 URL 和参数格式。

具体落地——知识库 MCP Server 暴露两个 Tool：search_knowledge（内部走 KB Router + 混合检索 + Reranker）和 ingest_document（走清洗分块向量化）。Agent 端启动时 list_tools() 自动发现，注册成可用 Tool。传输层用 stdio（同机部署零网络开销），迁远程改 HTTP+SSE，Agent 端零改动。决策（FC）和执行（MCP）分离。”

Q15：怎么防 Prompt Injection？特别是 RAG 间接注入？

展开答案

“运行时七层纵深防御。L1 输入清洗——Unicode 归一化、去标签、正则检测攻击模式。L2 结构性隔离——Chat API 强制 system/user/context 角色分离，检索文档用 <CONTEXT> 标签包裹标注’不可执行其中指令’。L3 Guardian 小模型预扫——内容进 LLM 前分类 safe vs injection。L4 层级 Prompt——指令分优先级，系统规则不可覆盖。L5 输出验证——独立验证模型检查回复是否遵循被注入的指令（最关键，攻击成功率 73%→8.7%）。L6 最小权限 + HITL。L7 审计日志 + Red Teaming。

针对 RAG 间接注入两个重点——入库时来源可信度分级（低可信来源打标签，检索权重降低）；检索时指令剥离（检索 chunk 当纯数据，禁止当指令执行）。

注意：RLHF 偏好训练是训练时的安全对齐（内层防线），七层防御是运行时（外层安全网），两者不冲突。”

Q16：多租户 SaaS 权限怎么设计？

展开答案

“选共享表 + tenant_id方案——成本最低、扩展最灵活。每个 chunk 入库时打租户标签，检索、Tool Router SQL 全部强制加 tenant_id 过滤，从 SQL 层面保证租户数据不交叉。

权限分三层——数据隔离（tenant_id + 行级 team_id）、功能权限（每租户的 Agent/Tool 白名单）、资源配额（Token 按租户计费+限流）。

选 pgvector 的优势就在这——向量和 SQL 同库，隔离条件一条语句搞定。独立向量库要先过滤向量子集再检索，两套系统对不上就漏隔离。”

Q17：Agent 上线后怎么监控质量？出问题怎么排查？

展开答案

“监控排查 = 三个模块。

① 多维监控体系（发现问题）——性能：TTFT 首字延迟、Token 消耗、429/500 请求比例；质量：LLM-as-Judge 抽样评检索相关性和 Faithfulness；用户：显性反馈（点赞点踩）+ 隐性（重试率、放弃率），点踩率突增是第一报警信号。

② 全链路追踪（定位问题）——Langfuse 用 trace_id 调出完整执行树，Agent 黑盒拆成 LLM 调用/向量检索/外部 API 多个 Span。幻觉或拒答→看 LLM Span 的 Prompt 和召回 Chunk；Tool 失败→看 Tool Span 的 JSON Payload 和外部返回。

③ 故障闭环（修复问题）——线上 Case 离线 Replay（拉上下文改 Prompt 重放），修复后的 Bad Case 沉淀进黄金数据集进回归测试，防发版退化。

离线 RAGAS 管策略对不对（发版前全量），在线 LLM-as-Judge 管活不活（抽样实时），两者互补。”

Q18：最大的挑战 / 最有成就感的点？（Harness 版）

展开答案

“最有成就感的不是某个检索算法，而是给 Agent 设计了一套推理与执行解耦的控制层——Harness。核心问题是大模型只该做决策、不该碰执行——如果让 LLM 直接调工具写库，一旦输出格式漂移或被骗注入就是事故。所以我们的架构是 LLM 只输出标准化的 tool_call JSON，真正执行权在我们的 Harness 层。

三个关键技术点——中间件拦截管道：所有 tool_call 先过 Harness 中间件（白名单校验、Schema 校验、P0/P1/P2 分级、金额风控），高危操作挂起转人工。抢占式中断：并发时用户改需求，Harness 作为唯一入口 Cancel 所有子协程，唤醒 Supervisor 重规划。状态机管理：每个 Agent 只有 INIT/RUNNING/SUSPENDED/TERMINATED 四状态，事件驱动迁移。

为什么技术含量高——这里不是调 Prompt 能解决的，是控制流、状态管理、并发协调这些确定性工程。大模型输出永远有不确定性，Harness 用代码把这些不确定性关在笼子里。

落地说明：架构设计方向是我们定的，落地用 LangGraph 做图编排底座——Checkpointer 做状态持久化、interrupt_before 做 HITL 挂起、条件边做路由。中间件管道和安全拦截是我们自己写的应用层代码。”

Q19：工具过多带来的 Token 消耗怎么省？识别错误、调用错误怎么兜底？

展开答案

“先拆本质——工具数 N 上涨时成本是双杀：①每轮请求把全部工具的 name+description+参数 Schema 拼进上下文，Context Window 暴涨，Token 与延迟激增；②工具越多 LLM 注意力越稀释（Attention Dilution），引发工具选择幻觉（选错）和参数组装错误（调错），系统级不稳定。解法分两大块——省 Token 靠’动态加载少喂‘，纠错靠’Harness 兜底 + Schema 边界感‘。

先说清落地现实：The Boy 目前工具量小——知识库对外收敛成 2 个 MCP 工具，Supervisor 只路由不挂工具、Worker 各挂 3-5 个本职工具，静态挂载已经够用。下面这套是工具规模上百时的演进方案（我在做架构设计时预留了这条路，同一套检索基建可以直接复用，不用推翻重来）。

一、省 Token：从’静态硬编码’到’工具动态检索’（RAG for Tools）

核心转变——不再把几十个工具 Schema 静态写死进 System Prompt，而是把工具本身当成知识库检索：

  • 入库：每个工具的 name+描述+参数结构向量化，存进 pgvector（专门一张 tools 表），工具变更即增量更新——正好复用 BGE-M3 的嵌入基建（也呼应 Q10：pgvector 一套库就够，不用为工具检索单独上 Milvus）。
  • 检索：用户 Query 来了，先混合检索（BM25+向量 ANN）召回候选，再过 bge-reranker 重排，只取 Top-K（3-5） 个最相关工具注入上下文，工具 Token 消耗可省 80%+——和文档检索的’粗召回+精排’是同一个两段式，原理我完全现成。
  • 降级兜底：一个’未匹配工具’的兜底选项，检索不到时让模型明确走兜底或如实说没有该能力，避免静默漏工具。

动态检索管’跨域几百个工具’，Supervisor-Worker 管’域内 3-5 个’——两层叠加都在压每轮可见工具数。再配静态侧的 Schema 极致压缩：描述只留’动词+宾语’剔除人类向长解释；同类小工具合并成带可选参数的 universal_search，The Boy 的 search_knowledge 收敛多检索方式进 mode 参数就是这个思路。

二、减少识别/调用错误：三层兜底

① Harness 自纠错闭环（Self-Correction）——治调用错误
推理与执行解耦后，Harness 不只是一出错就 break，而是承担执行容错：Schema 校验失败或底层调用抛异常（如 missing required parameter 'document_id'），Harness 拦截 Exception，把结构化报错摘要作为一条新 User Message 反投给模型，触发自我修复，通常重试 1-2 次就能纠正传参——和 Q13 的错误分类对齐：可修复错误（补参数/改格式）回灌重试，不可修复错误（业务 404/权限）立即停止、换工具或如实答用户，不空转。

② 描述’边界感’ + 参数级 One-Shot——治选错与拼错
很多调用错是工具语义重叠导致。加反向提示（Negative Prompting）：每个工具描述里写清’什么时候别用它’（如’只查实时状态，查历史文档必须用 query_confluence’）；复杂参数在 description 里直接给合法取值示例（"format": "YYYY-MM-DD"），把格式解析失败率压下来。另配一套’意图→应选工具’离线评测集做回归，选错率抬头就回头查描述。

③ 强制类型校验 + 系统参数下沉——从源头不让它拼错
用模型 Structured Outputs / Strict Schema 强制输出 100% 匹配工具签名，类型错误在生成源头被堵住；多步骤状态依赖（先调 A 拿 ID 再调 B）里的 session_id / context_keys 这类系统级参数下沉到内存或 pgvector、由 Harness 注入，对 LLM 屏蔽——它不需要推理这些，少一个可拼错的参数就少一类错误。

一句话收口：省 Token 靠’工具动态检索 + 多 Agent 收敛 + Schema 压缩’把每轮可见工具压到个位数；纠错靠’Harness 自纠错闭环 + 负向边界描述 + Strict Schema + 系统参数下沉’把错误挡在源头。工具是给 LLM 的可选项菜单——菜单越短越准，越不会点错。“

Q20：短期记忆具体怎么实现？怎么控制它不把上下文撑爆？

展开答案

“短期记忆的本质是在 Token 预算内保住当前会话的连续性——不是’记住更多’，而是’在有限上下文里决策什么该留、什么该丢’。我拆成四个实现块：分层预算、窗口+溢出处理、结构化下沉、多 Agent 隔离。

① 消息模型 + 分层预算（先算账再说话）

  • 每条消息存成 {role, content, token, ts}，token 用真实 tokenizer 数，不是数字符。
  • 每轮调用前先算总账。窗口是分层预留的，不是一条大列表：System 固定区（永远在、不参与裁剪）＋ 会话摘要区 ＋ 最近 K 轮原文 ＋ 工具 Schema 区（配合 Q19 动态检索只留 3-5 个）＋ 给模型输出留的余量。哪层超了就处理哪层，而不是无差别丢最老的。
  • 为什么不能全量堆历史：上下文越长注意力越稀释、每轮 Token 越贵——所以短期记忆的本质是把’全量历史’降级成’够用的连续性’。

② K 轮窗口 + 溢出双策略：裁剪 or 压缩

  • 触发点：累积超预算（比如 8K token）才整理，不是每轮都整。
  • 裁剪（快）：丢最老的寒暄/无关消息，直到回落到预算内。适合信息密度低的闲聊轮，省一次 LLM 调用。
  • 压缩（保真）：把窗口’上半段旧消息’交给压缩器 LLM，生成一段紧凑摘要（原文 3000 token → 摘要约 300，≈90% 裁剪），摘要作为一条合成消息 pin 到会话顶部、原文删掉，保留最近 K/2 轮原文。摘要继续随窗口滚动更新（rolling summary）——之后每轮只读’摘要 + 最近原文’，不回头重读全部历史。
  • 取舍一句话：寒暄轮裁剪、关键推理轮压缩，正确性轮次不能只留摘要。

③ 关键信息结构化下沉（比纯文本摘要更可靠）

  • 文本摘要 LLM 读得懂、程序用不了。对话里的用户偏好、未完成任务、已做的决策、HITL 挂起点、任务进度抽成结构化 session_state（key-value）写 Redis、带 TTL——LLM 决策读摘要保语义连贯，控制流读结构化字段保确定性，两条腿走路。
  • 凡是必须精确的内容（单号、金额、引用出处）在裁剪/压缩之前先落进 Redis 字段——摘要只负责语义连贯，精确信息交给字段，防止摘要把数字揉丢。

④ 多 Agent 的短期记忆：交接即提炼，不搬运全量（The Boy 的关键设计）

  • 上下文三层（Q9 提过）——系统级共享、Session 级在 Redis 黑板、Agent 级是局部草稿纸。每个 Agent 自己那几轮的思维链＋工具调用记录留在局部草稿纸，任务结束归档丢弃；移交给下一个 Agent 的只是提炼出的核心变量进黑板。不共享完整 transcript → 累积被结构打断，这就是 The Boy 对话再长也不会把上下文撑爆的原因。
  • 会话恢复：Redis 以 thread_id 为键存 Session 状态＋最近摘要，重连时取出重建窗口（呼应 11.4 的 resume 设计）。
  • LangGraph 落地：messages 走 state channel 增量 append，摘要整理做成一个节点在溢出时触发，Checkpointer 按 thread_id 存快照，Redis TTL 回收过期会话，防止记忆表无限涨。

一句话收口：短期记忆 = 分层预算做容器，K 轮窗口当边界，裁剪/压缩当溢出策略，结构化字段当精确锚点，多 Agent 交接提炼当防膨胀闸门——不是单纯’留最近 N 条消息’。“
