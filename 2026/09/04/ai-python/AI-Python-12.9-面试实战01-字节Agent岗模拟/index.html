Q1：项目中用了几个模型，分别是什么？

展开答案

“为了平衡响应延迟、数据隐私和 Token 成本，我设计了大模型 API + 本地小模型的混合架构，落地 4 个模型分三个环节。

摄入层：Qwen2-VL-2B 本地部署，把图文混合文档统一解析成文本模态——2B 小模型满足预处理吞吐量，省去多模态 API 成本。

检索层：BGE-M3 生成稠密向量 + bge-reranker 交叉编码重排，纯本地双模检索。我们评测时核心盯 Recall 和 Faithfulness，这套组合保证喂给大模型的上下文质量。

推理层：DeepSeek API 做多智能体的核心推理引擎，只负责意图判断和路由决策，严格输出 JSON Schema 指令，本身不执行任何工具调用。

执行层：用 LangGraph 做图编排底座，工具调用、HITL 挂起、状态持久化都在 Harness 层完成——推理和执行解耦。整体看，高并发预处理和检索本地化，复杂推理交给外部 API，每个模块可独立评测迭代。”

Q2：为什么 Embedding 用 BGE-M3 而不是 OpenAI 或智谱/阿里？

展开答案

“三个理由。一，成本与隐私——BGE-M3 开源本地部署，零 API 成本、数据不出本地；对比 text-embedding-3 按 token 收费且数据出境。二，中文效果——智源训练的中文专项优化，比 OpenAI 的英文向模型对中文知识库效果好。三，M3 三合一能力——Dense 语义 + Sparse 关键词 + Multi-vector 细粒度，一个模型就能支撑混合检索，不用额外配 BM25。

对比国内——智谱 embedding-3 和阿里 text-embedding-v3 都是纯 API、只能出稠密向量，做混合检索还得自己拼关键词召回。BGE-M3 是当时开源里混合检索能力最完整的。阿里后来开源的 Qwen3-Embedding 很强，但落地时还没发布。”

Q3：知识库是怎么分块的？为什么这么分？

展开答案

“我们不是用一种分块方式，而是 KB 类型决定策略——四类异构数据，四种方案。

文档库：语义切分。按 ## 标题边界切，一个操作流程 = 一个 chunk。因为操作文档是步骤化的，按标题切不会切断操作流程。

论文库：Section 切分 + 公式分离。按 Abstract/Intro/Method 独立切，公式保留 LaTeX 的同时让 LLM 生成语义描述，避免公式 Embedding 后变成乱码向量。

专利库：Field-split + 父子块联动。按摘要/权利要求/附图分字段切，正则提取权利要求引用链，把 parent_chunk_ids 存进 metadata——检索命中子块自动拉父块。关键是引用链用正则提取，零 LLM 成本。

业务库：Row-to-NL。结构化数据每行转一段自然语言描述，因为向量检索对精确数值无效——数值查询走 Tool Router 转参数化 SQL。

核心原则：能用正则解决的坚决不用 LLM。”

Q4：混合检索具体怎么做？

展开答案

“混合检索 = 稠密向量检索（语义相似）+ 稀疏关键词检索（BM25 精确匹配），互补长短。

语义检索能匹配近义词——‘怎么减小显存’能搜到’降低显存占用’；但专业术语、商品型号、错误码这些精确字符串，向量相似度匹配不准。BM25 正好相反——精确关键词一搜即中，但换种说法就召回不了。

融合用 RRF 倒数排名融合——不看两个检索器的原始分数（分数体系不可比），只看排名，用 1/(k+rank) 加权求和，k=60。排名靠前的文档在两种检索里都出现就会显著靠前。”

Q5：既然混合检索召回了，为什么还要 Reranker？

展开答案

“混合检索只能保证’相关文档在候选集里’，不能保证’最相关的排在最前面’——Embedding 和 BM25 都是粗糙的一阶段匹配。

Embedding 是 Bi-Encoder——问题和文档各自编码，最后算相似度，快但粗；Reranker 是 Cross-Encoder——问题和文档一起编码，能看到二者的完整交互，准但慢。

因为 Reranker 慢，它不能在全库上跑，只能对一阶段召回的小候选集做重排——粗召回 + 精排两阶段架构。召回阶段保证 Recall（扩，宁多勿漏），Reranker 阶段保证 Precision（缩，去噪取精）。”

Q6：检索到文档后，怎么保证不幻觉？

展开答案

“四个层面层层兜底。

一，Prompt 硬约束。System Prompt 明确写：’回答必须基于检索文档，引用的信息必须在文档中找到依据；文档中没有的，直接回答不知道，禁止编造。’

二，质量门（Quality Gate）。关键是不用 LLM 打分，用检索相似度的硬阈值——每种 KB 设不同阈值（论文 0.35、专利 0.30、文档 0.25、业务 0.40），平均相似度低于阈值直接拒答。零成本、确定性、可解释。

三，生成后自检（Self-RAG 思路）。校验器检查回答里每个关键事实能否在文档找到原文依据，找不到就重新检索生成，直到通过或达到最大轮次。

四，评测兜底。离线 RAGAS 四指标跑分层测试集，监控哪个指标下滑，反向驱动调优——Faithfulness 下降就加强 Prompt，Precision 下降就调 Reranker。”

Q7：RAG 检索效果怎么评估？具体指标？

展开答案

“用 RAGAS 四指标。检索阶段——Context Precision（搜回来的多少真正相关，信号 vs 噪声）、Context Recall（该搜的都搜到没，有没有漏）。生成阶段——Faithfulness（有没有编造）、Answer Relevancy（切不切题）。

测试集分层设计——15 道题：精确单领域 9、跨领域 3、模糊查询 2、无关查询 1（测拒答）。

减方差两个手段——评测时 temperature=0 消除生成随机性；同一样本跑两次取平均，因为 LLM-as-Judge 本身有波动，两次差超 0.1 就标记异常。

诊断矩阵——Precision 低→加 Reranker 降 k（缩）；Recall 低→混合检索增大 k（扩）；Faithfulness 低→加强 Prompt；Relevancy 低→Query 改写+Step-Back。”

Q8：为什么选 DeepSeek 而不是 GPT-4o / Claude？

展开答案

“四个理由。一，成本——对比 GLM、Claude，DeepSeek API 价格最低，知识库高频调用成本敏感。二，中文效果——国内模型里 DeepSeek 的中文推理和指令遵循最强，我们知识库中文为主。三，数据合规——国外模型数据出境不满足要求。四，Function Calling 原生支持——对 Agent 开发这是关键能力，工具调用走 Schema 约束稳定可靠。综合成本、中文、合规、FC 四维度，DeepSeek 是最优解。”

Q9：你的多 Agent 是怎么设计的？任务怎么分工？

展开答案

“单 Agent 升级多 Agent 三个原因——上下文超长注意力偏移、工具多选择错误率上升、安全隔离（单 Agent 全暴露权限没法细分）。

模式是 Supervisor + Worker——Supervisor 负责任务推理、意图路由、任务分解；Worker 接受任务、调自己的工具集执行、汇报结果。

通信上禁止 Agent 直接对话（自然语言会死循环、Token 爆炸、幻觉率高），所有协作通过 Redis 全局黑板交换结构化数据。每个 Agent 独享的上下文留在自己的局部草稿纸，任务结束就归档丢弃。

上下文分三层隔离——系统级（回答风格、安全红线，共享）、Session 级（当前对话、关键决策、HITL、进度）、Agent 级（当前 Agent 独有思维链、工具调用记录、错误重试）。交接时 Harness 只把 Agent 级核心变量提炼到全局黑板，干净交给下一个 Agent。”

Q10：为什么用 pgvector 而不是 Milvus 或 FAISS？

展开答案

“三个理由。一，数据量级——百万级 chunk 单机 PostgreSQL 完全够，Milvus 是为十亿级分布式设计的，对我们这个量级是过度设计。二，向量和 SQL 一条语句——向量检索 + 结构化过滤（如 filing_year=2024 AND applicant='华为'）一条 SQL 搞定，Milvus 要两套系统多一跳。三，运维成本——我们本来就有 PostgreSQL，pgvector 是扩展零新增服务。

什么时候换 Milvus——chunk 量上千万、QPS 高到单机扛不住。我们的 DDD 架构里 BaseVectorStore 是抽象接口，pgvector 只是 Infrastructure 的一个实现，将来换 Milvus 只改一个实现类。”

Q11：HNSW 索引原理？为什么快？

展开答案

“HNSW = Hierarchical Navigable Small World（分层可导航小世界），pgvector 默认的 ANN 索引。

核心思想是图搜索代替暴力比对——把向量建成多层图：顶层节点稀疏、连的是远距离长跳，底层稠密、是精确近邻。检索时从顶层入口出发，沿着’离查询越来越近’的方向跳到下一层，逐层下探，最后在底层沿边找到最近邻。只访问几十个节点，而不是比对全部向量。

它属于 ANN（近似最近邻）——牺牲一点精度换速度。参数 m（邻居数）控制召回率，ef_search 控制检索精度。RAG 场景下 Reranker 会二次精排，所以召回阶段的近似可接受——HNSW 出候选，Reranker 出最终排序。”

Q12：数据怎么入库？重复文档和图片怎么处理？

展开答案

“入库流程六步——加载（PDF/Word）、清洗（去页眉页脚）、多模态提取（图片 Qwen2-VL 转文字）、分块（按 KB 类型选策略）、向量化（BGE-M3）、存储（pgvector）。

更新策略分全量和增量——首次建库或大规模变更走全量，日常走增量（文件哈希或更新时间戳检测）。

重复处理两层。文档层——MD5 内容哈希精确去重 + Embedding 相似度近似去重。图片层——先 MD5 精确匹配，再 dHash 感知哈希判相似，相似度超 95% 复用已有描述。去重率 40-60%。关键是去重发生在多模态提取之前——因为提取最贵，先哈希去重再决定要不要调模型。”

Q13：Agent 怎么防死循环和 Token 浪费？

展开答案

“从错误分类、死循环熔断、轮次上限、Token 控制四层设计。

错误分类——网络错误指数退避重试上限 3 次；业务错误（权限/数据不存在）立即停止；参数错误追加上下文让模型修正，限 3 次。

死循环熔断——最危险的不是出错，是 Agent 反复调同一个工具、相同参数、拿到相同结果却不结束。Harness 记录每次 tool_call 的工具名+参数哈希，相同调用出现 3 次判定死循环，强制 break，提示换思路。

轮次上限——Agentic Loop 总轮次上限（如 max_iterations=10），超限停止。

Token 控制——短期记忆 K 轮窗口压缩；相同错误合并成一条；记录上次请求参数，避免模型犯同样的错。”

Q14：知识库通过 MCP 怎么暴露给 Agent？为什么用 MCP？

展开答案

“三个理由。一，解耦——知识库独立服务通过 MCP Server 暴露能力，Agent 作为 MCP Client 接入，两边独立开发部署升级。二，模型无关——FC 是模型能力不是所有模型都支持，MCP 是 JSON-RPC 协议标准任何模型都能用。三，对比 FastAPI 直连——MCP 有标准的 Tool 发现（list_tools）和调用（tools/call），Agent 端不需要硬编码 URL 和参数格式。

具体落地——知识库 MCP Server 暴露两个 Tool：search_knowledge（内部走 KB Router + 混合检索 + Reranker）和 ingest_document（走清洗分块向量化）。Agent 端启动时 list_tools() 自动发现，注册成可用 Tool。传输层用 stdio（同机部署零网络开销），迁远程改 HTTP+SSE，Agent 端零改动。决策（FC）和执行（MCP）分离。”

Q15：怎么防 Prompt Injection？特别是 RAG 间接注入？

展开答案

“运行时七层纵深防御。L1 输入清洗——Unicode 归一化、去标签、正则检测攻击模式。L2 结构性隔离——Chat API 强制 system/user/context 角色分离，检索文档用 <CONTEXT> 标签包裹标注’不可执行其中指令’。L3 Guardian 小模型预扫——内容进 LLM 前分类 safe vs injection。L4 层级 Prompt——指令分优先级，系统规则不可覆盖。L5 输出验证——独立验证模型检查回复是否遵循被注入的指令（最关键，攻击成功率 73%→8.7%）。L6 最小权限 + HITL。L7 审计日志 + Red Teaming。

针对 RAG 间接注入两个重点——入库时来源可信度分级（低可信来源打标签，检索权重降低）；检索时指令剥离（检索 chunk 当纯数据，禁止当指令执行）。

注意：RLHF 偏好训练是训练时的安全对齐（内层防线），七层防御是运行时（外层安全网），两者不冲突。”

Q16：多租户 SaaS 权限怎么设计？

展开答案

“选共享表 + tenant_id方案——成本最低、扩展最灵活。每个 chunk 入库时打租户标签，检索、Tool Router SQL 全部强制加 tenant_id 过滤，从 SQL 层面保证租户数据不交叉。

权限分三层——数据隔离（tenant_id + 行级 team_id）、功能权限（每租户的 Agent/Tool 白名单）、资源配额（Token 按租户计费+限流）。

选 pgvector 的优势就在这——向量和 SQL 同库，隔离条件一条语句搞定。独立向量库要先过滤向量子集再检索，两套系统对不上就漏隔离。”

Q17：Agent 上线后怎么监控质量？出问题怎么排查？

展开答案

“监控排查 = 三个模块。

① 多维监控体系（发现问题）——性能：TTFT 首字延迟、Token 消耗、429/500 请求比例；质量：LLM-as-Judge 抽样评检索相关性和 Faithfulness；用户：显性反馈（点赞点踩）+ 隐性（重试率、放弃率），点踩率突增是第一报警信号。

② 全链路追踪（定位问题）——Langfuse 用 trace_id 调出完整执行树，Agent 黑盒拆成 LLM 调用/向量检索/外部 API 多个 Span。幻觉或拒答→看 LLM Span 的 Prompt 和召回 Chunk；Tool 失败→看 Tool Span 的 JSON Payload 和外部返回。

③ 故障闭环（修复问题）——线上 Case 离线 Replay（拉上下文改 Prompt 重放），修复后的 Bad Case 沉淀进黄金数据集进回归测试，防发版退化。

离线 RAGAS 管策略对不对（发版前全量），在线 LLM-as-Judge 管活不活（抽样实时），两者互补。”

Q18：最大的挑战 / 最有成就感的点？（Harness 版）

展开答案

“最有成就感的不是某个检索算法，而是给 Agent 设计了一套推理与执行解耦的控制层——Harness。核心问题是大模型只该做决策、不该碰执行——如果让 LLM 直接调工具写库，一旦输出格式漂移或被骗注入就是事故。所以我们的架构是 LLM 只输出标准化的 tool_call JSON，真正执行权在我们的 Harness 层。

三个关键技术点——中间件拦截管道：所有 tool_call 先过 Harness 中间件（白名单校验、Schema 校验、P0/P1/P2 分级、金额风控），高危操作挂起转人工。抢占式中断：并发时用户改需求，Harness 作为唯一入口 Cancel 所有子协程，唤醒 Supervisor 重规划。状态机管理：每个 Agent 只有 INIT/RUNNING/SUSPENDED/TERMINATED 四状态，事件驱动迁移。

为什么技术含量高——这里不是调 Prompt 能解决的，是控制流、状态管理、并发协调这些确定性工程。大模型输出永远有不确定性，Harness 用代码把这些不确定性关在笼子里。

落地说明：架构设计方向是我们定的，落地用 LangGraph 做图编排底座——Checkpointer 做状态持久化、interrupt_before 做 HITL 挂起、条件边做路由。中间件管道和安全拦截是我们自己写的应用层代码。”

Q19：工具过多带来的 Token 消耗怎么省？识别错误、调用错误怎么兜底？

展开答案

“先拆本质——工具数 N 上涨时成本是双杀：①每轮请求把全部工具的 name+description+参数 Schema 拼进上下文，Context Window 暴涨，Token 与延迟激增；②工具越多 LLM 注意力越稀释（Attention Dilution），引发工具选择幻觉（选错）和参数组装错误（调错），系统级不稳定。解法分两大块——省 Token 靠’动态加载少喂‘，纠错靠’Harness 兜底 + Schema 边界感‘。

先说清落地现实：The Boy 目前工具量小——知识库对外收敛成 2 个 MCP 工具，Supervisor 只路由不挂工具、Worker 各挂 3-5 个本职工具，静态挂载已经够用。下面这套是工具规模上百时的演进方案（我在做架构设计时预留了这条路，同一套检索基建可以直接复用，不用推翻重来）。

一、省 Token：从’静态硬编码’到’工具动态检索’（RAG for Tools）

核心转变——不再把几十个工具 Schema 静态写死进 System Prompt，而是把工具本身当成知识库检索：

  • 入库：每个工具的 name+描述+参数结构向量化，存进 pgvector（专门一张 tools 表），工具变更即增量更新——正好复用 BGE-M3 的嵌入基建（也呼应 Q10：pgvector 一套库就够，不用为工具检索单独上 Milvus）。
  • 检索：用户 Query 来了，先混合检索（BM25+向量 ANN）召回候选，再过 bge-reranker 重排，只取 Top-K（3-5） 个最相关工具注入上下文，工具 Token 消耗可省 80%+——和文档检索的’粗召回+精排’是同一个两段式，原理我完全现成。
  • 降级兜底：一个’未匹配工具’的兜底选项，检索不到时让模型明确走兜底或如实说没有该能力，避免静默漏工具。

动态检索管’跨域几百个工具’，Supervisor-Worker 管’域内 3-5 个’——两层叠加都在压每轮可见工具数。再配静态侧的 Schema 极致压缩：描述只留’动词+宾语’剔除人类向长解释；同类小工具合并成带可选参数的 universal_search，The Boy 的 search_knowledge 收敛多检索方式进 mode 参数就是这个思路。

二、减少识别/调用错误：三层兜底

① Harness 自纠错闭环（Self-Correction）——治调用错误
推理与执行解耦后，Harness 不只是一出错就 break，而是承担执行容错：Schema 校验失败或底层调用抛异常（如 missing required parameter 'document_id'），Harness 拦截 Exception，把结构化报错摘要作为一条新 User Message 反投给模型，触发自我修复，通常重试 1-2 次就能纠正传参——和 Q13 的错误分类对齐：可修复错误（补参数/改格式）回灌重试，不可修复错误（业务 404/权限）立即停止、换工具或如实答用户，不空转。

② 描述’边界感’ + 参数级 One-Shot——治选错与拼错
很多调用错是工具语义重叠导致。加反向提示（Negative Prompting）：每个工具描述里写清’什么时候别用它’（如’只查实时状态，查历史文档必须用 query_confluence’）；复杂参数在 description 里直接给合法取值示例（"format": "YYYY-MM-DD"），把格式解析失败率压下来。另配一套’意图→应选工具’离线评测集做回归，选错率抬头就回头查描述。

③ 强制类型校验 + 系统参数下沉——从源头不让它拼错
用模型 Structured Outputs / Strict Schema 强制输出 100% 匹配工具签名，类型错误在生成源头被堵住；多步骤状态依赖（先调 A 拿 ID 再调 B）里的 session_id / context_keys 这类系统级参数下沉到内存或 pgvector、由 Harness 注入，对 LLM 屏蔽——它不需要推理这些，少一个可拼错的参数就少一类错误。

一句话收口：省 Token 靠’工具动态检索 + 多 Agent 收敛 + Schema 压缩’把每轮可见工具压到个位数；纠错靠’Harness 自纠错闭环 + 负向边界描述 + Strict Schema + 系统参数下沉’把错误挡在源头。工具是给 LLM 的可选项菜单——菜单越短越准，越不会点错。“

Q20：短期记忆具体怎么实现？怎么控制它不把上下文撑爆？

展开答案

“短期记忆的本质是在 Token 预算内保住当前会话的连续性——不是’记住更多’，而是’在有限上下文里决策什么该留、什么该丢’。我拆成四个实现块：分层预算、窗口+溢出处理、结构化下沉、多 Agent 隔离。

① 消息模型 + 分层预算（先算账再说话）

  • 每条消息存成 {role, content, token, ts}，token 用真实 tokenizer 数，不是数字符。
  • 每轮调用前先算总账。窗口是分层预留的，不是一条大列表：System 固定区（永远在、不参与裁剪）＋ 会话摘要区 ＋ 最近 K 轮原文 ＋ 工具 Schema 区（配合 Q19 动态检索只留 3-5 个）＋ 给模型输出留的余量。哪层超了就处理哪层，而不是无差别丢最老的。
  • 为什么不能全量堆历史：上下文越长注意力越稀释、每轮 Token 越贵——所以短期记忆的本质是把’全量历史’降级成’够用的连续性’。

② K 轮窗口 + 溢出双策略：裁剪 or 压缩

  • 触发点：累积超预算（比如 8K token）才整理，不是每轮都整。
  • 裁剪（快）：丢最老的寒暄/无关消息，直到回落到预算内。适合信息密度低的闲聊轮，省一次 LLM 调用。
  • 压缩（保真）：把窗口’上半段旧消息’交给压缩器 LLM，生成一段紧凑摘要（原文 3000 token → 摘要约 300，≈90% 裁剪），摘要作为一条合成消息 pin 到会话顶部、原文删掉，保留最近 K/2 轮原文。摘要继续随窗口滚动更新（rolling summary）——之后每轮只读’摘要 + 最近原文’，不回头重读全部历史。
  • 取舍一句话：寒暄轮裁剪、关键推理轮压缩，正确性轮次不能只留摘要。

③ 关键信息结构化下沉（比纯文本摘要更可靠）

  • 文本摘要 LLM 读得懂、程序用不了。对话里的用户偏好、未完成任务、已做的决策、HITL 挂起点、任务进度抽成结构化 session_state（key-value）写 Redis、带 TTL——LLM 决策读摘要保语义连贯，控制流读结构化字段保确定性，两条腿走路。
  • 凡是必须精确的内容（单号、金额、引用出处）在裁剪/压缩之前先落进 Redis 字段——摘要只负责语义连贯，精确信息交给字段，防止摘要把数字揉丢。

④ 多 Agent 的短期记忆：交接即提炼，不搬运全量（The Boy 的关键设计）

  • 上下文三层（Q9 提过）——系统级共享、Session 级在 Redis 黑板、Agent 级是局部草稿纸。每个 Agent 自己那几轮的思维链＋工具调用记录留在局部草稿纸，任务结束归档丢弃；移交给下一个 Agent 的只是提炼出的核心变量进黑板。不共享完整 transcript → 累积被结构打断，这就是 The Boy 对话再长也不会把上下文撑爆的原因。
  • 会话恢复：Redis 以 thread_id 为键存 Session 状态＋最近摘要，重连时取出重建窗口（呼应 11.4 的 resume 设计）。
  • LangGraph 落地：messages 走 state channel 增量 append，摘要整理做成一个节点在溢出时触发，Checkpointer 按 thread_id 存快照，Redis TTL 回收过期会话，防止记忆表无限涨。

⑤ 存储分层——结构化字段到底存哪？（面试官追问点）
不是’Redis 还是 checkpointer’二选一，是三层嵌套：字段定义在 LangGraph State（逻辑层，messages/summary/session_context 都是 State schema 字段）；checkpointer 是持久化机制，每个 super-step 把整份 State 快照落盘，支撑 resume 和 HITL 恢复；The Boy 的 checkpointer 后端是 Redis（RedisSaver，key=thread_id）——物理上全在 Redis，checkpointer 是’负责把 State 写进 Redis 的那条代码路径’，不是手写 Redis 客户端。
真正该画的边界是什么进 State / 什么进黑板 / 什么不落盘：State 放’要恢复、图节点要读’的（摘要、决策、精确字段），代价是每步全量快照，所以大而临时的别塞 State（Agent 完整思维链放进去，每次 super-step 都整份重存 = 写放大，Task 结束直接丢）；跨 Agent 交接的结构化数据走 Redis 黑板独立键（独立 TTL、非图组件可读，Q9）；纯临时的草稿纸哪都不进。

⑥ 记忆注入节奏——记忆是每轮都注入吗？长期和短期一起进？（追问）
不是’每轮把三层记忆全塞进去’。分三档节奏——系统级每轮都带，但是固定小段常量（风格/红线），不随对话涨；短期每轮/Agent 每跳都带（对话连续性必需），但带的是’最近 K 轮原文＋滚动摘要’这个有界窗口，不是全部历史（④ 的防膨胀机制在管）；长期绝不全量每轮注入——分两类：身份画像类（用户是谁/固定偏好）会话启动时注入一次成 profile 卡片，聊到新偏好才增量更新写入、之后生效；情节/相关片段类按当轮 query 触发一次 top-k 语义检索，只把命中的 3-5 条拼进来。
为什么长期不能全量：token 成本随对话爆炸＋大量无关记忆反而注意力稀释（反效果）。注入的正确姿势是’固定一小段＋有界携带＋按需检索’，三层不是三份全量叠在一个 prompt 里。

⑦ 对话历史到底存 Redis 还是 DB？查询走哪个？（追问）
先分清’历史’的两副面孔——热历史（正在跑的会话：最近 K 轮原文＋摘要＋session_state）和冷历史（会话结束的完整留档、长期偏好）。The Boy 的分层：运行中的热历史走 Redis——LangGraph RedisSaver 按 thread_id 存 State，续聊＝按 thread_id 秒取重建，黑板/多 Agent 交接也在这（Q9），TTL 自动回收过期会话（Redis 不是可丢的缓存，会话活着时它是唯一事实源）；会话结束的完整留档走 PostgreSQL——原样落库做审计、bad case 复盘、RAGAS 分层测试集、长期记忆挖掘的原料（Redis 易失，权威副本必须在 DB）；要语义召回的长期偏好做向量化进 pgvector，命中后回 DB/缓存取原文。
查询按场景分流：续聊/resume→Redis（快）；Redis 过期或跨实例→从 PostgreSQL 归档重建 State（DB 兜底）；事后回看/审计/离线分析→PostgreSQL；长期记忆语义召回→先 pgvector 检索再回取原文。每轮喂 LLM 只读 Redis 热窗口，不碰 DB。
一句话：Redis 管’活着’（热读写、TTL 短命），DB 管’存档’（权威长存）——不是二选一，是一热一冷两层，查询按’正在聊还是事后查’分流。

一句话收口：短期记忆 = 分层预算做容器，K 轮窗口当边界，裁剪/压缩当溢出策略，结构化字段当精确锚点，多 Agent 交接提炼当防膨胀闸门——不是单纯’留最近 N 条消息’。“

Q21：怎么判断两个向量相不相似？用什么度量？

展开答案

“先答度量公式，再答关键点：检索系统里的’判断相似’其实是分层动作，不同环节用的’相似’定义根本不一样。

① 三种主流度量

  • 余弦相似度：cosθ = A·B / (|A||B|)，只看方向夹角，范围 [-1,1]。语义由方向承载、不应受文本长度干扰，所以语义检索默认它——长文本向量模长大，用点积会’天然更相似’，余弦把这个偏差消掉。
  • 欧氏距离（L2）：√Σ(aᵢ-bᵢ)²，直线距离，对模长敏感。一旦两个向量都归一化成单位向量，L2² = 2 - 2cosθ，和余弦单调等价——所以常说’归一化后 L2 ≈ 余弦’。
  • 点积：Σaᵢbᵢ = |A||B|cosθ，含模长项。BGE-M3 这类 embedding 输出默认就做 L2 归一化（单位向量），此时点积 == 余弦——很多系统就存归一化向量直接点积当相似度，pgvector 建 cosine 索引即可。

选型直觉：语义检索默认余弦；真在意’绝对距离’用 L2；归一化后点积就是余弦。没有绝对最优，跟向量空间性质有关——用离线评测集对比着选（Q7 那套）。

② 工程上’判断相似’是三层，不只是算一个数

  • 召回层（粗）：不能全库两两算余弦（O(N·d)），用 HNSW/IVFPQ 近似（Q11）——只跟分层图的邻居比，牺牲一点精度换速度。坑：pgvector 建 HNSW 索引时选的 operator class（cosine/l2/ip）必须和查询算子一致，否则索引不生效。
  • 精排层（准）：余弦是 Bi-Encoder 的浅层相似；Cross-Encoder Reranker 把 query 和 doc 拼一起联合编码、输出学习出来的相关度 logit，比余弦准——召回和精排用的是两把尺子（Q5 粗召回+精排）。
  • 判’相不相似’靠阈值，但阈值不可乱搬：余弦 [-1,1]、L2 [0,∞)，不同度量阈值没法互搬；同一种度量，不同领域/语言/embedding 模型分数分布都不同，必须各自标定——The Boy 质量门就是每个 KB 各设一个阈值（论文 0.35、专利 0.30、文档 0.25、业务 0.40，Q6），业务库文本和论文文本在向量空间里的分布本来就不一样。

③ 最常被坑的一点：相似 ≠ 相关
稠密余弦和 BM25 词频分数体系不可比，混合检索融合用 RRF 只看排名不看分（Q4）——分数只能在一个度量内部比大小。而且余弦高只说明语义近，不保证是正确相关：答案是’相关文档里的可支撑内容’决定的，所以才有 Reranker 和 RAGAS 的 Context Precision（Q3/Q7）。

一句话收口：度量三选一（语义默认余弦），工程’判断’三层化（召回近似+精排学习+阈值标定），分数只在同度量内可比、跨检索器只看排名，相似高≠相关。“

Q22：BGE（M3）是什么结构？是 transformer 的 encoder 那部分吗？

展开答案

“是的，BGE 就是 encoder-only（纯编码器）的 transformer——只做’理解→输出表示’，不做生成。先分清三族架构：encoder-only（双向注意力，BERT/XLM-R/BGE 这一族）看全句、产出句向量；decoder-only（自回归，GPT/DeepSeek/Qwen）只看左边、逐 token 生成；encoder-decoder（T5）做翻译摘要。The Boy 里 BGE-M3 变向量、DeepSeek 生成——都是 transformer，但一个是’看懂’一个是’说话’。

BGE-M3 的骨架是 XLM-RoBERTa-large（BERT 的多语言变体）：24 层、1024 维、16 头、约 5.68 亿参数、支持 8192 token、100+ 语言。

关键点：encoder 的输出还不是 embedding，中间还差两步——① encoder 最后一层给每个 token 一个 1024 维上下文向量（QKV/attention 只是算这些表示的手段，不是 embedding 本身——这是最常被混的坑）；② pooling 把整段 token 压成一个句向量，BGE-M3 的 dense 头用 [CLS] token 的向量（norm(H[0])），不是 mean pooling（社区转换工具经常标错，池化方式必须和训练时一致，用错了线上效果崩）；③ 训练目标（MLM 预训练＋对比学习＋自蒸馏）决定’语义近→向量近’。

BGE-M3 特别之处：一个 encoder 挂三个头——dense（CLS 向量，L2 归一化后点积=余弦，语义召回）、sparse（每个 token 学一个可学习词权重，类 BM25/SPLADE，关键词召回）、multi-vector（每 token 一个向量，ColBERT 式 MaxSim，细粒度匹配）。一个模型撑起混合检索（呼应 Q2/Q4），The Boy 本地 2.2GB 跑的就是它。

收口：BGE = encoder-only（XLM-R 骨架）→ CLS 池化出句向量；attention/QKV 是’内部怎么算表示’，余弦是’表示出来后怎么比’——两层别混。“

Q23：对话轮次太多、上下文装不下，怎么优化？有哪些手段？

展开答案

“轮次一多，病根是全部历史每次都进上下文——token 涨、注意力稀释、TTFT 涨、成本涨。优化方向一句话：别让’全部历史’一直活着，让’够用的记忆’活着。 手段按五档讲，从砍到拆——

① 砍：截断类（最简单）

  • 滑窗截断：只留最近 K 轮、丢最老——适合寒暄和任务已完成的前置轮。
  • 按类型裁，不只是按时间裁：先丢工具调用的原始 JSON、内部提示、图片只留 VLM 生成的描述不留 base64——这类又长又不需要模型推理的内容最先砍。
  • 系统 Prompt 瘦身：能搬进代码的（当前日期、固定配置）不写进 prompt。

② 压：摘要类（保语义）

  • 滚动摘要：旧轮压成摘要 pin 顶部（Q20 讲实现细节）。
  • 递归/多级摘要：摘要再长就做’摘要的摘要’，map-reduce 层次化——比一次性让模型吞全部更省、更不丢中间内容。
  • 关键信息提纯（改写式压缩）：把旧对话重写成几条规范化’已确定事实’（’用户要 A 不要 B’、’已订 3 号票’），丢过程只留结论——比摘要更结构化。

③ 查：历史外置类（对话当库查）

  • 对话历史向量化＋当轮 query 检索 top-k 相关旧轮（conversation RAG）：彻底告别全量携带，跨很多轮的依赖靠检索、不靠窗口。
  • 配合记忆分档注入（Q20⑥）：画像会话开头注入一次、片段按需查，不是每轮全量叠。

④ 沉：关键状态结构化

  • ‘必须精确/程序要用’的（偏好、未完成任务、单号）在裁剪之前先落 Redis 结构化字段——控制流读字段保确定性、LLM 读摘要保连贯，摘要有损、字段无损（Q20③⑤）。

⑤ 拆：别让对话无限长（架构根治）

  • 任务化/会话拆分：一次用户请求=一个子任务，Agent 草稿纸任务结束即归档（Q20④），长对话被拆成多个短任务，每个只带’提炼后的交接’——这是 The Boy 防膨胀的根本手段。
  • 话题切换/任务完成时主动’结单’：开新上下文、结论写入长期记忆，不背旧包袱继续聊。
  • 大窗口模型当兜底、不当默认：真需要全史回溯时才临时切大窗口。

选型逻辑：轮次少→砍；语义重要→压；跨很多轮才相关→查；程序要用→沉；控制不住→拆。 五档可叠加。

收口：轮次优化的全集 = 砍（截断）＋压（摘要）＋查（历史检索）＋沉（结构化）＋拆（任务化）。Q20 是其中’短期记忆’一层的具体实现，这题问的是手段全景。“

Q24：RAG 里一个大文件 400 万字，怎么处理？索引和 embedding 怎么实现？

展开答案

“先讲透一个原理，否则后面全是死记——embedding 是’一次性有损压缩’：无论文本多长，最终都被压成一个 1024 维向量。400 万字硬压成一个向量，等于把整本书压缩成三个字的摘要——里面什么都有、什么都分不清，检索时根本定位不到’离职赔偿’那一页。所以必须先按语义切块、让每一块产生一个聚焦的向量，就像给书做目录。下面用一个 400 万字的《员工手册》走完’切 → 向量化 → 索引 → 检索’四步。

① 切块（核心，效果上限全在这）

  • 切多粗是权衡，不是越细越好：块太大→一个向量混进多个主题，只能定位到’这本手册’却定位不到’离职那章’，命中还浪费 context；块太小→单句向量没上下文，’它’指谁都分不清。目标是每块一个主题、语义自洽。
  • 第一刀：按结构切——以标题/章节为边界（##/1.1），’离职管理’整章=一块，操作流程不被拦腰切断。
  • 第二刀：父子块，拿两头好处——parent＝整章《离职管理》原文（要喂给 LLM 的完整上下文），child＝章内每段（做向量检索的聚焦小向量），child 只存一个 parent_id 指针。检索时 child 命中 → 沿 parent_id 拉出整章喂 LLM。小向量搜得准、大章节答得全——就像地图：先用目录格子定位到街区，再翻开整页图看全貌（The Boy 专利库就是 Field-split＋父子块＋正则引用链，这条路已验证过）。
  • overlap 重叠：相邻块重叠 10-15%——防止’一个想法正好被切断：前半在 A 块尾巴、后半在 B 块头’，重叠保证它完整落在至少一块里。
  • 表格/公式另处理：公式向量化是乱码，LaTeX 原文保留＋补一句语义描述。
  • 能正则切绝不上 LLM 切：5500 块全用 LLM 切又贵又慢，章节规则够用就够（The Boy 原则：能用正则解决的不花 LLM）。

② 向量化——离线批量，不是每请求一次

  • 入库是离线一次性的，所以能做得稳：512-1024 token 一块，分批喂 BGE-M3（一次几十条、显存可控），失败重试＋断点续跑。
  • 量级（回答’会不会爆’）——4M 字 ≈ 280 万 token ÷ 512 ≈ 5500 块；每块一个 1024 维向量 ≈ 全部 20-30 MB。pgvector＋HNSW 存几千条是毛毛雨（呼应 Q10：百万级 chunk 单机都够）。再次强调：难点不是存不下，是切得准不准、检索拉得对不对。

③ 索引——让 5500 块里’查得快＋查得准’

  • 向量＋metadata 一条 SQL 进 pgvector：metadata 记 文件名/章节路径/页码/parent_id——能’全库搜但限定这本手册/这章’（Q10 同库优势），parent_id 供父子块回拉。
  • 建 HNSW 索引：把 5500 个向量织成一张’分层邻居图’，查询只访问几十个近邻而非全量比对（Q11）。

④ 检索闭环——用户提问走完整条路

  • 问’离职 N+1 怎么算’ → query 也向量化 → HNSW 从 5500 里粗召回约 50 个候选 → Reranker 精排取 top 5 → 命中的是 child 段落 → 沿 parent_id 拉出整章 → 质量门过关（Q6）→ 喂 LLM 作答。
  • 全程喂给 LLM 的是一章上下文，不是 400 万字——这就是大文件 RAG 的完整闭环。

⑤ 父子块怎么实现？’怎么找到父块’？（追问）
关键纠正：父子关系不是检索时才’找’的，是切分时就定死的——靠字符偏移的包含关系，不是靠向量相似度。赋值机制：外层循环遍历父块、对每个父块的正文再切子块——子块从哪个父块正文里切出来就归谁，parent_id 是’当前正在处理哪个父块’，是赋值不是查找（切分循环自带归属，不需要向量相似度、不需要事后回查）；只有想’整篇统一全局切子块’时才需要字符区间包含判断（此时父块别设 overlap，否则一个子块可能命中两个父块）。实现 = 两个切分器：child splitter（512 token/段落）负责做向量，parent splitter（也设大小上限 ~2000 token，不能真把整章拉爆 context）负责存上下文。检索三步：子块向量近邻 top-k → 收集 distinct parent_id → 按 id 回查父文本（去重，5 个命中常只来自 1-2 章）→ 喂 LLM。只给子块做 embedding（向量更少更聚焦），父块只存原文。现成实现：LangChain ParentDocumentRetriever、LlamaIndex HierarchicalNodeParser＋AutoMergingRetriever；The Boy 专利库正则提取引用链→parent_chunk_ids 进 metadata，是同一条思路的自写实现。

收口：大文件处理 = 把’整本书’降维成’5500 个聚焦向量＋章节索引’；切块质量决定上限（结构切＋父子块＋overlap），量级 20-30MB 根本不是问题。“

Q25：长期记忆怎么召回？什么时候触发召回？

展开答案

“先纠正一个惯性——长期记忆不是’需要时全量调出来’，要按两类记忆、三种触发节奏。长期记忆里其实混着两种东西，召回方式完全不同：

  • 画像类（用户是谁、固定偏好、红线）——相对静态，会话启动时注入一次成 profile 就够，不用每轮重查；聊到新偏好才增量更新、之后才生效（呼应 Q20⑥）。
  • 片段类（上次那件事、历史结论、任务轨迹）——跨会话的，要按语义检索。

片段类的召回有三种设计，从重到轻：
① 每轮 top-k（默认推荐）：每轮用户消息到达，用当前 query 对长期记忆库做一次语义检索，召回 top 3-5 条拼进上下文。pgvector 单次查询毫秒级、只取 3-5 条成本极小，还能随话题动态换相关记忆——大部分系统这个就够。
② 触发式（省、但信号要做对）：不是每轮都查，检测到’这轮需要历史背景’才触发——命中指代词（’上次那个’’按我的习惯’’我之前说过’）、意图分类判’需要偏好/历史’、或短期记忆里找不到自足信息（context 缺失）。触发式省一次检索，但漏判就丢上下文，信号要调准。
③ 画像类专属：会话启动预热——新会话开头把用户偏好 profile 拉出来注入 system 区，片段类再按 ①② 走。

工程细节（面试常追）：

  • 用什么当检索 query：别直接用原始用户消息——里面可能有指代（’那个方案’），短期记忆里的指代长期记忆库听不懂。先做一次 query 改写（结合会话摘要补全指代），再拿改写后的独立 query 去召回（呼应 query 改写/Step-Back 思路）。
  • 召回结果注入哪：长期事实属于’身份/背景’，注入 context 前缀或 system 区，不混进当前对话流，避免污染当前意图。
  • 为什么不全量每轮：token 成本＋大量无关记忆稀释注意力（反效果，Q20⑥）；体量用 top-k＋相关度阈值压住——低于阈值宁可不注入，给错记忆比不给更糟。

The Boy 落地：用户偏好 Redis 键值＋pgvector 向量化；节奏 = 会话启动拉 profile ＋ 对话中每轮对片段类做 top-k 语义召回（query 先改写去指代），命中的长期片段和短期记忆一起进分层预算容器（Q20）。

收口：长期记忆召回 = 画像启动注入一次＋片段按需/每轮 top-k 检索；触发键是’改写后的当前 query’而不是原始消息；体量用 top-k＋阈值压住，别全量每轮——给错记忆比不给更糟。“

Q26：怎么控制模型幻觉？有哪些手段？

展开答案

“先说结论性认知再上手段——幻觉只能压不能灭：LLM 是概率生成，’编’是它的默认倾向，目标是把它管到’能发现、可兜底、不落地造成损害‘。手段分五层，越靠前越治本。注意 Q6 讲的是我们 RAG 场景’答不答/怎么保真’的具体四层，这题问的是控制幻觉的完整手段全景，互补。

① 知识供给（让它不缺知识，就没理由编）：RAG grounding——答前先检索相关文档再答（The Boy 核心）；但检索质量要先保证——Recall 低=漏了知识→只能编，混合检索＋Reranker 就是干这个（Q4/Q5）；搜不到就有权拒答/如实说不知道，不硬答；数值/实时/内部状态一律走工具或 SQL 精确查（业务库 Tool Router），不让模型凭记忆蹦数字。

② 指令约束（让它别编）：System Prompt 硬约束要给出可执行话术而不是空喊’别编’——‘只基于以下参考资料回答，不要添加资料中没有的信息；如果无法回答，请说”根据已有资料无法回答”‘（rag/06 生成侧三件套原话）＋引用溯源：要求标注出处 [文档A-第3页]/chunk id——逼它只能从给定内容里组织语言，还给事后校验留抓手；给’不确定就承认’的安全出口；生成侧降 temperature（注意：temp=0 只减少不消除）。

③ 生成后校验（把已经编的拦下来）：置信度检查（第二 LLM）——独立判’这句话是否被文档支持’（旧博客 rag/06 就叫置信度检查，实现就是 LLM-as-judge 或专用 NLI 小模型，同七层防御 L5 输出验证思路）；Self-RAG 自检——回答里每个关键事实回文档找原文依据，找不到→重检索重生成、限轮次（The Boy Q6 已落地）；一致性校验——同一问题多次采样，回答不一致=可疑；质量门硬阈值——检索相似度低于阈值直接拒答（The Boy Q6，零成本确定性）。检索侧补 CRAG——检测到’检索回来的文档本身不可信’时自动评估＋改 Query 重查（rag/05、rag/10）；注意 Self-RAG/CRAG 每个 query 要多 3-9 次 LLM 调用，按可靠性要求取舍，别无脑全上。

④ 评测/监控（发现幻觉→驱动调优）：RAGAS Faithfulness/Relevancy 离线分层测试（Q7）盯幻觉率趋势；线上抽样 LLM-as-judge 打 grounding 分＋点踩率/拒答率报警（Q17）；bad case 沉淀进黄金测试集回归（Q17）。

⑤ 架构治本（少让它猜）：能用代码/正则/工具/结构化查询解决的，不给 LLM 自由发挥（The Boy 原则：能用正则解决的不花 LLM）；生成与查证分离——多 Agent 里配专职’验证 Agent’复核另一个 Agent 的输出；训练/选型层：选指令遵循好、被对齐过的模型（RLHF/DPO 是把’不编’训进模型的离线手段，对应 10.4，但我们调 API 主要靠选模型）。

边界补充（常被追问）——检索到的上下文是错的，模型也会’忠实幻觉’（Faithfulness 高但 grounding 错）：所以检索质量本身要管，光管生成侧不够；’知识性幻觉’（编事实）和’推理错误’手段侧重不同；幻觉率要用 Faithfulness/grounding 类指标衡量，不是靠感觉。

收口：幻觉控制 = 知识供给（有据可答）＋指令溯源（只答有据的）＋生成后校验（把编的拦下）＋评测监控（驱动调优）＋工具/架构优先（少让它猜）；压不灭，管到’能发现、可兜底’。“

Q27：对话内容是怎么叠加的？怎么判断快撞到上下文上限？

展开答案

“拆成两个子问题：叠加机制解释’为什么每次请求越来越贵’，判定时机解释’凭什么知道快撞线’。

① 叠加机制：LLM API 是无状态的，所谓’上下文’＝客户端每轮把累积消息列表整体重发

  • 每一轮 user/assistant 消息都 append 进一个消息列表——LangGraph State 的 messages channel 用 operator.add reducer：新消息追加、旧的不删，State 单调变长。
  • 但模型接口无状态，每轮请求都要把 system＋摘要＋累积消息重新序列化发一次 → 单轮 token ≈ 每条存活消息 × 它被重发的轮数。所以对话越往后单轮越贵、越长、越慢——这就是必须管理的根源。
  • 每条消息记账 {role, content, token}，token 用真实 tokenizer 数，不是数字符。

② 判定公式：别靠感觉，用’预算−预留’的水位线

关键坑：不能把 context 用满去装输入——模型还要生成输出 token，输入占满 100%，输出要么被截断、要么直接 400 报错。

③ 分档水位＋对应动作

  • 低水位（<60%）：只追加，不处理。
  • 高水位（~80%）：触发整理——把最早一段旧消息压成滚动摘要（Q20②），摘要设固定 token 上限；摘要再超就做’摘要的摘要’。
  • 临界（~90%＋）：强制收尾——Agent 场景直接中断继续推理，让模型用现有信息尽快给最终答案，别边想边涨到爆。
  • 精确计数为主，K 轮条数当第二道粗防线（快但不准，防止计数没跟上时先兜底）。

④ The Boy 落地：messages 走 LangGraph state 增量 append＋RedisSaver 快照（Q20⑤）；每次调用前按上式算账（Q20①的分层预算就是这套的容器），超水位在 Harness 层触发摘要节点或提前 break（与 Q13 轮次上限同一层）。

收口：对话叠加＝消息无脑 append、请求却整体重发，所以越来越贵；判定上限＝用’max_context−输出预留−安全边际’做预算，60/80/90 分档水位触发压缩或收尾——别等爆，提前 20% 就动手。“

Q28：文档解析时图片和表格的数据丢了，怎么办？

展开答案

“先立框架：图片/表格丢失很少是单一模型的问题，而是文档解析、结构化、切分、索引、检索、生成整条链路共同造成的。所以按’定位→恢复→降级→监控‘四段答，原则一句话——宁可标记不确定，也不能静默丢失或让模型猜测。

① 定位：丢可能发生在七个环节，逐层排查

环节 常见问题 检查方式
文件解析 扫描件无文本层、解析器忽略图片 对比原文与解析结果
OCR/视觉 图片文字漏识别、公式错 抽样核对 OCR 结果
表格提取 合并单元格、跨页表头、行列丢失 检查 HTML/JSON 结构
文本切分 表头与数据行被拆开 查看分块结果
向量化 图片没生成描述、表格被压成无结构文本 检查入库内容
检索 只召回正文、没召回关联图片表格 查召回日志
模型生成 数据已召回但模型忽略/误读 检查 Prompt 与上下文

② 恢复：图片走多模态链路，表格存三种形态
图片——不能只抓图片附近的文字，建多模态管线：从原文提取图片并保存页码/坐标/标题/上下文 → OCR → 视觉模型生成描述 → 图表额外抽’图类型/横纵轴含义/图例/数据点/趋势与异常’ → 描述＋OCR＋原图地址一起入库；检索命中描述时把原图一起返回给多模态模型复核。记录结构：

表格——不能转成连续文本，三种形态同存：原始表格截图（视觉复核）＋HTML/结构化 JSON（保行列、表头、合并单元格）＋Markdown/自然语言（模型理解＋向量检索）。

复杂表格额外处理：多级表头、合并单元格、跨页表头、重复表头、单位与脚注、空单元格继承、表题与正文引用关系。切分按’完整表格’或’表头＋若干数据行’，每个分块都重复保留表头，否则数据行单独检索就失去含义。数值精确查询走 Tool Router SQL（The Boy 业务库，Q3），Markdown 给 embedding 做语义召回、结构化行给 SQL 做精确——一套两用。

③ 降级：无法可靠解析时的多级回退

关键：解析失败时宁可标记不确定交人工，也不给 LLM 一个残缺结构去猜。

④ 监控：怎么发现丢（完整性校验＋指标）
校验清单：原文件图片数 vs 提取数、表格区域 vs 解析表格数、行列/表头数量、关键字段（数值/金额/日期/百分比）、OCR 与表格置信度阈值、解析结果与页面截图抽样比对；生成答案必须带页码/表格编号/图片编号（顺带给引用溯源兜底，呼应 Q26②）。量化指标四件套：

收口：图片表格丢失不是单一模型问题，是解析→结构化→切分→索引→检索→生成全链路共担。做法＝布局感知解析＋OCR＋表格结构识别＋多模态，图片/表格各存’原始截图＋结构化数据＋文本描述’三形态，绑定页码与坐标；失败走多级回退、以人工复核兜底；用数量/结构/置信度校验＋抽检把’安静地丢’变成’可发现、可追溯’。“

Q29：怎么观察模型召回了哪些 chunk？检索结果怎么追踪？

展开答案

“先立一个严格认知：Chunk 是检索器召回的，模型只会看到最终注入 Prompt 的那部分——中间隔着 Rerank、过滤、Token 截断。所以观察的核心不是’看模型看到了什么’，而是给 RAG 链路加一层检索追踪日志，把下面三个集合分开记：

只有三层分别记录，才能判断问题到底出在召回、排序、上下文截断、还是模型没采用。

① 从问题到回答，观察这 8 个锚点

阶段 记什么
用户问题 原始 query、用户、时间
Query 改写 改写后的检索词、子问题
初步召回 chunk_id、来源文档、页码、相似度
过滤 权限/时间/文档类型等过滤条件
重排序 Rerank 前后排名与得分
上下文组装 最终传给模型的 chunk
Token 截断 哪些 chunk 被截断或淘汰
最终回答 回答实际引用了哪些 chunk

② Chunk 必须带元数据，不能只把文本传给模型

③ 检索函数输出完整追踪——打印两层：初步召回 vs Rerank 后进模型的

④ Prompt 里给每个 chunk 明确边界＋编号，逼模型引用

并让模型’每个结论必须标对应 CHUNK_ID；没有证据就明说”检索内容不足”，不得自行推测’。效果：’算法贡献度由代码贡献、任务交付和质量指标组成。依据：[doc_002_p08_c01]’——从答案反查它用了哪些 chunk，形成审计闭环（呼应 Q26②引用溯源）。

⑤ 生产环境建议整条链路记录一条 Trace

⑥ 图片/表格要特别追踪（呼应 Q28 的丢失问题）

这样就能判断问题到底是五层里的哪一层：①根本没解析出来 → ②解析了没召回 → ③召回了被 Rerank 淘汰 → ④Rerank 保留了但 Token 超限被截断 → ⑤传给模型了但模型没采用。前四层是检索/上下文问题，最后一层才是生成问题——不再互相甩锅。

⑦ 可选的检索调试页面：四区域（用户问题＋改写 query / 召回 Top20 / Rerank Top5 / 最终注入上下文），每个 chunk 展示 chunk_id、文档名、页码、类型、向量分、Rerank 分、预览、原文链接、是否最终送入、是否被引用。

收口：观察召回的核心 = 把’召回≠Rerank 保留≠最终进 Prompt≠模型引用’四个集合分开记全——配合引用溯源和黄金集 Recall@k，才能精确定位问题出在召回、排序、截断还是生成。“
