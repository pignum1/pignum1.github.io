Q1：PagedAttention 为什么能提升吞吐量？

展开答案

核心原理

PagedAttention 把 KV Cache 切成 16 token 一个 Block，不预分配连续显存，通过 Block Table 做逻辑→物理映射。三大设计——固定 Block（类比 OS 4KB 页）、Block Table（类比 OS 页表）、Copy-on-Write（类比 OS fork，相同 System Prompt 只存一份）。效果：显存利用率 35%→96%，相同 System Prompt 省 20× 显存。

面试话术

“把 KV Cache 按 16 token 分块，Block Table 逻辑→物理映射。类 OS 虚拟内存——不预分配连续空间、按需分配、CoW 共享前缀。利用率 35%→96%。”

易混淆点

  • ❌ “PagedAttention 解决的是 n×n 矩阵太大” → ✅ 那是 Flash Attention。PagedAttention 解决的是 KV Cache 碎片化

Q2：Continuous Batching vs Static Batching？

展开答案

核心原理

Static Batching 等整个 batch 完成才释放——一个慢请求拖累全部。Continuous Batching 每个 decode step 后重新组装 batch——完成的立即移除，新的立即插入。GPU 利用率 30-50%→90%+，吞吐量 5-10×。

面试话术

“Static 整 batch 等最慢的。Continuous 逐 token 动态组 batch——完成的走、新的进→GPU 永远满载。”

Q3：投机解码的原理？

展开答案

核心原理

小模型（草稿模型）一次猜多个 token，大模型一次验证。接受率 >80% 时大模型调用次数减少 3-4×，总延迟降 2-3×。草稿模型必须同 tokenizer，通常选同一家族小模型。输出质量由大模型保证——验证并纠正，最终质量和正常大模型完全一样。

面试话术

“小模型猜、大模型验。一次前向查 4 个 draft——接受率 80% 时大模型调用减少 3-4×。同 tokenizer 是硬要求。质量不降——大模型纠正错的部分。”

易混淆点

  • ❌ “跟 Perceiver-Reasoner 一样” → ✅ 投机解码是同任务提速，Perceiver-Reasoner 是分任务提效果。完全不同的东西

Q4：vLLM + LoRA 部署架构？

展开答案

核心原理

一个 vLLM 实例加载基座 W 只一次，挂载 N 个 LoRA adapter。请求通过 API 指定 model name，vLLM 自动路由到对应 adapter。同一个 batch 混合不同 adapter 请求（Punica GEMM 内核），吞吐量接近纯基座推理的 85-90%。切换任务 = 换 adapter，W 不变。

面试话术

“一基座 N adapter，W 只加载一次。API 指定 model→vLLM 路由到对应 LoRA。同 batch 混 adpater，Punica GEMM→吞吐 85-90% 纯基座。”

Q5：量化方法对比（GPTQ / AWQ / GGUF）？

展开答案

核心原理

GPTQ 逐列量化加误差补偿，精度最高。AWQ 保护高激活通道，性价比最好。GGUF 不是量化算法是文件格式，配合 llama.cpp 在 CPU 上跑大模型。部署 GPU 服务端选 GPTQ/AWQ，本地 CPU 推理选 GGUF。正常训练不量化，唯一例外 QLoRA——基座 4-bit 冻住，只训 FP16 LoRA 旁路。

面试话术

“GPTQ 最准（逐列+误差补偿），AWQ 最快（保护重要通道），GGUF CPU 跑（llama.cpp）。GPU 部署选前两个，MacBook 本地跑选 GGUF。训练不量化，除了 QLoRA。”
