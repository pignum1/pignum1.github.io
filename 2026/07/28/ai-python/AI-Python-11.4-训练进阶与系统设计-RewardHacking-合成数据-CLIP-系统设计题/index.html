11.4：训练进阶与系统设计场景

最后一篇缺口补全：训练进阶（Reward Hacking + 合成数据 + CLIP）+ 系统设计场景题（AI 客服 + LLM 网关）。两个系统设计题是二面/三面的高分密码。

一、Reward Hacking（奖励破解）

1.1 一句话

RLHF 训练中，LLM 学会了”怎么让奖励模型打高分”而不是”怎么生成真正好的回答”。

1.2 典型表现

1.3 为什么发生

奖励模型是 RLHF 第二步训练的——给两个回答让人类标注”哪个更好”。但奖励模型是”偏好预测器”，不是”真理判断器”。它会学到人类标注中的偏见：长回答 > 短回答、自信语气 > 谨慎语气、迎合 > 反驳。

1.4 怎么缓解

方案 做法
KL 散度约束 限制 LLM 输出不允许偏离 SFT 模型太远
改进奖励数据 标注时刻意包含”短但精准”、”长但啰嗦”的对比
DPO 替代 PPO DPO 不需要单独训 RM，直接优化偏好 → 减少了作弊空间
多样化评估 不只靠 RM 打分，加规则检查（长度、多样性、事实性）

1.5 面试速答

“Reward Hacking 是 RLHF 的经典问题——模型学会了讨好奖励模型而不是真正变好。表现：回答变长、变谄媚、回避争议。解法：KL 散度约束限制偏移、DPO 替代 PPO 减少 Reward Model 依赖、多维评估不只靠一个打分。”

二、合成数据

2.1 什么场景需要合成数据

真实数据不够、或真实数据有隐私问题、或需要特定分布的数据时。

隐私保护 医疗数据不能直接用，合成模拟数据
多语言 中文问答数据不够，从英文翻译+改写

2.2 两种生成方式

2.3 核心挑战

挑战 说明
多样性不足 LLM 生成的数据趋于平均化，缺少创造性

三、CLIP 对比学习深入

3.1 CLIP 做了什么

CLIP（Contrastive Language-Image Pre-training）是 VLM 的基础组件。它让模型学会”把图片和对应的文字描述拉近，把不相关的推开”。

3.2 对比学习核心机制

3.3 为什么 CLIP 能泛化到没见过的东西

CLIP 用了 4 亿图文对训练——不是传统分类训练（猫/狗/车分 1000 类），而是”任意图片↔任意文字”的对齐。所以它能理解”一只穿着圣诞毛衣的柯基”这种训练数据里不可能有的组合——因为它分别理解”圣诞毛衣”和”柯基”。

3.4 面试速答

“CLIP 通过对比学习对齐图片和文字——最大化匹配对的相似度，最小化不匹配对。用了 4 亿图文对训练，泛化能力强到可以理解训练数据里没见过的概念组合。VLM（如 LLaVA/Qwen-VL）的图像编码器就是用 CLIP 训出来的 ViT。”

四、系统设计场景题

4.1 AI 客服系统设计

需求：7×24 语音/文字客服，支持多语言，能查订单、退货、投诉升级。

以下按面试回答的递进逻辑组织——从顶层设计到底层状态机，从”能跑通”到”生产级”。

第一层：开场定调 — 三步法确立架构视野

回答系统设计题，最忌讳一上来画架构图。先定义边界与核心理念。

“在深入具体架构之前，我先明确三个核心挑战。一，幻觉控制——客服容错率极低，必须基于事实回答。二，业务逻辑复杂度——不仅是问答，涉及多步操作：核身→查订单→查规则→执行退款。三，可扩展性与成本——随业务增长接入的系统越来越多，Token 成本需要全局统筹。

基于此，我的设计围绕三个核心理念：MCP 标准化底座——所有业务系统通过 MCP 协议封装为 Tool，避免 LLM 与底层 API 紧耦合。Agentic Loop + Harness 双引擎——Agentic Loop 负责’怎么做对’，Harness 负责’不要做错’。全局统一 Token 机制——多模态输入、RAG 上下文、中间思考全纳入统一管控。”

第二层：物理架构落地 — 四层拆分

基于三大理念，物理架构分四层：

层 做什么 关键技术
接入层 多模态+多语言+长连接 Whisper ASR, WebSocket, 语言路由
Agent 调度层 Agentic Loop 驱动，Harness 管控 ReAct, MCP Tool 调用, Supervisor 多 Agent
RAG 增强层 压制幻觉，提供事实依据 混合检索(BM25+Vector), pgvector, Reranker
安全兜底层 防注入、防越权、防不可用 PII 脱敏, P0/P1/P2 分级, 降级到预设 FAQ

第三层：核心引擎 — Agentic Loop + Harness 如何协作

“Agentic Loop 和 Harness 是双引擎。Loop 管执行——‘怎么做对’；Harness 管管控——‘不要做错’。不是替代关系，是执行层和管控层的上下配合。”

以退款高危场景为例：

组件 职责
Agentic Loop 拆任务、调 Agent、汇总结果
Harness 熔断、超时、权限检查、人工接管
两者关系 执行层 + 管控层，上下配合不互相替代

第四层：深水区 — 大模型怎么”调工具”？Harness 怎么拦截？

面试官追问到这里，说明在考底层机制。核心认知：大模型是”文本生成器”，不执行动作。触发链路分四步。

Step 1: 工具协议注入：系统通过 MCP 封装层将底层 API 抽象成 JSON Schema（如 ExecuteRefund 需要 order_id + amount），作为 tools 参数连同 Prompt 发给 LLM。

Step 2: 模型触发（不是执行）：LLM 不输出聊天文本，输出结构化 tool_call：

模型只输出”需求清单”——真正执行的是外围宿主程序。

Step 3: Harness 拦截（中间件管道）：宿主程序收到 tool_calls，第一件事不是调路由，是丢进 Harness 中间件：

  1. 解析 name="ExecuteRefund", amount=600
  2. 查工具安全配置：threshold < 500
  3. 600 > 500 → 越权 → 拒绝转发

Step 4: 状态挂起与反馈注入：拦截成功 → 打断 Loop → 挂起上下文 → 触发人工审核。审核不通过 → Harness 伪造错误 Observation 塞回 LLM → LLM 根据错误重新思考，向用户抱歉。

一句话：模型只提需求，Harness 执掌审批权。模型输出 JSON Payload → Harness 作为必经网关决定放行还是拦截。

第五层：Harness 生命周期 — 何时生效、怎么生效

核心定义：Harness 是有状态的生命周期管理器，由三个组件构成：

  • 全局上下文与记忆池（跨 Agent 共享状态）
  • 中间件管道（拦截器链，指令解析+安全校验）
  • 资源与监控器（统一 Token 机制，成本+并发+死循环监控）

四时机 Hook：

时机 节点 Harness 做什么
事前 初始化期 启动 Loop，分配 Token 预算，准备路由历史
事中 意图解析期 LLM 输出 Tool Call → 决定：调真实 API 还是路由给另一个 Worker Agent
事中 拦截校验期 调 API 前但未发网络请求 → 风控规则校验，决定是否挂起转人工
事后 状态注入期 API 返回 → 包装成 Observation 注入上下文 → 驱动下一轮 Loop

代码层面怎么生效：Agentic Loop 本质是 while 循环或异步 DAG，Harness 控制这个循环。所有 LLM I/O 被 Harness 接管。规则触发时 Harness 直接 break 或抛出 InterruptException——上下文序列化停止，发往 MCP Server 的 HTTP 请求被物理掐断。

核心理念：业务流与控制流分离。无论 Agent 推理多复杂，最终执行权在 Harness。

第六层：多 Agent 状态交接 — 上下文的切割与浓缩

多 Agent 协作的核心难点——不能把 Agent A 的 20 轮对话原封不动复制给 Agent B（上下文污染 + Token 爆炸）。

状态分层：

层 内容 可见性
全局黑板 (Global Blackboard) Order_ID、VIP 等级、对话大目标等结构化关键信息 所有 Agent 可见
局部草稿纸 (Local Scratchpad) 单个 Agent Loop 内的 Thought→Action→Observation 试错过程 任务结束后归档丢弃

交接链路四步：

  1. 售前 Agent 调用 Transfer_To_PostSales(reason="用户要退款", order_id="12345")
  2. Harness 截获 Transfer Tool → break 售前 Loop → 将 reason + order_id 写入 Redis 全局黑板
  3. Harness 用轻量 Prompt 对历史对话做极简摘要（如”用户情绪焦躁”），一并存入
  4. 开辟新草稿纸 → 启动售后 Loop。售后 Agent 醒来时 Context 极其干净——系统 Prompt + 交接变量 + 前情摘要

一句话：多 Agent 交接 = Harness 主导的”线程销毁与重建”。Agent 之间不直接通信，通过 Harness 总线用标准 Tool Call 完成。

第七层：并发与抢占式中断 — 用户中途变需求怎么办

Supervisor 不是”转交后就消失”，而是转变为异步等待的挂起状态。

并发执行：Harness 用多线程/异步协程同时启动多个 Worker Agent Loop，统一 Token 机制并行计算消耗。子 Agent 间禁止直接对话（防死循环 + Token 爆炸），只能通过全局黑板交换结构化数据。

抢占式中断（用户突然说”算了，直接退款”）：

  1. Harness 是唯一入口——用户新消息先到 Harness Web Server，不塞给子 Agent
  2. Harness 发现当前 Session 有子 Agent 在异步执行 → 立刻极速意图判定
  3. 意图变更 → Cancel 所有子协程，销毁 Loop，终止未发出的 MCP 调用
  4. 唤醒挂起的 Supervisor → 注入系统中断消息：[System Interruption]: "用户中止了当前任务，子任务已被强制取消。请重新规划。"
  5. Supervisor 拿到中断上下文 → 输出新 Plan → Harness 启动新 Worker

第八层：Harness 状态机 — 底层设计的基石

任何 Agent 在 Harness 中永远只处于四种状态：

状态 含义 触发
🟢 INIT 初始化就绪 Agent 刚分配任务，上下文+Tool 列表准备完毕
🔵 RUNNING 运行/推理中 大模型在输出或等待输出
🟡 SUSPENDED 挂起/阻塞 Tool Call 发出后等 API 返回或人工审核（可能持续几小时）
⚫ TERMINATED 终止/销毁 任务完成，或超时/死循环被 Harness 熔断

状态流转由事件驱动。业界标准用**图计算（Graph-based）**落地——每步是图上一个节点，状态流转是节点间的连线。不手写嵌套 while（回调地狱），Harness 按图的路径执行，每个 Agent 的状态切换清晰可追溯，并发场景下不会死锁或丢失上下文。

第一部分：明确挑战与核心设计理念（开场定调，展现架构视野）

“面试官您好。如果要设计一个企业级 AI 客服系统，我认为面临的核心挑战不仅是回答问题，更是如何控制幻觉以及如何安全地执行复杂的业务指令。因此我的设计思路不会停留在’调一个大模型 API’上，而是围绕标准化与可控性构建一个底座。系统贯彻三个核心理念：

一、标准化集成 (MCP 封装)：客服需要频繁调用内部 CRM、订单等系统。采用 MCP 协议对底层业务 API 和知识库统一封装。大模型作为 Client 接入，实现底层工具即插即用和零代码解耦。

二、稳健的引擎控制 (Agentic Loop + Harness)：核心是动态的 Agentic Loop（智能体循环），让 AI 通过’思考→行动→观察’解决问题。为防止死循环或越权操作，外围加一层强管控的 Harness（控制线束），负责生命周期监管、熔断和安全拦截。

三、全局统一 Token 机制：所有多模态输入、检索上下文和中间思考，纳入统一 Token 机制管理——全局上下文截断优化、高并发限流和成本追踪。”

第二部分：四层物理架构落地（展示系统级拆解能力）

“基于上述理念，具体架构拆解为四个核心层：

第一，接入层（多模态与路由）：处理多语言和多模态输入。文本走 WebSocket 保证长连接实时性；语音接入 ASR 转换（Whisper base + faster-whisper 流式）。重点优化端到端延迟，目标 < 500ms。

第二，Agent 核心调度层：系统的大脑。Agentic Loop 开始运转——LLM 识别意图后，通过 MCP 协议动态调用 Tool。同时，Harness 实时监控 Loop 运行状态——一旦发现重复调用无效 API，立即介入熔断。

第三，RAG 知识增强层：解决业务知识问答。产品 FAQ、退货政策 Embedding 存向量库（pgvector）。采用混合检索（Keyword + Vector），召回最相关的上下文片段喂给 LLM，从根本上压制幻觉。

第四，安全与兜底层：执行严格 PII 脱敏（手机号 138****1234）。退款、改签等高危写入操作，Harness 触发 Human-in-the-Loop，必须经由人工审核。LLM API 严重超时 → 自动降级到预设标准 FAQ 话术库，保证服务不中断。”

第三部分：架构演进与多 Agent 选型（展示扩展性与业务适配性）

“关于单 Agent 还是多 Agent，设计原则是不盲目堆砌，依业务复杂度演进。

业务初期：客服场景较收敛，单 Agent 挂载几个基础 Tool 就能搞定——响应快、易维护。

业务中后期：客服覆盖售前导购、售后维权、技术支持等多个复杂领域。单 Agent 的 Prompt 会极其臃肿，导致上下文丢失、Tool 调用混乱。此时升级到多 Agent 架构——采用 Supervisor (路由控制节点) + Worker Agents (领域专家) 模式。

用户进线后，Supervisor 识别大类意图：参数咨询 → 路由给挂载商品库的’售前 Agent’；退款争议 → 路由给挂载订单 API 的’售后 Agent’。这种设计完美解耦了业务逻辑，让每个 Agent 职责纯粹，系统更容易测试，也进一步降低了模型的幻觉率。”

Harness + Agentic Loop 的退款场景协作：

组件 职责
Agentic Loop “怎么做对”——拆任务、调 Agent、汇总结果
Harness “不要做错”——熔断(>8轮)、超时(>30s无响应)、权限检查(P0拦截)
两者关系 执行层 + 管控层，上下配合，不互相替代

4.1.1 工具触发与拦截链路：大模型如何”调工具”并被 Harness 拦截

现代 LLM 架构中，大模型本身不执行动作——它是”文本生成器”。触发工具依赖外围调度系统和模型之间的 Schema 契约。链路分四步：

第一步：工具协议注入（MCP → LLM 感知）

Agentic Loop 启动时，系统通过 MCP 封装层将底层 API 抽象成标准化 JSON Schema（如 ExecuteRefund 需要 amount 和 order_id），作为 tools 参数连同 Prompt 发给大模型。

第二步：模型触发（生成 tool_call，不是执行）

模型推理认为需要退款时，不输出聊天文本，而是输出结构化 tool_call：

模型只输出”需求清单”——真正执行的是外围宿主程序。

第三步：Harness 拦截（中间件管道）

宿主程序收到 tool_calls 后，第一件事不是调路由，而是丢进 Harness 中间件管道：

  1. 解析出 name="ExecuteRefund", amount=600
  2. 查询工具安全配置：threshold < 500
  3. 600 > 500 → 越权 → 拒绝向下游 MCP Server 转发

就在这个解析和转发环节，Harness 卡住了脖子。

第四步：状态挂起与反馈注入

拦截成功后，Harness 打断 Agentic Loop，挂起上下文，触发人工审核工单。审核不通过 → Harness 伪造一条错误 Observation（{"role": "tool", "content": "权限不足或被拒绝"}）塞回 LLM。LLM 根据错误信息重新思考，向用户输出抱歉话术。

一句话：大模型的”触发”本质是输出 JSON Payload；Harness 之所以能绝对拦截，因为它是这个请求落地成系统 API 调用之前的必经网关。

4.1.2 Harness 生命周期：是什么 + 何时生效 + 怎么生效

核心定义：Harness 是有状态的生命周期管理器，由三个核心组件构成：

  • 全局上下文与记忆池：跨 Agent 共享和传递状态
  • 中间件管道：拦截器链，负责指令解析、安全校验
  • 资源与监控器：承载统一 Token 机制，计算成本、控制并发、监控死循环

大模型和 MCP 接口是”被动调用”的组件，Harness 是那个一直在跑的 Main() 函数。

四时机 Hook：

时机 节点 Harness 做什么
事前 初始化期 启动 Agentic Loop，分配 Token 预算，准备路由历史
事中 意图解析期 LLM 输出 Tool Call → Harness 决定：发给 MCP 调真实 API，还是路由给另一个 Worker Agent
事中 拦截校验期 调用真实 API 前但未发网络请求 → 触发风控规则，校验权限，决定是否挂起转人工
事后 状态注入期 API 返回结果 → Harness 包装成 Observation 格式，注入上下文，驱动下一轮 Loop

中间件拦截代码实现（拦截发生在拿到 JSON 之后、真正调用 API 之前）：

关键理解：LLM 返回的 tool_calls 只是”提案”，你的代码是”审批人”。审批通过才执行，不通过就拒绝或挂起。

代码层面怎么生效：Agentic Loop 本质是 while 循环或异步 DAG。Harness 控制这个循环——所有 I/O 被 Harness 接管。规则引擎触发时，Harness 在代码里直接 break 或抛出 InterruptException，上下文序列化停止，发往 MCP Server 的 HTTP 请求被物理掐断。

核心理念：业务流与控制流分离。无论 Agent 逻辑多复杂，最终执行权始终被 Harness 锁死。

4.1.3 多 Agent 状态切割与交接

多 Agent 协作不能把 Agent A 的聊天记录原封不动复制给 Agent B——导致上下文污染和 Token 爆炸。

状态分层设计：

层 内容 可见性
全局黑板 (Global Blackboard) Order_ID、VIP 等级、对话大目标等结构化关键信息 所有 Agent 可见，跨节点共享
局部草稿纸 (Local Scratchpad) 单个 Agentic Loop 内的 Thought→Action→Observation 试错过程 当前任务结束后归档或丢弃

交接链路四步：

  1. 主动抛出：售前 Agent 调用 Transfer_To_PostSales(reason="用户要退款", order_id="12345")
  2. Harness 拦截：截获 Transfer Tool，break 售前 Loop，将 reason + order_id 写入 Redis 全局黑板
  3. 智能浓缩：Harness 用轻量 Prompt 对历史对话做极简摘要（如”用户情绪焦躁”），存入全局黑板
  4. 初始化新 Loop：开辟新草稿纸，启动售后 Loop。售后 Agent 醒来时，Context 极其干净——只有系统 Prompt + 交接变量 + 前情摘要

一句话：多 Agent 交接本质是 Harness 主导的”线程销毁与重建”。Agent 之间不直接通信，通过 Harness 总线用标准 Tool Call 完成数据提取移交。

4.1.4 并发调度与抢占式中断

复杂场景下 Supervisor 不是”转交任务后就消失”，而是转变为异步等待的挂起状态。

并发执行：Harness 用多线程/异步协程同时启动多个 Worker Agent Loop，通过统一 Token 机制并行计算消耗。子 Agent 之间禁止直接对话（防死循环+Token 爆炸），必须通过 Harness 管控的全局黑板交换结构化数据。

抢占式中断（用户变需求）：

  1. Harness 是唯一入口——用户新消息先到 Harness，不直接塞给子 Agent
  2. Harness 发现当前 Session 有子 Agent 在异步执行 → 立刻对用户输入做极速意图判定
  3. 意图变更 → Cancel 所有子协程，销毁 Loop，终止未发出的 MCP 调用
  4. 唤醒 Supervisor，注入系统中断消息：[System Interruption]: "用户中止了当前任务，子任务已被强制取消。请重新规划。"
  5. Supervisor 拿到中断上下文 → 输出新 Plan → Harness 启动新 Worker

4.1.5 Harness 状态机设计

任何 Agent 在 Harness 中永远只处于四种状态之一：

状态 含义 触发条件
🟢 INIT 初始化就绪 Agent 刚被分配任务，上下文和 Tool 列表准备完毕
🔵 RUNNING 运行/推理中 大模型在输出或等待大模型输出
🟡 SUSPENDED 挂起/阻塞 Tool Call 发出后，等外部 API 返回或人工审核（可能持续几小时）
⚫ TERMINATED 终止/销毁 任务完成输出答案，或超时/死循环被 Harness 熔断

状态流转由事件驱动（Event-Driven）。不是手写嵌套 while——业界标准用**图计算（Graph-based）**方式：每一步是图上的一个节点，状态流转是节点间的连线。Harness 按图的路径执行，状态流转清晰可追溯。

4.1.7 Harness 与 LangGraph 的落地对应

Harness 概念 LangGraph 落地
中间件拦截 Tool 节点的前置逻辑
HITL 挂起 interrupt_before 在节点前暂停

4.2 LLM API 网关设计

需求：统一接入多个 LLM（GPT/Claude/DeepSeek/GLM），支持负载均衡、降级、成本控制、权限管理。

第一层：API Schema 统一与流式抹平

不同厂商的请求/响应协议差异巨大，网关统一映射为一套标准 Schema（通常以 OpenAI API 为行业标准）。

差异点 网关处理
请求/响应体 Claude 的 Messages API、OpenAI 的 Completions API、GLM 的特定参数 → 统一映射
流式传输 统一 SSE 事件流格式，抹平不同模型 Chunk 结构差异
思考过程字段 DeepSeek-R1 等 reasoning 模型的 reasoning_content → 统一解析标准化输出

第二层：智能路由与无感切换

  • 故障转移 + 熔断降级：主模型 5xx / 429 / 超时 → 自动重试路由到备用模型。业务端对底层报错和重试零感知。
  • 策略路由：按成本（简单任务走低价模型，复杂任务走高成本模型）、按延迟/负载（动态评估各 Provider 的 TTFT 分发流量）。
  • AB 测试与灰度：按比例切流量给新模型。

第三层：模型差异抹平与能力补齐

  • Token 规范与上下文裁剪：不同模型的 Tokenizer（tiktoken/SentencePiece）和 Context Window 极限不同 → 统一 Token 估算与截断保护。
  • Function Calling / 结构化输出适配：原生支持 Tool Call 的模型做格式转换；不支持 Tool Call 的模型，网关层通过 Prompt 注入 + JSON Schema 解析模拟实现 Tool Call 能力。

第四层：企业级统一治理与观测

  • 鉴权与多租户：统一颁发内部 API Key，隔离各业务线的权限与额度。
  • 用量与成本管控：实时统计 Request / Token 消费量，设置 TPM（Tokens Per Minute）和 RPM 限流。
  • 全链路可观测：监控 TTFT（首字延迟）、TPOT（生成延迟）、成功率、各 Provider 成本。
  • 内容安全与脱敏：请求入参 PII 脱敏，响应出参合规词过滤。

面试答题框架（四层版）：

“LLM 网关四层设计。一，Schema 统一——不同厂商 API 协议、SSE chunk、思考字段全部映射成一套标准。二，智能路由——故障熔断降级 + 策略路由（成本/延迟/AB灰度）。三，能力补齐——Token 估算截断 + 不支持 Tool Call 的模型用 Prompt 注入模拟。四，治理观测——多租户鉴权、TPM/RPM 限流、TTFT/TPOT 监控、PII 脱敏。核心价值是让业务方对底层模型差异零感知。”
