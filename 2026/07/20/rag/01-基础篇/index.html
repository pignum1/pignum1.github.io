RAG 01：基础篇 — 从零搭建 RAG，理解三大核心组件

基于 RAG From Scratch Part 1-4。本文覆盖 RAG 系统的 Indexing（索引）、Retrieval（检索）、Generation（生成）三大组件。

核心观点：RAG 的质量不取决于底层 LLM 有多强，而取决于三个工程决策——怎么切（Chunking）、怎么搜（Retrieval）、怎么排（Rerank）。这三个决策做好了，用 GPT-3.5 也能达到 GPT-4 直答的效果。

3.2 Chunking 策略 —— 全文最关键的决策

面试官问”chunk_size 怎么定”，不是在等一个数字，是在等你讲出权衡。

3.2.1 好 Chunk 的四大准则

准则 含义 违反后果
语义完整 一个 chunk 包含一个完整的语义单元 句子截断 → 向量无意义 → 检索不到
粒度适中 不太大（噪音多），不太小（上下文断裂） 过大→检索不准；过小→信息不全
上下文自足 chunk 本身可独立理解，不依赖前后文 “如上所述”这种指代 → LLM 看不懂
可溯源 metadata 记录来源文档、页码、章节 检索到了但不知道出自哪里

3.2.2 五种切分策略对比

策略 怎么切 适合 局限 推荐度
固定大小 每 N 字符一刀切 快速原型 句子被截断，语义破碎 ⭐
递归分块 \n\n→\n→空格→字符 逐级降级 通用首选 对表格/代码不够友好 ⭐⭐⭐⭐⭐
语义分块 按段落/章节边界（用 Embedding 判断断点） 结构清晰的文档 依赖模型判断，有误差 ⭐⭐⭐⭐
句子级 按句号/换行切，保持句子完整 FAQ、对话 单句可能太短，信息量不足 ⭐⭐⭐
Agent 分块 用 LLM 逐段判断”这里该不该切” 复杂文档 慢、贵（每条 chunk 一次 LLM 调用） ⭐⭐

3.2.4 上下文分块（Contextual Chunking）—— 零成本提升近一倍的技巧

来自参考文章的核心技巧：给每个 chunk 前面拼接它的父标题路径。

为什么有效：向量 Embedding 会编码整个文本，包含了标题信息后，chunk 向量”知道”自己属于哪个主题。用户搜”RLHF 训练流程”时，带标题的 chunk 匹配度远高于纯内容 chunk。

实测数据（来自参考文章）：

方案 Recall@5
普通分块 41%
上下文分块（拼接父标题） 78%

代价：几乎为零。只是在入库前多做了字符串拼接。

3.2.5 不同文档类型的切法速查

文档类型 建议策略 chunk_size 特殊处理
技术博客/文章 递归分块 500-1000 拼接父标题路径；保留标题作为 metadata
代码 AST 按函数/类边界 不限 按 def/class 切，不按字符硬切
FAQ 按 Q&A 对切 — 一个 Q&A 对 = 一个 chunk，不需要 overlap
PDF 论文 递归分块 800-1500 表格/公式单独提取描述后再入库
对话记录 按轮次切 — 保留 speaker 信息在 metadata
API 文档 按接口切 — 一个接口（endpoint + params + example）= 一个 chunk
合同/法律文书 按条款切 不限 保留条款编号，方便溯源
财报/数据报告 语义分块 1000-2000 表格转 Markdown 描述，保持完整不切

3.2.6 chunk_size 怎么定 —— 面试标准回答

“chunk_size 取决于文档类型和 Embedding 模型的输入上限。一般从 500-1000 开始实验。太小（<200）丢失上下文，太大（>2000）引入噪音。实践中加 10-20% overlap 防止关键信息被切断。对不同格式——代码用 AST 按函数切、FAQ 按 Q&A 对切、表格保留完整结构——不一刀切。更重要的是做上下文分块——给每个 chunk 拼接它的父标题路径，实测 Recall 能从 41% 提升到 78%。“

chunk_size 优势 劣势 适合场景
< 200 精确匹配关键词 上下文断裂 FAQ、代码片段
500-1000 平衡精度和上下文 — 通用推荐
1000-2000 语义完整 噪音增多 论文、长报告
2000+ 篇章级完整 向量稀释严重 特定摘要场景

本质

相似度计算（Cosine Similarity）

模型 维度 最大输入 中文支持 部署方式 费用

选模型的核心考量：

  1. 最大输入长度 > 你的 chunk_size（否则会被截断）
  2. 中文支持 — 做中文知识库优先选 BGE 系列
  3. 维度 — 高维度=更精准但存储大、检索慢

3.4 向量存储（VectorStore）

内部做了什么：

  1. 对每个 chunk 调 embedding.embed_query(chunk.page_content) → 向量
  2. 把 (向量, chunk文本, metadata) 三元组存入数据库
  3. 建向量索引（如 HNSW），加速近邻搜索

向量数据库选型：

数据库 定位 适合规模 特点
Chroma 轻量级，嵌入式 < 10 万 本地开发首选，pip install 即用
pgvector PostgreSQL 插件 < 100 万 和业务库共用一个 PG 实例，运维简单
Milvus 分布式向量数据库 百万～亿级 支持 GPU 加速索引，云原生
Pinecone 全托管云服务 不限 零运维，按量付费
Weaviate 开源 + 云托管 < 千万 自带向量化 + 混合检索

四、Retrieval 深度拆解

检索不是”一个向量相似度搜索”就完事了。工业界标准的检索链路是三条路径逐步收敛：

4.1 向量检索（Dense Retrieval）

三种检索模式：

search_type 算法 什么时候用
"similarity" 纯余弦相似度（默认） 通用场景
"mmr"（Max Marginal Relevance） 兼顾相似度 + 多样性 Top-K 结果太雷同时（如多次返回同一段的不同 chunk）
"similarity_score_threshold" 只返回相似度 > 阈值的 需要过滤低分噪音（如阈值 0.7）

K 值怎么选：

K 值 效果 适合
1-2 信息不足，LLM 没东西参考 ❌ 几乎不用
4-10 平衡信息量和噪音 ✅ 通用推荐
20+ 噪音多，Token 浪费，LLM 被无关内容干扰 ⚠️ 仅当配了 Reranker 精排时可用

向量检索的天然局限：对同义词、缩写、精确关键词匹配差。

4.4 Rerank 精排 —— 把”差不多”变成”就是它”

Bi-Encoder vs Cross-Encoder

这是理解 Rerank 的核心概念：

两者的分工：

Bi-Encoder Cross-Encoder
角色 粗排（Recall） 精排（Rerank）

七、多模态 RAG —— 图片/表格/视频怎么被检索到

面试官问”图片、表格怎么处理”，是在考你半结构化数据的 Indexing 策略。

7.1 核心思路：Indexing 时统一成文本模态

图和表不能直接向量化——必须在 Indexing 阶段用 Vision LLM 把它们转成文字描述，再用描述向量去检索。

7.2 不同文件类型处理速查

文件类型 怎么处理 关键工具 面试一句话
图片里的文字 OCR 提取 → 文本向量化 Tesseract / GPT-4V “先用 Vision 模型读图，转成文字再建索引”
图表/架构图 LLM 生成文字描述 → 向量化 GPT-4V / Qwen2-VL “让模型描述图里有什么、表达了什么趋势”
PDF 表格 保留 Markdown 结构 → 整表向量化 Unstructured “表格不切，保留完整结构作为一个 chunk”
PPT 每页 = 文本 + 图片，分别处理 Unstructured “一页 PPT 拆成文本和图片两路”
视频 音频转文字 + 关键帧截图 → 描述 Whisper + GPT-4V “视频 = 音频文案 + 关键画面描述”

7.3 面试追问：为什么不等检索时再去读图？

“因为检索时只有用户问题的向量，没法直接和图片像素做相似度匹配。必须在 Indexing 阶段提前把图/表转成文字，让它们也能被搜到。多模态 RAG 的本质就是——Indexing 时把一切统一成文本模态。”

7.4 实际索引结构

检索命中后，LLM 拿到的是文字描述 + 原始图片路径，可以展示给用户。

八、RAG vs Fine-tuning —— 什么时候用什么

8.1 一句话区别

  • RAG = 考试带小抄（需要时查，考完扔）——知识在外面
  • Fine-tuning = 考前死记硬背（记在脑子里）——知识在模型参数里

8.2 全景对比

维度 RAG Fine-tuning
原理 检索外部文档 → 拼进 Prompt 用标注数据继续训练 → 修改模型权重
知识存储 外部向量数据库 模型参数内部
知识更新 更新文档 → 重建索引，分钟级 重新标注数据 → 重新训练，天~周级
事实准确性 高（有文档约束） 中（可能用旧知识或编造）
答案可溯源 ✅ 知道来自哪篇文档 ❌ 无法追溯
延迟 多 100~500ms（检索开销） 无额外延迟
成本 API 调用付费（低） GPU 训练 + 数据标注（高）
数据需求 文档库（无需标注） 标注数据集（问题-标准答案对）
控制目标 “说什么”（内容/事实） “怎么说”（风格/格式/语气）
幻觉风险 低（有文档兜底） 较高（可能自信地胡说）

8.3 一张图决定选谁

8.4 两者可以一起用

“Fine-tuning 教模型怎么说，RAG 教模型说什么。两者互补，不是互斥。”

九、面试速查

Q1：chunk_size 设多少合适？

从 500-1000 开始实验。太小（<200）丢失上下文，太大（>2000）引入噪音。加 10-20% overlap。关键技巧：上下文分块（拼接父标题路径），实测 Recall 从 41%→78%。

Q2：图片/表格能被 RAG 检索到吗？

能。Indexing 时用 Vision LLM 生成文字描述，用描述向量检索。命中后返回描述 + 原始文件路径。核心原则：Indexing 时把一切统一成文本模态。

Q3：RAG vs Fine-tuning 怎么选？

知识频繁更新、需要溯源 → RAG。需要特定格式/风格、低延迟 → Fine-tuning。两者可互补：Fine-tuning 教”怎么说”，RAG 教”说什么”。

Q4：向量检索的局限？怎么解决？

同义词/缩写匹配差。三步解决：① 混合检索（向量 + BM25）→ Recall +7%；② Reranker 精排（Cross-Encoder）→ Recall +9%；③ 查询变换（HyDE / Multi Query，02章）→ Recall +3%。

Q5：为什么不全用 Cross-Encoder 做检索？

全库 10000 篇每篇都要和问题拼在一起跑模型，太慢太贵。Bi-Encoder 快速捞候选（粗排），Cross-Encoder 精细挑（精排），是工业界标准做法。

Q6：RRF 融合比简单加权好在哪里？

不需要调权重（只有 k 一个参数），不受分数量纲影响（向量分 [0,1]，BM25 分可以几百），基于排名更稳定。

Q7：RAG 系统的性能瓶颈在哪？

Rerank（Cross-Encoder）占全链路延迟 ~50%，是最重的一步。优化方向：① 减少候选数（20 而非 50）；② 批量推理（多对同时打分）；③ 换更快的 Reranker 模型。
