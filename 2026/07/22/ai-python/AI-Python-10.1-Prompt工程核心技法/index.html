10.1：Prompt 工程核心技法

Prompt Engineering 不是”写一句提示词”——是让 LLM 按你的预期输出结果的系统工程。本文覆盖面试最常问的三种技法：CoT 思维链、Few-Shot 少样本、结构化输出。

零、本章速查表

技法 做什么 核心机制 成本 一句话
CoT 思维链 让 LLM 分步推理，不直接给答案 在 Prompt 中要求 “Let’s think step by step” Token 消耗 +50-100% “把大问题拆成小步骤，一步步推出答案”
Few-Shot 给 LLM 看几个例子，照着格式输出 在 Prompt 里嵌入 2-5 个示例 Token 消耗 +示例长度 “给你几个范例，照着这个格式来”
结构化输出 强制 LLM 输出 JSON/Pydantic，不跑偏 Function Calling / with_structured_output 零额外成本 “不是建议输出 JSON，是强制只能输出 JSON”

一、CoT 思维链（Chain-of-Thought）

1.1 一句话

不让 LLM 直接给答案，让它把推理过程写出来，然后从推理过程中提取答案。

1.2 为什么有效

1.3 两种实现方式

Zero-Shot CoT：加一句魔法咒语就行

Few-Shot CoT：给几个推理范例

1.4 什么时候用、什么时候不用

该用 CoT 不该用 CoT
数学推理、逻辑推理 简单事实问答（”法国的首都是什么？”）
多步问题求解 翻译、摘要
需要验证中间结果 创意写作

原则：问题需要多步推理才用 CoT，简单问题加 CoT 浪费 Token。

1.6 CoT 之外的推理模式全景

CoT 是最基础的，但不是唯一解。复杂度和可靠性逐级递增：

模式 核心思路 复杂度 适合
CoT 一条链推理到底 ⭐ 数学/逻辑
Self-Consistency CoT 跑 N 次，多数投票 ⭐⭐ CoT 不稳定时
ToT 每步探索多条路径，剪枝 ⭐⭐⭐⭐ 需要回溯
GoT 思想可合并、拆分、聚合 ⭐⭐⭐⭐⭐ 大纲/架构
ReAct 推理 + 调工具交替 ⭐⭐⭐ Agent 标配
Reflection 自我评价，不行重来 ⭐⭐⭐ 代码/写作

Self-Consistency：多跑几次，投票决定

ToT（Tree of Thoughts）：每步分叉，剪枝前进

GoT（Graph of Thoughts）：思想可以合并

ReAct：推理 + 行动交替

ReAct = Agent 的标准工作模式，LangChain 的 create_react_agent 底层就是这个。

Reflection：自己给自己打分

一张表决定用哪个

你的问题 选哪个
简单数学/逻辑推理 CoT
需要高可靠性、容错 Self-Consistency
多步探索、需要回溯 ToT
多线汇聚、综合结论 GoT
需要查外部信息 ReAct（Agent 标配）
需要高质量输出、自动迭代 Reflection

1.7 市场上 Agent 的执行模式

主流答案：ReAct + 变体。 几乎所有生产级 Agent 的底层都是 ReAct，只是每家有自己的改进：

框架/产品 执行模式 特点
LangChain Agent ReAct 标准版，思考→行动→观察 循环
LangGraph ReAct + 图编排 ReAct 循环画成有向图，可加条件分支、并行、循环
OpenAI Assistant ReAct + 内置工具 你只定义工具，OpenAI 内部自动做 ReAct
Claude Agent (MCP) ReAct + MCP 工具 思考→调 MCP Server→拿到结果→继续思考
AutoGPT ReAct + 长链规划 先规划子任务列表，每个子任务跑 ReAct
Manus Plan-then-Execute 先出完整计划 → 用户确认 → 逐步执行
SWE-Agent / Devin ReAct + 代码编辑 思考→读文件→写代码→运行→看报错→修正

为什么都是 ReAct？

实际业务中的选择：

场景 选什么 原因
客服机器人 ReAct 一问一答，不需要复杂规划
代码助手 ReAct + Reflection 写完检查一遍，多轮迭代
数据分析 Agent ReAct + Plan 先看有哪些表→写SQL→看结果→调整
自动化工作流 LangGraph（ReAct 图化） 流程固定，节点+条件边

市面上没有 Agent 直接用裸 CoT 或裸 ToT。ReAct 是绝对主流，Plan-Execute 是变体，LangGraph 是工程化封装。面试时就说 “我们的 Agent 基于 ReAct 模式，用 LangGraph 做图化编排”。

二、Few-Shot 少样本学习

2.1 一句话

给 LLM 看 2-5 个范例，让它按同样格式输出。不是微调模型，只是把例子写在 Prompt 里。

2.2 为什么有效

2.3 示例怎么选

原则 说明
覆盖边界 正面、负面、中性各放一个，不要让 LLM 只见过一种
从简单到复杂 先给简单的例子，再给复杂的
和目标格式一致 你期望输出什么格式，例子就用什么格式
2-5 个够用 太多了反而让 LLM 困惑，且浪费 Token

三、结构化输出

3.1 一句话

让 LLM 的输出可以被代码可靠地解析——不一定是 JSON，但一定是机器可读的结构。

3.2 四种方式

方式 原理 可靠性 适用场景
Prompt 描述 “请输出 JSON 格式” ⚠️ 低 快速验证、一次性脚本
JSON Mode (API 参数) response_format={"type": "json_object"} 中 OpenAI API
Function Calling 协议层 Schema 约束 高 GPT-4 / DeepSeek / GLM 等支持 FC 的模型
Prompt + 后处理 明确格式标记 + 代码解析兜底 中高 不依赖模型能力，任何 LLM 都适用

3.3 Function Calling 方式（协议层硬约束）

优点：最可靠，模型在 token 级别被 Schema 约束。
缺点：模型必须支持 Function Calling（开源小模型、本地多模态模型不支持）。

3.6 为什么 The Boy 选择 Prompt 后处理而不是 Function Calling？

原因 说明
LangGraph 架构 The Boy 用 LangGraph 做图编排，每个节点处理结构化 State（TypedDict），节点内部就是普通 LLM 调用 → 后处理提取结果 → 更新 State
模型无关 不绑定特定模型 API，换模型不用改代码
本地模型 BGE-M3、Qwen2-VL 等本地模型不支持 Function Calling，Prompt 方式是唯一选择
多层兜底 正则提取失败 → 降到更宽松的解析 → 再失败 → 让 LLM 重新生成

3.8 该选哪个？

两种方式不是互斥的。生产系统中，Function Calling 优先，Prompt 后处理做 fallback——“硬约束优先，软约束兜底”。

五、面试速查

Q1：CoT 和 Few-Shot 有什么区别？

“CoT 是教 LLM 怎么想（展示推理过程），Few-Shot 是教 LLM 输出长什么样（给格式范例）。两者常组合——Few-Shot 里给 CoT 范例。”

Q2：结构化输出一定要用 Function Calling 吗？

“不一定。两种主流方案——Function Calling 是协议层硬约束，最可靠，但依赖模型支持；Prompt + 后处理是软约束，用自定义标记（如 <decision>）约定格式，代码正则提取后校验。The Boy Assistant 用的是后者，因为 LangGraph 架构下节点本身就是结构化 State，而且本地模型（BGE-M3、Qwen2-VL）不支持 Function Calling。原则：Function Calling 优先，Prompt 后处理兜底，两种不是互斥的。”

Q3：Few-Shot 给几个例子合适？

“2-5 个。太少覆盖不全，太多浪费 Token 且可能让 LLM 困惑。关键是例子的质量（覆盖边界 case）而不是数量。”

Q4：CoT 的代价是什么？

“Token 消耗增加 50-100%，延迟增加。简单事实问答不要用 CoT。判断标准：问题需要多步推理才加 CoT，否则就是浪费。”
