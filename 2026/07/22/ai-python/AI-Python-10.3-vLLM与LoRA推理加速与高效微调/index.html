10.3：vLLM 与 LoRA — 推理加速 + 高效微调

大模型落地最后一公里：vLLM 解决”怎么跑得快”，LoRA 解决”怎么训得省”。生产环境中，vLLM 做推理服务，LoRA 做领域适配，两者组合实现”一个基座 + N 个 Adapter”的高效部署。本文覆盖原理、代码、以及面试中最关键的几个问题。

一、vLLM 解决什么问题——三个浪费场景

1.1 场景一：KV Cache 碎片化浪费

三个请求来了——A 只需 100 token、B 只需 50 token、C 需要 2000 token。原生方式给每个请求按最大长度（2048）预分配连续显存：

PagedAttention 解法：把 KV Cache 切成 16 token 一个 Block。不预分配、不要求连续、需要多少给多少。

1.2 场景二：相同 System Prompt 重复存储

100 个用户前面都挂着同一个 5000 token System Prompt（”你是一个专业助手…”）。

为什么 KV Cache 能共享？缓存的是 K 和 V 的原始值，不是 Attention 的输出。不同用户的 Q 不同，去匹配同一份 K → 权重不同 → 从同一份 V 提取出的信息不同 → 最终结果自然不同。K 和 V 只取决于 System Prompt 本身，100 个用户完全一样。

三、Continuous Batching

3.1 一句话

不是”一个 batch 跑完再组下一个”，而是每个 decode step 后重新组装 batch——完成的立即移除，新的立即插入。

四、LoRA：低秩适应

4.1 问题：全量微调贵在哪

4.2 核心原理

一句话：不改原权重 W，在旁边加一个低秩旁路 A×B。W 冻住，只训 A 和 B。

权威图解（来源：dvgodoy/LLM-visuals，CC-BY）：

上面是冻住的原始权重 W，下面是 LoRA 旁路 A→B。两路输出相加。只有橙色部分需要训练。

原本 W 是 d×d 的大矩阵（如 4096×4096 = 16M 参数）。LoRA 用 A(d×r) 和 B(r×d) 两个小矩阵的乘积近似 ΔW。r 很小（4~16），参数量从 d² 降到 2dr，少了上百倍。

关键设计：

设计 做法 原因
A 初始化 小随机值 打破对称，让 A 有初始方向
B 初始化 全零 保证 ΔW = B×A = 0，训练从零开始
α/r 缩放 output = Wx + (α/r) × (xAB) 控制 LoRA 更新幅度，α 通常 = r 或 2r
只在 Q、V 注入 不改 K 和 FFN Q 决定”关注谁”，V 决定”输出什么”，任务相关性最强

4.3 为什么”低秩”有效？

低内在维度假设：模型适配下游任务时，权重的变化 ΔW 集中在一个低维子空间里。实验证明 r=8 的 LoRA 就和 r=64 的共享大部分关键信息方向，剩下的方向主要是噪声。

六、面试速查

面试频率评估：vLLM + LoRA 是 2025-2026 年 AI Infra / MLE 岗的中高频题。PagedAttention 和 LoRA 原理是面试官最爱追着问的——不是”你知道名字就行”，而是要能讲清楚”为什么这么设计”。属于80 分 → 95 分的关键差距题。

Q1：PagedAttention 为什么能提升吞吐量？和操作系统有什么关系？（高频）

“核心原因是 KV Cache 内存利用率从 20-40% 提升到 ~96%。传统方法给每个序列预分配最大长度的连续显存，大部分是空的。PagedAttention 把 KV Cache 切成固定大小的 Block，通过 Block Table 做逻辑到物理的映射——和 OS 虚拟内存分页一模一样。再加上 Copy-on-Write 共享前缀（如 System Prompt），进一步节省显存。省下来的显存可以放更多请求 → 更大的 Batch → 更高吞吐。”

Q2：Continuous Batching 和 Static Batching 有什么区别？（高频）

“Static Batching 等整个 batch 所有请求都跑完才释放，一个慢请求拖累一整个 batch。Continuous Batching 每个 decode step 后重新组装 batch——跑完的立即移除，新的立即加入。GPU 永远满载，平均延迟降 10 倍。”

Q3：LoRA 为什么只微调 Q 和 V 的投影矩阵？

“实验结论：只注入 Q、V 效果最好。Q 决定’关注什么位置’，V 决定’关注到之后输出什么内容’——这是 Attention 中任务相关性最强的两个矩阵。K 主要负责匹配，通用性更强，不需要改。FFN 层的参数太多且对通用知识影响大，改了容易灾难性遗忘。”

Q4：LoRA 的 rank 怎么选？（非常高频）

“r=8 是经典默认值，r=16 更稳。r 太小（<4）表达能力不足，太大（>64）收益递减且可能过拟合。实际调参：先用 r=8 快速验证，效果好就不动；不好再试 r=16 或 r=32。另外不同层可以用不同 rank——浅层通用特征用低 rank，深层任务特征用高 rank。”

Q5：vLLM + LoRA 部署有什么要注意的？

“1）--enable-lora 和 --max-loras 必须配置，max-loras 要 ≥ 实际并发使用的 adapter 数。2）LoRA adapter 的大小和 rank 有关，rank=64 的 adapter 约几十 MB 到几百 MB。3）异构 LoRA batching 有 Punica GEMM 内核优化，吞吐量接近纯基座推理的 85-90%。4）如果用到 4-bit QLoRA 基座，adapter 必须在启动时指定，不支持运行时热切换。”

Q6：LoRA 怎么合并回原模型？推理有额外延迟吗？

“LoRA 的一个关键优势是推理时零额外延迟。因为 ΔW = B·A 是低秩的，可以直接计算 B·A → 加到原始 W 上 → 得到一个和原来一样大的矩阵。合并后推理速度和原模型完全一样。vLLM 不做物理合并（为了支持多个 adpater 共享基座），但通过 Punica 内核让 LoRA 旁路的计算开销可以忽略不计。”
