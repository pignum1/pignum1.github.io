RAG 09：GraphRAG 实战

传统 RAG 只能检索”文本片段”，无法理解实体间的关系。GraphRAG 将知识图谱与向量检索结合，能回答”谁和谁有什么关系”这类需要跨文档推理的问题。本章讲解知识图谱构建、图谱检索与向量检索的融合。

1. 传统 RAG 的局限

1.1 什么问题传统 RAG 回答不了？

场景： 知识库里有 10 篇关于公司员工的文档。

根因： 传统 RAG 只能找”写出来的文本”，无法推理”没写出来但可以从关系推导的信息”。

1.2 GraphRAG 如何解决

GraphRAG 在向量检索之外，额外构建一个知识图谱，显式存储实体和关系：

    flowchart LR
    A[张三] -->|汇报给| B[王五]
    C[李四] -->|汇报给| B
    A -->|所属| D[技术部]
    C -->|所属| E[市场部]
    B -->|职位| F[CTO]
    A -->|职位| G[经理]
    C -->|职位| H[总监]

    style C fill:#e6f7e6,stroke:#4caf50,stroke-width:2px,color:#333

用户问”张三和李四的关系”时，图谱可以沿着边遍历，推理出两人都汇报给王五。

1.3 和 Multi-representation / RAPTOR 的关系

这三者都是对 flat chunking 的升级方案，但各管一个维度，互补而非替代。

Multi-representation RAPTOR GraphRAG
解决什么问题 chunk 太小，概括性问题找不到 长文档层级结构丢失 chunk 之间实体关系丢失
怎么组织索引 摘要向量 + 原文，两层 递归聚类 → 树 实体+关系 → 图
检索方式 搜摘要 → 返回原文 自顶向下遍历树 图遍历 + 向量融合
适合场景 “这篇论文的核心结论” “第三章讲了什么” “A 公司和 B 公司有什么关联”
对应文章 04 高级索引篇 04 高级索引篇 本章（09）

一个例子串起来：文档库有 50 篇 AI 行业研报，用户问”OpenAI 和 Anthropic 在 AI Safety 方面各有什么布局？”

一句话：Multi-repr 管”这篇文档整体在说什么”，RAPTOR 管”这篇文档的哪一章讲了什么”，GraphRAG 管”不同文档的实体之间有什么关联”。实际项目中三者可以叠加使用。

2. 知识图谱基础

2.1 什么是知识图谱？

知识图谱 = 实体（节点）+ 关系（边）+ 属性

组成 例子 说明
实体（Node） 张三、技术部、Python 图中的”点”
关系（Edge） 汇报给、所属、擅长 连接两个实体的”线”
属性（Property） 年龄=30、级别=P7 实体上的附加信息

2.3 知识图谱 vs 向量检索

维度 向量检索 知识图谱
存储 文本片段 + 向量 实体 + 关系
擅长 “X是什么？” “X和Y有什么关系？”
推理 无（只匹配相似文本） 有（沿关系遍历）
精确度 模糊匹配 精确结构化
构建成本 低（自动 Embedding） 高（需要抽取实体和关系）

5. GraphRAG：图谱 + 向量融合

5.1 为什么要融合？

单独用 能回答 不能回答
向量检索 “Python装饰器怎么用？” “张三和李四是什么关系？”
知识图谱 “张三和李四是什么关系？” “请详细解释FlashAttention的原理”

融合后： 两种问题都能回答。

5.2 融合架构

    flowchart TB
    Q[用户问题] --> C{问题类型?}

    C -->|事实查询\nX是什么| V[向量检索]
    C -->|关系查询\nX和Y的关系| G[图谱查询]
    C -->|复杂推理| H[混合检索\n向量+图谱]

    V --> L[LLM 生成回答]
    G --> L
    H --> L

6. GraphRAG 的适用场景

6.1 什么时候用 GraphRAG？

场景 是否需要 GraphRAG 原因
企业组织关系 是 需要推理汇报链、协作关系
人物/事件关联分析 是 需要跨文档连接信息
知识推理 是 需要多跳推理（A→B→C）
简单 FAQ 否 向量检索足够
文档问答 否 不涉及关系推理
代码/技术文档 否 查具体概念即可

6.2 GraphRAG 的成本

维度 成本
构建 高（需要 LLM 抽取实体/关系）
存储 中（图数据库 + 向量数据库）
查询 中（需要判断路由 + 两路查询）
维护 高（实体/关系需要更新）

建议： 只有确实需要”关系推理”的场景才上 GraphRAG，普通 RAG 场景用 07.1-07.3 的方案就够了。

6.3 实战场景分析：训练平台操作文档

一个训练平台的配置项有几十个，需不需要 GraphRAG？结论不是一刀切的——要看用户问的是”怎么配”还是”X 和 Y 怎么一起配”。

配置项的复杂性

训练一个模型需要同时配多个维度，它们不是独立的，而是一张约束关系网：

跨项约束示例：

关联类型 例子
资源约束模型 A100 80G 最多放 70B 模型，再大要多卡/量化
数据集约束资源 10TB 数据集 → 需要 SSD + 多节点并行加载
奖励函数约束数据集 RLHF 的 reward model 输出格式 → 数据集标注格式必须匹配
模型约束超参 70B 用 batch_size=1-2，7B 用 batch_size=32
跨项冲突 多节点 + 小数据集(< 1000 条) = 通信开销 > 计算收益，白花钱

两种方案对比

方案 A：纯元数据 + Chunking

适用：用户问单点操作型问题。

局限：用户问组合型问题时答不好——“我要训练 70B 模型，4 卡 A100 够不够？batch_size 设多少？”

方案 B：元数据 + 知识图谱（推荐）

检索时三层协同：

落地建议

阶段 做什么 什么时候
P0 元数据过滤 + HyDE + Rerank 现在就做，覆盖 80% 单点操作问题
P1 知识图谱建模约束关系 当用户频繁问”X 和 Y 怎么配”时加入
P2 GraphRAG 融合检索 P1 的图谱数据积累够了再上

核心结论：操作文档的首要价值是”查得到步骤”，P0 先跑起来。配置约束是锦上添花——等你发现用户真正在问组合型问题时再加图谱，不要一开始就上全套。
