RAG 04：高级索引篇 — 用更聪明的方式组织索引

基于 RAG From Scratch Part 12-14。三种技术解决同一个痛点：flat chunking 太粗糙，一篇长文档应该怎么组织索引才能检索得更准？

和 05 篇的关系：04（本章）在 索引阶段 优化数据结构 → 产出更高质量的候选 → 交给 05 在 检索后 做精排（Re-ranking）、质量评估（CRAG）、逐句自省（Self-RAG）。04 让检索”找得更准”，05 让检索”信得更对”，两者在 RAG 流水线中首尾衔接。

零、本章速查表

技术 解决什么问题 核心思想 索引大小 检索精度 工程复杂度

RAPTOR 层级结构丢失 递归聚类 → 树状索引 N× 高 ⭐⭐⭐⭐

核心问题：

这些技术用在哪个阶段？

三种技术都同时影响索引（Indexing）和检索（Retrieval）两个阶段——它们在索引时改变数据结构，在检索时改变查询方式。不是”切片替代品”，而是在切片之后的升级方案。

技术 索引阶段做了什么 检索阶段做了什么 和基础篇的关系
Multi-representation LLM 生成摘要 → 摘要向量 + 原文分存两层 用摘要向量匹配 → 返回原文全文 替代基础篇的”chunk 直接存+搜”
RAPTOR 递归聚类 chunks → LLM 逐层生成摘要 → 建树 自顶向下遍历树，逐层定位 在基础篇切块之后，增加层级聚类
ColBERT 每个 Token 独立向量化（而非每 chunk 一个向量） Query Token × Doc Token → MaxSim 匹配 替代基础篇的”每 chunk 一个向量”

一、Multi-representation Indexing（多表征索引）

一句话

每篇文档生成两个向量：摘要向量用来检索匹配，原文向量（或直接存原文）用来返回给 LLM。检索时”搜摘要、返回原文”。

面试要点

  • 和普通 RAG 的区别：普通 RAG 用 chunk 的向量检索，multi-rep 用摘要的向量检索，返回原文
  • 什么场景需要：文档很长（论文、报告、法律文书），用户的问题往往是概括性的
  • 额外成本：每篇文档多一次 LLM 调用（生成摘要），批量处理可并行

二、RAPTOR（递归抽象处理）

一句话

把 chunks 按语义聚类 → 每类生成摘要 → 摘要再聚类 → 更高层摘要 → 形成树状索引。检索时自顶向下遍历，找到最匹配的层级。

树的层数不是固定的：小文档可能只有 2 层，大论文可能有 4-5 层。层数由聚类算法自动决定。

面试要点

  • 核心创新：不是 flat 的一层 chunk → vector 映射，而是递归构建层级索引
  • 检索效率：不需要扫全部 chunks，自顶向下剪枝，对数级复杂度
  • 适用场景：长文档（论文、报告、书籍），需要概括性回答
  • 工程复杂度高：需要聚类算法 + 多次 LLM 摘要生成，建索引慢

三、ColBERT（Token 级交互检索）

一句话

传统方式是一个文档一个向量。ColBERT 是文档里每个 Token 一个向量。检索时 Query 和 Document 做 Token 级别的精细匹配。

为什么一个向量不够

MaxSim 匹配

查询和文档做Token 级匹配：

ColBERT 的分数 = 每个查询 Token 找到的最佳文档 Token 匹配分的平均值。这就是”延迟交互”（Late Interaction）——查询和文档分别先算好各自的 Token 向量，检索时才做交互匹配。

五、面试速查

Q：三种技术什么时候用？

“长文档需要概括性检索 → Multi-representation 或 RAPTOR。需要最高检索精度（如法律/医疗）→ ColBERT。工程资源有限 → Multi-representation 成本最低。想展示架构深度 → RAPTOR 的递归聚类思想最亮眼。”

Q：ColBERT 为什么没大规模流行？

“存储成本太高——每个 Token 一个向量，索引大小是传统 Embedding 的 100 倍。检索时需要做 Token 级交互，速度也慢。实际项目中通常用传统 Embedding + Reranker 来平衡精度和成本。”

Q：你项目中用的是哪种？

“Super Agent 的 RAG 用的是混合检索（Dense + Sparse）+ Reranker 的方案，没有用到这三种高级索引。原因是知识库大小在十万级，传统 Embedding + Reranker 的精度已经满足需求。RAPTOR 更适合百万级、长篇文档库的场景。”
