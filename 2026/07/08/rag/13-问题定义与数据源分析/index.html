RAG 13：问题定义与数据源分析

前面 01-12 学的是”怎么做 RAG”。13-16 进入生产级系统设计——以 The Boy Assistant 知识库为例，覆盖 4 类异构数据源的完整设计。本文聚焦问题定义和数据源分析。

零、本章速查表

数据源 文本风格 关键挑战 Chunk 策略 检索策略
平台操作文档 口语化、步骤化 截图信息丢失、步骤连贯性 Semantic（标题） Hybrid + Step-Back
算法论文 学术化、公式密集 公式语义丢失、风格不匹配 Section + 公式分离 HyDE + Hybrid
专利文档 法律化、结构化 权利要求引用关系 Field-split + 父子块 Query Structuring
业务数据 结构化、数值多 精确数值查询失效 Row → NL 描述 Tool Router SQL

一、为什么一个通用 KB 不够？

1.1 四类数据的本质差异

一刀切的设计必然有短板——用同一套 chunk_size、同一种检索策略处理四种数据，总有两三种效果差。

1.2 核心设计原则

原则 说明
KB 类型决定策略 4 类数据各有独立 KB，各自选择切分/检索策略，不互相污染
共用基础设施 Embedding 模型、pgvector、Reranker 跨 KB 共享
路由透明化 用户只问一个问题，路由层自动判断意图 → 分发到正确 KB
多模态统一 所有图片/公式/表格 → 文本描述 → Embedding，统一成文本模态

5.4 策略选择

  • 安全: 禁止裸 SQL 拼接，强制参数化查询

七、面试速查

Q：为什么不做成一个通用 KB，而是四个独立 KB？

“四类数据的文本风格、结构化程度、多模态需求完全不同——论文是学术化+公式，专利是法律化+引用链，文档是口语化+截图，业务是结构化+数值。一刀切的 chunk_size 和检索策略必然有短板。KB 类型决定策略，但 Embedding 模型、pgvector、Reranker 共用，既保证精度又控制成本。”

Q：论文为什么必须用 HyDE？

“用户用口语问’Transformer 怎么减少计算量’，论文里写的是’降低自注意力机制计算复杂度’——向量距离很远。HyDE 让 LLM 先编一个学术风格的假答案，用假答案的向量去搜，命中率大幅提升。”

Q：业务数据为什么不能用向量检索？

“向量检索不理解 ‘>’ ‘=’ ‘BETWEEN’。用户问’QPS 大于 1000 的模型’，向量会把所有提到 QPS 的文档都返回，不管数值。所以必须走 Tool Router——LLM 提取参数，转成参数化 SQL，既精确又防注入。”
